# pet-agent

基于真实宠物身份的**经验记录与调取** Agent。

> 面向真实宠物的长期个性化陪伴系统：以**一只真实存在的猫**为身份锚点，
> 把主人对这只猫的经验记下来、在用得上时调出来，并提供拟人化陪伴与行为解读。
>
> **知识对象是「主人的经验」，不是「猫的心思」**（D29）——「猫的意图」不可验证
> （人类自己也只有 26–40%，三分类随机水平 33%）；「主人的经验」可验证，
> **且使评测第一次成为可能**。

**三个值得单看的数**：

- **代价加权错误率 = 0.00，而 macro-F1 只有 0.74。**
  路由不犯高代价的错（`chat ↔ record_event` 是 0.9 且静默的），
  但**过度澄清率 27%** —— 那正是「宁可多问一句」的代价，被量化出来了。
- **MRR 0.71 < recall 1.00**：相关项都召回了，但没都排在最前。
  消融组（`naive-retrieval`）就是用来暴露这一项的。
- **群体先验在留出猫上不如多数类基线**（0.364 < 0.506）——
  一个真实的负面结果，详见 [§0.5](#05-群体先验一个真实的负面结果)。

### 消融：**证明某个约束是必要的**

守卫的对照不是「基线与无守卫」，而是**同一个会编造的 LLM** 开/关守卫：

| | 守卫开 | 守卫关 |
| --- | ---: | ---: |
| 无据陈述率 | **0.000** | **0.333** |
| 健康禁词泄漏数 | **0** | **1** |

> 为什么需要故障注入：`MockLLM` 输出固定文案，**永远不会**触发守卫。
> 用它跑 `no-guard` 会得到「两组完全一致」，从而得出
> 「守卫没有价值」这个**反向结论**。故障注入把守卫的作用变成可测的数字。

### 明确**测不了**的（不是「跳过」，是「没有数字」）

| 项 | 为什么 |
| --- | --- |
| 「未知问题明确表示不知道」 | 需真实 LLM；`MockLLM` 输出固定文案，测的是 mock 的措辞而非系统行为 |
| E23 置信度校准、E25–E29 视觉 | 需带标注的测试集与兽医评分 |

> 给一个用占位数据算出的数字，**比没有数字更糟**：它有数字的样子，会被引用。
> 详细边界见 [§7 本报告不能证明什么](reports/eval.md)。

## 0.5 群体先验：一个真实的负面结果

> 这一节是这份 README 里**信息量最大的部分** —— 它回答了一个
> 此前一直只能回答「还不知道」的问题。

`docs/DESIGN.md` §7.3 U3 一直写着「群体先验尚未构建」。
现在它构建了：`scripts/build_priors.py` 从 **CatMeows 原始音频**（440 条 / 21 只猫）
用**本项目自己的提取器**算出每个情境的特征分布，
并按 §6.1 的要求**按猫留出 4 只**不参与统计。

### 结果：留出猫上不如「总是猜多数类」

| | |
| --- | ---: |
| 留出 macro-F1 | **0.364** |
| 留出准确率 | 0.407 |
| 多数类基线 | **0.506** |
| 区分度余量 | **−0.142** |

每个可用特征的分离度（情境间均值差 / 标准差）全在 **0.32–0.72**，
分布大幅重叠：

| duration | rms_mean | roughness | f0_mean | f0_slope | f0_range |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.72 | 0.64 | 0.52 | 0.44 | 0.44 | 0.32 |

论文报 ~90% 准确率而这里不如基线。最可能的解释是
**论文按样本而非按猫划分** —— 同一只猫同时出现在训练与测试里，
那测的是「认不认得这只猫」，不是「能不能泛化到新猫」。
这正是 §6.1 要求留出猫的原因。

### 于是系统必须拒绝使用它

一份「已实测」但不具区分度的先验产出的后验概率**不是证据**，
而是一个看起来很确定的噪声。所以新增了一道**区分度门禁**：

| 情形 | 结论 |
| --- | --- |
| 占位数据 | 不可用 —— 数字是编的 |
| 未做过留出评估 | 不可用 —— **无法确认**有区分度 |
| 实测不如基线 | 不可用 —— 已确认**没有**区分度 |

> 第三条最关键：它把「已实测」从「可用」里拆了出来。
> 初版只检查 `is_placeholder` —— 那只区分「编的」与「真的」，
> 不检查「真的有没有用」。

检查放在 **`bayes.interpret`（数学层）自己**，而不只是路由层 ——
因为「先验能不能产出概率」是**不变量**，不是路由的偏好。
任何绕过路由的调用路径（新调用方、脚本、重构）都撞得上去，
与「存储层强制要求 tenant_id」同一个思路。

### 这对产品意味着什么

`acoustic_plus_history` 模式（用群体先验算后验概率）**在本数据集上不可用**。
可靠路径是个体化：`case_based`（主人自己的标注历史）与 `measured_only`
（只给测量值、不给概率）。

**这也是一个正面的验证**：系统的 fail-closed 设计真的拦住了它 ——
如果当初没有这道门，它会从一份不具区分度的先验里输出
「等吃的 62%」这类数字，而用户完全无法分辨那是噪声。

## 0.6 习惯：从主人的记录里数出稳定模式

> 这一层回答三个**可数**的问题：**发生过几次、在什么时候、有多规律**。
> 三个都能由代码从已存储的事件重算 —— 所以这是本项目里少有的、
> 可以声称绝对数值的能力。

### 为什么习惯可验证，而「猫的心思」不可验证

| | 习惯 | 猫的心思 |
| --- | --- | --- |
| 例子 | 「观察到 12 次、跨 9 天、早上占 83%」 | 「它想让你起床」 |
| 可否重算 | ✅ 从存储的事件数出来 | ❌ 没有 ground truth |
| 用户可否核对 | ✅ 每条习惯带 `evidence_ids` | ❌ 只能选择信或不信 |

这正是 D29 把知识对象定为「主人的经验」的落点 ——
而且习惯是那一侧少有的、**能给出数字**的部分。

### 三个刻意的设计选择

**1. 「还不够」是一个状态，不是一个低分**

观察 2 次说「弱习惯」暗示它**是**一个习惯。所以强度是三值枚举，
且 `INSUFFICIENT` 附带**缺什么**：

```
只在 1 天出现过，不足 3 天 —— 单日多次不算习惯，习惯的必要条件是跨天重复
```

**2. 「发生时间」与「记录时间」严格分开**

| 用途 | 用哪个 | 为什么 |
| --- | --- | --- |
| 天数 / 跨度 | `occurred_at`，缺失回退 `created_at` | 在 N 天各记过一次就是 N 天证据 |
| **时段分布** | **只用 `occurred_at`** | 记「晚上补记」当成「晚上发生」，会认认真真算出一个**错误的时段分布**，而报告里看不出异常 |

所以从对话写入的记录（没有 `occurred_at`）**不会**产生时段分布，
而报告会说明有多少条因此未参与 —— 见上面的实测输出。

**3. 因果问题显式拒绝**

「它**为什么**怕吸尘器」与「它怕吸尘器吗」只差一个字，
但前者要的是**原因**，而习惯数据里只有次数/天数/时段。系统会说：

```
习惯记录里没有原因。我能说的是观察到的情况：
它很怕吸尘器
      观察到 2 次 / 2 天 / 跨度 7 天
```

拿观察记录回答因果问题，是一个**看起来像答案的东西** ——
与 D42（模型不得推断因果）同源。

### 与真实输入路径接缝处修掉的两个缺陷

习惯层自己的测试可以直接造 `subject="wake_up"` 的事件，于是全部通过 ——
而**真实对话路径里 `subject` 是从内容猜的**。这两处都是这样发现的：

| 缺陷 | 后果 |
| --- | --- |
| `extract_candidates` 从不设置 `occurred_at` | 对话写入的记忆没有发生时间（这是**正确的** —— 系统确实不知道何时发生；所以时段统计会诚实地报告缺失，而不是拿记录时间充数） |
| `_guess_subject` 认不出时回退到**内容哈希** | 「六点叫我起床」与「六点准时叫我」→ 不同哈希 → **不归组** → 同一习惯说三次也累加不起来，而报告显示「记录还太少」——**指向错误的原因** |

第二条已修：扩充了惯例类主体词表，并在主体仍无法识别时**显式报告**
「有多少条记录的主体无法识别」（而不是假装分组成功了）。

### 接口

```bash
GET /v1/pets/{pet_id}/habits          # 结构化习惯（每个数字可复算）
GET /v1/pets/{pet_id}/habits?text=true # 附人类可读渲染
```

## 3. 环境

本项目在 **WSL2 (Ubuntu 22.04)** 下开发，代码位于 Windows 文件系统以便 IDE 直接打开。

| 项 | 位置 |
| --- | --- |
| 项目代码 | `E:\workspace\pet-agent` ↔ `/mnt/e/workspace/pet-agent` |
| 虚拟环境 | `/root/.venvs/pet-agent`（放 WSL 原生盘，避免 9p 文件系统拖慢安装） |
| 包源 | 清华镜像（venv 内 `pip.conf`） |

```bash
# 激活环境
source /root/.venvs/pet-agent/bin/activate

# 或直接调用
/root/.venvs/pet-agent/bin/python -m pytest
```

### 测试

契约层不变量测试，**不需要大模型、不需要网络**，1 秒内跑完：

```bash
/root/.venvs/pet-agent/bin/python -m pytest tests/ -q
```

这些测试验证的不是「功能是否正确」，而是**「设计约束是否被结构性强制」**——
例如防自我强化、计划拓扑合法性、先验依赖不可静默丢弃、无证据时禁止输出数值置信度。

### 启动

```bash
# 1. 必填：鉴权签名密钥（缺失会**拒绝启动** —— 否则 user_id 可伪造）
export PET_AGENT_AUTH_SECRET=dev-secret

# 2. 起服务（无供应商密钥时自动走 mock，/healthz 会明确标注）
python -m uvicorn app.bootstrap:create_app_from_env --factory --host 0.0.0.0 --port 8000

# 3. 签发一个开发用 token；核对实际装配到的厂商 / 模型 / 端点
python -m app.bootstrap --issue-token user-1
python -m app.bootstrap --describe
```

> `MOCK_PROVIDER=1` 会让**视觉显式失败**（`UnavailableVision`）—— 那是刻意的（D45）。
> 想离线跑通档案链路就**不要设它**：无密钥时会用确定性的 `MockVision`。

一次跑通全部端点（**真 uvicorn 进程 + 真 HTTP + 真实音频下载**）：

```bash
bash scripts/run_smoke.sh
```

> **已知环境问题**：WSL 的 Windows 互通（`binfmt_misc` 的 `WSLInterop`）在 WSL 启动早期未注册，
> 导致 `.exe` 调用间歇性报 `Exec format error`。需要通过 `cmd.exe` 调用 Windows 侧工具时，
> 先 `cat /proc/sys/fs/binfmt_misc/WSLInterop` 确认存在。

## 5. 前端

移动端优先的单页应用。设计方向是**田野笔记**，而不是通用宠物 App 的可爱风 ——
因为项目的核心主张是「知识对象是主人的经验」，而田野笔记正是「每条观察都带出处」
的东西。所以视觉语言直接编码了后端的证据分层：

| 层 | 含义 | 形态 |
| --- | --- | --- |
| `measured` | 代码从音频算出的数字，可重算 | 实线边框 |
| `observed` | 模型对画面的**描述**，未经校验 | 虚线边框 |
| `inferred` | 统计推断 | 点线边框 |
| 主人标注 | 用户自己填的 | 手写下划线 |

不看图例也能感到区别 —— 这是刻意的：用户正是靠这个分层判断「该信多少」。

### 开发

```bash
cd web && npm install
npm run dev          # 5173，自动把 /v1 代理到 127.0.0.1:8000
```

需要后端在 8000 跑着，并临时开开发登录：

```bash
PET_AGENT_ALLOW_DEV_LOGIN=1 \
  python -m uvicorn app.bootstrap:create_app_from_env --factory --port 8000
```

### 验证

```bash
npm run typecheck    # tsc
npm run build
npm run smoke        # jsdom 挂载：证明能起来
npm run e2e          # 22 项断言：登录 / 五页 / 切换宠物 / 真实对话
```

> 这两个脚本用 jsdom 而不是 Playwright —— 无浏览器可用时它们仍然能跑，
> 而且能进入 CI。它们抓出过一个真缺陷：健康分级映射用了自造名
> （`monitor`/`urgent`），后端实为 `L1`/`L2`/`L3`，
> 于是五个分支全部落空、页面永远显示「没有拿到评估结果」，
> 而 `tsc` 与 `build` 都是绿的。
