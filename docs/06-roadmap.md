# 06 · 含金量提升路线

> 本文档回答一个问题：**怎么让这个项目更有含金量？需要加功能吗？**
>
> 结论先行：**不需要加功能，需要把已有设计变成可证明的结论。**

## 0. 核心判断

### 0.1 含金量 ≠ 功能数量

当前功能清单：

```
身份锚定 · 陪伴对话 · 行为解释 · 健康分诊
三层记忆 · 数据飞轮 · 多租户隔离
ASR · TTS · 评测集 · Web UI
```

**这已经超出一个人能做好做透的范围。** 继续加功能的边际收益是负的——
面试官不会因为你多了一个模块而加分，但会因为每个模块都是半成品而减分。

### 0.2 真正的漏洞

| 现状 | 面试官的问题 | 现在的回答 | 应有的回答 |
|---|---|---|---|
| 只有设计，没有结果 | 「效果怎么样？」 | 「设计上应该不错」 | 「recall@5 从 0.62 提到 0.81，误答率 0」 |
| 有评测集设计，没跑过 | 「你怎么知道有效？」 | 「我设计了六类评测」 | 「跑批结果在这里，这是基线和消融对比」 |
| 参数是拍脑袋的 | 「κ=5 怎么来的？」 | 「经验值」 | 「敏感性分析在 §X，κ 在 3–10 之间稳定」 |
| 依赖外部 API | 「断网能演示吗？」 | 「不能」 | 「有 mock provider，离线可跑全部评测」 |

**一句话**：这个项目现在是**一份很好的设计文档**，
但还不是**一个能证明自己有效的系统**。差距全在「可证明性」上。

---

## 1. 三条提升路径（按 ROI 排序）

```
Path 1  让主张可证明        ← ROI 最高，成本最低
Path 2  让深度可见
Path 3  补设计里的真实漏洞
Path 4  如果非要加功能（只加一个）
```

---

## 2. Path 1：让主张可证明（P0）

### 2.1 评测跑批 + **基线对比**

**这是整份路线里最重要的一件事。**

关键不在于跑分，在于**必须有基线**。没有基线的数字没有意义：

| 主张 | 基线 | 实验组 | 指标 |
|---|---|---|---|
| 混合检索比朴素向量好 | naive top-k | + 结构化预过滤 + 重排序 | `recall@5`、`MRR` |
| 记忆系统有用 | 无记忆（只有当前轮） | 三层记忆 | 记忆类问题准确率、**无据陈述率** |
| 守卫有效 | 无守卫 | + `response_guard` | 越界率、过度确定性率 |
| 声学证据比纯文本强 | text_only 推断 | 声学 + 个体历史 + 先验 | 情境分类准确率（macro-F1） |
| 防自我强化是必要的 | 允许 `SYSTEM_INFERENCE` 为 ACTIVE | 当前规则 | 长对话后幻觉率增长曲线 |

**最后一条特别有说服力**：故意跑一个"被污染的"配置，展示错误如何随轮次放大。
**用一个实验证明某个约束是必要的**，这比说「我做了防护」强得多。

**对照组怎么做**：用配置开关（`ABLATION_NO_GUARD=1`），同一套代码跑不同配置，
而不是维护两份代码。这样消融是**可复现的**。

### 2.2 不变量断言进 CI

把设计里的硬约束变成可执行断言：

```python
def test_no_active_system_inference(db):
    """防自我强化（docs/04 §3.5 R1）"""
    n = db.count(MemoryEvent, source=SYSTEM_INFERENCE, status=ACTIVE)
    assert n == 0, f"发现 {n} 条系统推断被当作事实存储"

def test_no_cross_pet_leakage(store, two_pets):
    for item in store.search_all(pet_id=two_pets.a.id):
        assert item.event.pet_id == two_pets.a.id

def test_health_never_says_healthy(assessments):
    for a in assessments:
        assert not any(p in a.recommendation for p in FORBIDDEN_PHRASES)

def test_insufficient_coverage_forbids_findings(assessments):
    for a in assessments:
        if a.coverage < MIN_COVERAGE_FOR_ASSESSMENT:
            assert a.level is UrgencyLevel.INSUFFICIENT_DATA
            assert not a.findings
```

这些测试**不需要大模型**，跑得快，可以直接挂在 CI 上。

**面试价值**：面试官看到 `test_no_active_system_inference` 这个函数名，
立刻知道你是真的把安全约束当工程问题在做，而不是写了一段免责声明。

### 2.3 真实成本数据

| 指标 | 怎么测 | 为什么要 |
|---|---|---|
| 每节点 token 消耗 | `node_trace` 累计 | 讲成本优化有依据 |
| p50 / p95 延迟 | 每节点打点 | 「哪个节点是瓶颈」 |
| 单次对话成本 | token × 单价 | 面试官很吃这个 |
| TTS / 记忆写入的异步收益 | 同步 vs 异步对比 | 证明架构决策有效 |

**面试表述**：

> 「单次对话平均 3.2K token，p95 延迟 4.1 秒，其中行为解释节点占了 2.3 秒。
> 我把 TTS 和记忆写入改成异步后，p95 降到 2.8 秒。」

有数字的架构讨论和没有数字的架构讨论，是两个层次。

### 2.4 一键可复现

```bash
make demo        # 起服务 + 灌样例数据 + 打开 Web UI
make eval        # 跑全部评测，输出报告
make ablation    # 跑消融对比，输出表格
```

要求：

- 固定随机种子
- 先验文件带 `sha256` 与版本号（`docs/03` §11 已要求）
- **mock provider**：无 API Key / 无网络时也能跑通全部评测
- `docker compose up` 一条命令起完整环境

> 面试时能现场 `make eval` 跑出结果，比放一张 PPT 里的表格可信得多。

**README 最终应该长这样**：

```markdown
## 评测结果

| 实验 | recall@5 | MRR | 无据陈述率 | p95 延迟 |
|---|---|---|---|---|
| 基线（naive top-k） | 0.62 | 0.54 | 0.18 | 3.9s |
| + 结构化预过滤 | 0.74 | 0.66 | 0.11 | 3.8s |
| + 重排序（本条） | 0.81 | 0.79 | 0.04 | 4.1s |

## 消融
| 配置 | 10 轮后幻觉率 |
|---|---|
| 允许 SYSTEM_INFERENCE 为 ACTIVE | 0.31 |
| 当前规则（本条） | 0.02 |
```

**这张表就是含金量。**

## 3. Path 2：让深度可见（P1）

### 3.1 消融实验

**这是论文级方法论，面试里几乎没人做。**

| 消融对象 | 观察什么 |
|---|---|
| 去掉 `response_guard` | 过度确定性表述率、越界率 |
| 去掉拒答策略（`retrieval_note`） | 幻觉率 |
| 去掉冲突消解（改为覆盖） | 「以前喜欢什么」类问题准确率 |
| 去掉强化机制（改为重复插入） | 检索结果重复率、上下文有效信息密度 |
| 去掉时间范围判定 | 误判「演变」为「矛盾」的比率 |
| 去掉个体化收缩（λ 固定为 0） | 声学分类准确率随样本数的变化 |

**「去掉 X 会怎样」是证明 X 有价值的最强方式。**

### 3.2 失败案例集

主动整理**自己的系统在什么情况下会失败**，比吹嘘成功有说服力得多。

格式：

| 案例 | 输入 | 期望 | 实际 | 根因 | 状态 |
|---|---|---|---|---|---|
| F1 | 两猫名字相近 | 不混淆 | 偶发混淆 | 向量检索未强制 pet 过滤（已修） | ✅ 已修 |
| F2 | 叫声含背景电视声 | 降低置信度 | 仍给 0.7 | 未做 SNR 门限 | ⬜ 待修 |
| F3 | 「它上个月…」 | 不判冲突 | 判为冲突 | valid_from 未解析 | ✅ 已修 |

**面试表述**：

> 「我整理了一份失败案例集，目前 12 个案例，已修 8 个。
> 其中最有意思的是 F3：用户说『它上个月喜欢逗猫棒』，
> 系统因为没解析出时间范围，把它当成了和新偏好的冲突。
> 这让我意识到冲突检测里**时间范围是必需条件，不是可选优化**。」

### 3.3 参数敏感性

设计里有几处「经验值」，需要证明它们不敏感：

| 参数 | 位置 | 现状 | 要做的 |
|---|---|---|---|
| `κ`（收缩常数）= 5 | `docs/03` §3.4 | 「经验值」 | 扫 κ ∈ {1,3,5,10,20}，看后验变化 |
| `DEDUP_TAU` = 0.92 | `docs/04` §3.2 | 拍板 | 扫 0.85–0.97，看误合并/漏合并 |
| 覆盖率门限 = 0.3 | `docs/07` §6 | 拍板 | 论证或标注为待验证 |
| 置信度分档 0.65 / 0.45 | `docs/03` §7 | 拍板 | 同上 |
| `robust_z` 阈值 = 3 | `docs/07` §5.3 | 拍板 | 同上 |

**如果没时间做全部，至少做 `κ` 和 `DEDUP_TAU`**——它们直接影响核心输出的质量。

**诚实的替代方案**：如果确实没调，就在文档里明确写
`⚠️ 未经验证的超参数，待实验确定`。**标注不确定性比假装有依据强。**

## 4. Path 3：补设计里的真实漏洞（P1）

这份自我批判是刻意写的——**主动交出弱点，比被问出来强**。

| # | 漏洞 | 严重度 | 解法 |
|---|---|---|---|
| G1 | **评测集的效度没人论证**——自己造的评测集，凭什么说它对？ | 高 | 见 §4.1 |
| G2 | `κ=5` 等超参无依据 | 中 | 见 §3.3 |
| G3 | 高斯 + 对角协方差假设未验证 | 中 | 在实验里报告残差；或改用非参数似然 |
| G4 | 依赖外部 API，无离线路径 | 高 | mock provider（§2.4） |
| G5 | 无并发/压测 | 低 | 无状态设计可兜；如实说明 |
| G6 | ASR 降权系数 0.85 无依据 | 低 | 标注为待验证 |

### 4.1 G1：评测集效度——这是最容易被打穿的点

**问题**：评测集是我造的，标准是我定的，那我测的到底是什么？

**解法：把评测项按「可客观判定」分层，只对能客观判定的部分声称可靠性。**

| 层 | 评测项 | 判定方式 | 可否声称可靠性 |
|---|---|---|---|
| **A. 客观可判定** | 幻觉（档案没有却说有） | 确定性：比对数据库 | ✅ 可声称 |
| | 租户隔离（交叉污染） | 确定性：比对 `pet_id` | ✅ |
| | 去重强化（条数/support） | 确定性：计数 | ✅ |
| | 冲突判定（时间重叠） | 确定性：逻辑 | ✅ |
| | 不变量（`system_inference AND ACTIVE`） | 确定性：计数 | ✅ |
| | 覆盖率门禁 | 确定性：结构校验 | ✅ |
| **B. 有参考标准** | 声学情境分类 | CatMeows 有上下文标签 | ◐ 可声称，但需说明先验与测试集同源的风险 |
| **C. 需主观判断** | 角色一致性 | LLM-as-judge | ⚠️ 需报告一致性 |
| | 措辞自然度 | LLM-as-judge | ⚠️ 同上 |
| | 「建议观察项」是否有用 | 人工 | ⚠️ 同上 |

**关键原则**：

1. **A 层是主力**。它们不依赖模型、可复现、跑得快，且直接对应项目的核心主张
2. **C 层不要声称绝对值**。只报告**相对比较**（配置 A vs B 谁更好），
   并给出标注一致性（多人标注的 Cohen's κ，或 LLM-as-judge 与人工的一致率）
3. **B 层要主动说明污染风险**：如果先验来自 CatMeows，
   而测试集也来自 CatMeows，那测的是**拟合先验的能力**，不是泛化能力。
   诚实的做法是：留出 hold-out 猫（21 只猫里留 4 只不参与先验统计）

**第 3 条尤其重要**——它是我在设计 `docs/03` 时就留下的隐患（L1 局限），
必须在评测设计里显式处理，否则会被追问。

## 5. Path 4：如果非要加功能

**只加能带来新维度的，不加同维度的。**

| 候选功能 | 新维度 | 成本 | 评价 |
|---|---|---|---|
| **时间线聚合问答** | **聚合查询 vs 相似度检索** | 低 | ✅ **唯一推荐** |
| 主动提醒（「明天该打疫苗了」） | 主动发起 vs 被动响应 | 中 | ◐ 可考虑 |
| 多宠物关系推理 | 跨实体时间线推理 | 高 | △ 场景偏窄 |
| 家庭成员共享一只猫 | 记忆来源冲突、权限模型 | 高 | ✗ ROI 低 |
| 更多宠物种类（狗） | 无 | 高 | ✗ 纯稀释 |
| 图像生成（生成该猫的图） | 无（是另一个产品） | 中 | ✗ 偏离主线 |

### 5.1 为什么只有「时间线聚合问答」值得加

因为它暴露了**纯向量 RAG 的根本局限**：

```
用户问：「团团这个月比上个月爱叫吗？」

向量检索：找一个"和这句话最相似的记忆"
  → 返回"最近晚上经常在门口叫"（相似度高）
  → ❌ 但这句话回答不了"比上个月多还是少"
```

**「比…多」是聚合，不是相似度。** 要答它必须：

```
自然语言 → 结构化查询（text-to-SQL / Query DSL）
         → 按月分组计数 → 比较 → 再措辞化
```

这带来三个新技术点：

1. **查询意图判别**：什么时候该走检索，什么时候该走聚合
   → 直接扩展 `understand_input`，是路由能力的新分支
2. **Text-to-SQL / 结构化查询生成**：需要 schema 注入 + 结果校验 + 失败重试
3. **检索与聚合的混合结果融合**：一次回答可能既需要事实（"它怕吸尘器"）又需要统计

**而且它天然服务于宠物场景**——主人真的会问「它最近是不是叫得比以前多」。
这不是为了炫技硬加的功能。

**面试表述**：

> 「我加这个功能不是为了堆特性，是因为它暴露了纯向量 RAG 的一个根本局限：
> 『比上个月多吗』是聚合问题，不是相似度问题。
> 所以我加了查询意图判别——先决定走检索还是走聚合——
> 聚合路径用 text-to-SQL 生成结构化查询，并对生成结果做 schema 校验和结果合理性检查。」

## 6. 范围收敛建议（重要）

**要有始有终，不要样样半成品。** 建议主动砍掉或简化：

| 项 | 建议 | 理由 |
|---|---|---|
| TTS 角色化语音 | **砍掉或极简化** | 对技术深度贡献低，成本不低。演示时放一段预生成音频即可 |
| 完整用户鉴权体系 | **只做数据层隔离** | `pet_id`/`user_id` 隔离是正确性问题必须做；JWT/OAuth 是 CRUD，没有展示价值 |
| Web UI | **够演示即可** | 一个单页 + 5 个按钮足够。堆前端不体现 AI 工程能力 |
| Track B 健康漂移 | **已决定延后** | 需要 21 天基线，demo 跑不出来 |
| 微信小程序 | **砍掉** | 审核与调试成本高，收益是「演示好看一点」 |

**把省下的时间投到 §2 和 §3。**

## 7. 优先级路线

| 优先级 | 事项 | 预计产出 | 面试价值 |
|---|---|---|---|
| **P0** | 评测跑批 + 基线对比 | README 里的效果表 | ★★★★★ |
| **P0** | 不变量断言 + CI | `tests/test_invariants.py` | ★★★★★ |
| **P0** | mock provider（离线可跑） | 断网也能演示 | ★★★★ |
| **P1** | 成本/延迟数据 | p95、token、单次成本 | ★★★★ |
| **P1** | 消融实验 | 消融表 | ★★★★★ |
| **P1** | 失败案例集 | 12 个案例 + 根因 | ★★★★ |
| **P1** | 参数敏感性（κ、DEDUP_TAU） | 敏感性曲线 | ★★★ |
| **P2** | 评测集效度分层（§4.1） | 评测设计说明 | ★★★★ |
| **P2** | 时间线聚合问答 | 新增检索范式 | ★★★ |
| **P3** | 主动提醒 | 新的 agent 范式 | ★★ |

### 建议的执行顺序

```
1. 补齐契约层 + tests/            （修掉当前的 import 失败）
2. mock provider + 一键可复现      （让一切可跑）
3. 评测跑批 + 基线对比             （产生第一个数字）
4. 不变量断言进 CI                 （把安全约束工程化）
5. 消融实验 + 失败案例集           （证明设计决策有价值）
6. 参数敏感性                      （把"经验值"变成"验证过的值"）
7. README 写结果表                 （把成果外化）
8. （可选）时间线聚合问答
```

**第 1–4 步做完，这个项目的含金量就已经超过了绝大多数作品集项目**——
因为它不再只是「我设计了」，而是「我设计了、我实现了、我测过、并且我知道它在哪里会失败」。

---

## 8. 一句话总结

> **含金量不来自你做了多少功能，
> 来自你能证明多少主张，以及你对自身局限的理解有多清楚。**

当前项目在「设计」这一维度上已经足够，
缺的是「可复现的实现」+「有基线的评测」+「诚实的失败分析」。

这三件事做完，不需要再加任何功能。
