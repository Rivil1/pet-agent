# 07 · 健康异常监测与分诊

> **本文档定义的模块不做诊断。** 定位是「健康数据记录 → 异常检测 → 分诊建议」。
> 这是本项目风险最高的模块，也是最能体现 AI 安全设计能力的模块。

## 1. 定位：监测与分诊，不是诊断

| 做 | 不做 |
|---|---|
| 记录用户报告的健康相关观察 | 给出疾病诊断结论 |
| 与个体基线比对，检测偏离 | 给出疾病名称 |
| 按紧急度分诊，建议就医 | 建议用药、剂量 |
| 输出可带给兽医的结构化记录 | 出具诊断书 / 证明文件 |
| 明确告知「无法评估」 | 输出「健康」「没问题」 |

### 合规依据

《动物诊疗机构管理办法》（农业农村部，2022-10-01 施行）：

- **第二条**：动物诊疗指动物疾病的预防、**诊断**、治疗和绝育手术等**经营性活动**，
  包括健康检查、采样、配药、给药、手术、**填写诊断书**和出具动物诊疗有关证明文件等。
- **第五条**：国家实行动物诊疗**许可制度**。
- **第十九条**：**执业兽医师**方可从事疾病预防、**诊断**、治疗、开具处方、**填写诊断书**。

**设计推论**：诊断与出具证明属许可活动；健康数据记录、异常检测、
就医建议不属于诊疗活动。因此本模块的输出必须严格限定在后者。

> 面试价值：主动说出这条边界，比说「我做了宠物健康 AI」可信得多。
> 它证明你知道自己在什么监管框架下做事。

## 2. 三不原则

这三条是硬约束，由 `health_guard` 强制执行，不是 prompt 建议。

### 2.1 不诊断

不输出疾病名称作为结论。极少数红旗情境下可以提及「典型表现」，
但措辞必须是 `这可能是 X 的典型表现，需由兽医确认`，而非 `它得了 X`。

### 2.2 不排除

**永不输出「健康」「没问题」「正常」「放心」。**

这是健康类 AI 最致命的错误：**absence of evidence is not evidence of absence**。
「没检测到异常」和「没有异常」是两件完全不同的事。

强制措辞：`本期记录中未发现明显偏离（这不等于健康）`。

### 2.3 不阻塞

红旗命中（L3）时，健康提示必须**抢占**其他输出。
即使用户在闲聊，紧急提示也必须出现在响应最前面，且不可被静默丢弃。

## 3. 双轨检测

两条轨道**必须并存**，因为它们的失效模式互补。

```
                     ┌──────────────────────┐
   用户记录 + 叫声    │  健康信号采集层       │
   特征 + 互动模式    └──────────┬───────────┘
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
   ┌──────────────────────┐          ┌──────────────────────┐
   │ Track A: 红旗规则     │          │ Track B: 基线漂移     │
   │ 确定性 · 硬编码 · 不学习│          │ 统计 · 个体化 · 学习   │
   │ 命中 → L3 立即就医    │          │ 偏离 → L1/L2         │
   └──────────────────────┘          └──────────────────────┘
              │                                   │
              └─────────────────┬─────────────────┘
                                ▼
                     ┌──────────────────────┐
                     │  分级 + 抢占 + 免责    │
                     └──────────────────────┘
```

**为什么要两条轨道？**

| | Track A 红旗 | Track B 漂移 |
|---|---|---|
| 目标 | 已知的**急性**危险 | 未知的**渐进**变化 |
| 方法 | 确定性规则 | 统计检测 |
| 可否学习 | **绝对不可**。学习可能让罕见红旗被优化掉 | 必须学习，基线是个体化的 |
| 失效模式 | 规则表不全会漏 | 数据不足时无法判断 |
| 代价 | 假阴性 = 猫可能死亡 | 假阳性 = 多跑一趟医院 |

假阴性代价远大于假阳性 → **红旗规则必须偏向过度触发**（优化 recall，牺牲 precision）。

## 4. Track A：红旗规则表

### 4.1 设计原则：规则是**数据**，不是代码

红旗规则存放在 `data/health/red_flags.yaml`，带版本号、来源引用与审核状态：

```yaml
version: "2026.09.1"
reviewed_by: null          # 待执业兽医审核
reviewed_at: null
rules:
  - id: urinary_obstruction
    urgency: L3
    species: cat
    title: 排尿困难（公猫尿闭风险）
    conditions:
      all_of:
        - signal: litter_box.visit_frequency
          op: ">="
          value: 5
          window: 2h
        - signal: litter_box.urine_output
          in: [none, few_drops]
    aggravating:
      - signal: vocalization.context
        equals: voiding_attempt
      - sex: male
    message: >
      频繁进出猫砂盆但几乎排不出尿，是尿道阻塞的典型表现。
      这属于急症，完全阻塞后 24-48 小时内可能危及生命，
      请立即就医，不要在家观察。
    never_say_healthy: true
    sources:
      - https://www.msdvetmanual.com/urinary-system/urolithiasis-in-small-animals/urethral-obstruction-in-small-animals
      - https://www.acvs.org/small-animal/urinary-obstruction-in-male-cats/
      - https://www.petmd.com/cat/conditions/urinary/urinary-tract-blockage-cats
```

**为什么做成数据文件**：让执业兽医可以审核与维护，
而不需要改代码。`reviewed_by: null` 明确标记「尚未经兽医审核」——
**未审核的规则不得上线**，这是流程约束。

### 4.2 已核实的红旗（需兽医审核后启用）

| ID | 情境 | 关键判据 | 依据强度 |
|---|---|---|---|
| `urinary_obstruction` | 排尿困难 / 尿闭 | 频繁进砂盆、蹲久、无尿或几滴、排尿时嚎叫；**公猫高发** | 强（多份兽医手册一致） |
| `respiratory_distress` | 呼吸异常 | 张口呼吸、呼吸急促、喘鸣 | 强 |
| `neurological` | 神经症状 | 抽搐、意识不清、突然瘫痪 | 强 |
| `hemorrhage_toxin` | 出血 / 中毒 | 出血不止、疑似误食毒物 | 强 |
| `persistent_vomiting` | 持续呕吐/腹泻 + 虚弱 | 持续且伴精神萎靡 | 中 |
| `anorexia` | 持续不进食 | 阈值**待兽医确认**（不同来源指引不一） | 中，阈值需审核 |
| `mucosa_change` | 黏膜苍白 / 黄染 | 牙龈颜色异常 | 中 |

> ⚠️ **重要**：`anorexia` 等阈值型规则的具体数值在不同兽医来源中不一致。
> 本表不自行断言阈值，一律标记为「待兽医审核」，审核前该规则处于 `disabled` 状态。
> 这是刻意的设计——**不确定的阈值宁可不用，也不能瞎给**。

### 4.3 已知的高价值场景

尿闭这个场景值得单独说明，因为它是**人机能力差异最大的点**：

MSD 兽医手册指出，主人**常把尿闭的迹象误认为便秘**。
而系统同时持有：叫声特征、砂盆行为记录、时间序列、性别。
这正好覆盖了人类失败的原因（单次观察、缺乏对照、误判归因）。

> 面试话术：这个模块的价值不在于我比兽医强，而在于我**记得住这只猫 30 天的基线**，
> 而主人记不住。系统的优势是纵向记忆，不是医学知识。

## 5. Track B：基线漂移检测

### 5.1 健康信号

系统**没有传感器**（无砂盆称重、无活动追踪、无进食量测量）。
信号全部来自用户报告 + 声学流水线：

| 信号 | 来源 | 说明 |
|---|---|---|
| 叫声特征偏移 | **复用行为解释器的声学流水线** | 疼痛状态常伴随叫声特征变化 |
| 夜间叫声频率 | 声学 + 时间戳 | 猫夜间异常嚎叫是常见就诊主诉 |
| 排尿/排便记录 | 用户记录 | 频次与性状 |
| 进食/饮水记录 | 用户记录 | 量或「吃了/没吃」的定性记录 |
| 互动频率 | 会话时间戳 | 活动量的弱代理指标 |
| 体重 | 用户记录 | 若有记录则是最强信号之一 |

**架构红利**：声学基线一套采集、两个消费方（行为解释 + 健康监测）。
不需要为健康模块单独搭一条音频链路。

### 5.2 检测方法：稳健统计

对每个信号维护个体基线的**滚动窗口**（默认 21 天），用稳健 z 分数：

```
robust_z = 0.6745 · (x − median) / MAD
```

**为什么用 MAD 而不是标准差**：一次就诊、一次出差、一次访客都会产生极端值，
标准差会被这些离群点撑大，导致真实偏离被掩盖。MAD 对离群点稳健。

**渐进漂移**用 EWMA / CUSUM 累积偏离量，避免单点噪声触发告警：

```
CUSUM⁺ₜ = max(0, CUSUM⁺ₜ₋₁ + (xₜ − μ − k))
```

超过决策阈值 `h` 才升级。

### 5.3 触发条件

| 级别 | 触发条件 |
|---|---|
| L1 观察 | 单次 `|robust_z| ≥ 3`，或单个信号轻微偏离 |
| L2 建议就医 | 连续 ≥ 3 天偏离，或 ≥ 2 个信号同时偏离，或 CUSUM 超阈值 |
| L3 立即就医 | Track A 红旗命中 |

## 6. 数据覆盖率与「无法评估」

这是诚实性要求，也是防幻觉的关键机制。

系统在给出**任何**评估前，必须先算覆盖率：

```
coverage = 有有效记录的信号数 / 需评估的信号数
```

| coverage | 系统行为 |
|---|---|
| < 0.3 | **只输出「数据不足，无法评估」**，并引导用户补充记录。禁止输出任何趋势判断 |
| 0.3 – 0.6 | 可输出 L1 观察，必须标注覆盖率与限制 |
| ≥ 0.6 | 正常分级 |

**硬规则**：覆盖率不足时输出「未发现异常」是**禁止的**——
那会把「我没数据」伪装成「它很健康」，是本模块最危险的失败模式。

## 7. 分级输出契约

```jsonc
{
  "assessment_id": "...",
  "pet_id": "...",
  "as_of": "2026-09-12T10:30:00Z",
  "level": "L2",
  "coverage": 0.71,
  "coverage_note": "本周有效记录 5/7 天",
  "signals_assessed": ["meal", "litter_box", "vocalization"],
  "signals_missing": ["weight", "water"],
  "findings": [
    {
      "signal": "litter_box.visit_frequency",
      "direction": "increase",
      "magnitude": 2.4,               // robust z
      "duration_days": 4,
      "baseline_window": "2026-08-22/2026-09-11",
      "note": "近 4 天砂盆访问次数持续高于它的基线（中位数 3 次/日 → 7 次/日）"
    }
  ],
  "red_flags_triggered": [],
  "recommendation": "建议预约兽医，并带上这份记录",
  "disclaimer": "本结果为基于行为记录的偏离提示，不是诊断，不能替代兽医检查。",
  "must_not_be_read_as": "未发现异常不代表健康"
}
```

### 字段约束

| 字段 | 约束 |
|---|---|
| `level` | 只能由规则表 + 统计检测决定，**LLM 不得修改** |
| `red_flags_triggered` | 只能来自 `red_flags.yaml` |
| `disclaimer` | **必填**，不可省略、不可被 LLM 改写 |
| `coverage < 0.3` 时 | `level` 必须为 `INSUFFICIENT_DATA`，`findings` 必须为空 |
| 任何情况下 | 禁止在输出中出现「健康」「正常」「放心」等表述 |

## 8. 明确禁止清单

由 `health_guard` 节点以正则 + 规则双重检查：

| # | 禁止行为 | 检查方式 |
|---|---|---|
| 1 | 输出疾病名称作为结论 | 疾病名词表匹配 + 上下文判定 |
| 2 | 出现「健康」「没问题」「正常」「放心」 | 关键词匹配 |
| 3 | 建议用药、剂量、人用药 | 药物名词表 |
| 4 | 覆盖率不足时输出「未发现异常」 | 逻辑校验 |
| 5 | 省略 `disclaimer` | 结构校验 |
| 6 | 给出生存期/预后判断 | 关键词 + LLM 复核 |
| 7 | 用「它得了 X」句式 | 句式匹配 |
| 8 | 修饰 L3 紧急度（弱化、延迟建议） | 级别一致性校验 |

第 8 条特别重要：**L3 不能被 LLM 在措辞时软化**。
用户问「它要不要紧」，回复不能变成「应该没事」。级别是数据，措辞必须服从级别。

## 9. 非对称代价

这是本模块的核心设计原则：

| 错误类型 | 场景 | 代价 |
|---|---|---|
| **假阴性** | 该报警没报 | 猫可能死亡 —— **不可接受** |
| **假阳性** | 不该报警报 | 多跑一趟医院 —— **可接受** |

**因此**：

- Track A 阈值偏向**过度触发**（优化 recall，放弃 precision）
- 宁可用户被提示「建议就医」十次里有九次是虚惊
- 绝不因为「避免误报」而抬高红旗阈值

这与通用 AI 产品的优化目标（提升体验、减少打扰）**方向相反**。
安全关键型产品的目标函数不一样，这一点必须显式写出来。

## 10. 与既有模块的复用

| 复用对象 | 复用方式 |
|---|---|
| 声学流水线 | 行为解释器提取的特征直接进健康信号层 |
| 记忆系统 | 用户记录的健康观察走同一套 `MemoryEvent`，`event_type = health` |
| 基线思想 | 与行为解释器的分层贝叶斯收缩同源：个体基线 vs 群体基线 |
| 守卫节点 | `health_guard` 与 `response_guard` 并列，检查项独立 |
| 可观测性 | 健康评估结果落库，保留 `rule_version` 以便事后审计 |

## 11. 面试价值

这个模块是「如何处理 high-stakes AI」的标准答案，可以讲五个层次：

1. **确定性 vs 统计的分工**：已知急性危险用硬规则（永不学习），
   未知渐进变化用统计（必须学习）。学习型系统会优化掉罕见的高代价事件。
2. **不对称代价**：安全关键场景下目标函数与通用产品相反。
3. **显式的「无法评估」状态**：拒绝在数据不足时给结论，
   而不是把「没数据」包装成「没问题」。
4. **合规边界意识**：知道诊断是许可行为，主动把产品口径收窄。
5. **规则即数据**：红旗表是可版本化、可由领域专家审核的配置，
   而不是埋在代码里的 magic number。

## 12. 本期范围与已决事项

### 12.1 范围决策

**本期只实现 Track A + 健康数据模型**，Track B 仅保留接口与设计。

理由：Track B 的基线漂移检测需要约 **21 天的个体历史数据**，而演示场景无法自然积累。
强行实现的结果是「代码写了、但演示只能用合成数据跑」，性价比低。

|---|---|---|
| Track A 红旗规则引擎 | ✅ 实现 | 救命能力，且为规则匹配，成本低 |
