# 13 · 多模态观测：用照片视频做可验证的评估

> 提案：**既然无法观察就只能编造，那就用多模态把「能观察的」扩大。**
>
> 本文档评估这个方向。**结论：方向正确，且明显优于拟人化——
> 但理由与直觉不同：它的价值不是「让猫说话」，而是「缩小知识缺口」。**

## 1. 核心判断

### 1.1 它不解决拟人化问题，它扩展**事实层**

`docs/12` 的批判结论是：拟人化不能表达需求与生理状态，因为**有真实答案但我们不知道**。

多模态观测做的事是：**把「不知道」的范围缩小**。

```
                        可测量区（事实层可说）
┌────────────────────────────────────────────────────┐
│ 无多模态：  外貌 / 品种                             │
│ 加多模态：  + 体况 / 面部疼痛信号 / 姿态 / 呼吸频率  │
└────────────────────────────────────────────────────┘
                        │
                        │  ← 这个边界在移动
                        ▼
┌────────────────────────────────────────────────────┐
│ 仍不可知：  内脏疾病 / 精确需求 / 主观体验           │
│            → 仍然禁止编造                            │
└────────────────────────────────────────────────────┘
```

**关键推论**：

| 输出 | 多模态之后 | 归属 |
|---|---|---|
| 「照片里它的耳朵后压、眼睑半闭，FGS 评分 4/10」 | ✅ **可以说了** | `fact_layer`（有依据） |
| 「本喵肚子疼」 | ❌ **仍然禁止** | `companion_layer`（虚构台词） |

> **它扩大的是事实层的表达能力，不是扮演层的编造空间。**
> 这两件事必须分清，否则会有人拿「我们有多模态」当成「所以可以随便编」的借口。

### 1.2 为什么这比拟人化正确

| | 拟人化语言 | 多模态观测 |
|---|---|---|
| 面对知识缺口 | **用虚构填补** | **缩小缺口** |
| 用户能否追问依据 | 不能 | 能（分项分数 + 拍摄质量） |
| 错误可被发现吗 | 几乎不能 | 能（与兽医评分比对） |
| 产品护城河 | 低（一个 prompt 就能抄） | 中高（需要数据与验证） |

## 2. 三个有科学依据的可测量项

这三个都是**已发表的、被兽医界使用的工具**，不是我们发明的。

### 2.1 Feline Grimace Scale（FGS）· 面部疼痛评估

| 项 | 内容 |
|---|---|
| 来源 | Evangelista MC et al., *Scientific Reports* 2019, [doi:10.1038/s41598-019-55693-8](https://doi.org/10.1038/s41598-019-55693-8) |
| 性质 | **验证过的**猫急性疼痛评估量表 |
| 验证方式 | 35 只临床上处于疼痛状态的客户猫 + 20 只对照猫，笼内无干扰录像；疼痛组给予镇痛后重复录像 |
| 5 个动作单元 | **耳朵位置 / 眶周收紧 / 口吻部紧张 / 胡须位置 / 头部位置** |
| 计分 | 每项 0–2（0=无，1=中度或不确定，2=明显），另有「无法评分」选项 |
| 已知难点 | 文献明确指出：**即使对专家，猫也是疼痛评估上出了名困难的物种** |

**且有自动化研究**：

| 研究 | 内容 |
|---|---|
| [手机端全自动深度学习模型](https://pmc.ncbi.nlm.nih.gov/articles/PMC10703818/) | 3447 张猫脸图像、标注 37 个 landmark，训练 CNN + XGBoost，明确面向**智能手机场景** |
| [视频自动化疼痛识别](https://pmc.ncbi.nlm.nih.gov/articles/PMC11564822/) | 基于面部 landmark 的视频识别 |
| [可解释的自动化疼痛识别](https://pmc.ncbi.nlm.nih.gov/articles/PMC10238514/) | 强调可解释性——与我们的「证据可追溯」原则一致 |

> **这是本方向最强的支撑**：不仅有验证过的量表，还有已发表的自动化实现路径，
> 且「专家也困难」这一事实本身就论证了辅助工具的价值。

### 2.2 Sleeping Respiratory Rate（SRR）· 静息呼吸频率

| 项 | 内容 |
|---|---|
| 地位 | **兽医明确让主人在家测的项目**，用于监测心衰（CHF）发展 |
| 临床背景 | HCM 是最常见猫心脏病，约 **1/7** 猫受影响，是 9 岁以上成年猫主要死因；早期常无症状 |
| 为什么在家测 | **到院应激会加重病情**，远程监测优于门诊复查 |
| 测法 | 猫**睡着或静息**时，数 60 秒胸廓起伏次数 |
| 参考来源 | Tufts 心脏病学家庭监测指引、VVS 主人手册、[J Feline Med Surg 2013 研究](https://doi.org/10.1177/1098612X13508940) |

**这是产品定位最好的一个**：

> **我们不是在教育用户一件新事，而是在替兽医做他已经让主人做的事。**

- 需求已被兽医界验证（不需要我们论证）
- 任务是机械的（数数）→ 自动化的价值**明确且无争议**
- 不涉及诊断，只涉及**测量**
- 且它天然是**纵向的**（每天测）→ 与我们的记忆系统/时间线完美契合

### 2.3 Body Condition Score（BCS）· 体况评分

| 项 | 内容 |
|---|---|
| 地位 | 兽医标准工具，用于评估体脂与肥胖 |
| 照片可行性 | [Front Vet Sci 2025](https://doi.org/10.3389/fvets.2025.1604557) 专门研究「**仅凭照片**能否准确评估猫 BCS」 |
| **重要发现** | 研究同时测量 **inter-evaluator bias** —— 即**评估者之间本身就有分歧** |

**结论：BCS 从照片评估尚未定论。** 存在评估者间分歧意味着**存在准确率上限**。
价值低于前两者，建议排在后面。

## 3. 必须分清的一件关键事

**文献验证的是「方法」，不是「我的实现」。**

| | 已发表的工作 | 我们若用通用 VLM |
|---|---|---|
| 模型 | **专门训练**的 CNN（3447 张标注图、37 个 landmark） | Qwen-VL 零样本 |
| 验证 | 有 NRMSE 等量化指标 | **无** |
| 适用条件 | 受控拍摄条件 | 主人随手拍 |

**用通用 VLM 做 FGS 评分，这个组合没有任何人验证过。** 不能因为方向有文献支持，
就默认实现也有效。

**因此**：

| 阶段 | 做法 |
|---|---|
| 起步 | 通用 VLM 出**结构化评分**（5 个动作单元分别打 0/1/2/无法评分） |
| **必经步骤** | **与兽医评分做一致性检验**（weighted kappa / ICC / 组内相关） |
| 门槛 | 一致性达不到阈值 → **不上线疼痛评估功能**，只输出「观察到 X、Y」的原始描述 |
| 进阶 | 若准确率不足，改为 landmark 检测 + 几何描述子（文献路径） |

> **诚实原则**：在验证之前，输出只能是
> 「照片中可以看到耳朵后压、眼睑半闭」，**不能是**「疼痛评分 4/10」。

## 4. 五个现实约束

### 4.1 拍摄条件（最大障碍）

FGS 的原始方案是**笼内无干扰录像**，要求正面、放松、双耳可见、无遮挡。
主人随手拍的照片绝大多数**不满足**。

**对策：质量门禁 + 拍摄引导**

```
上传 → 质量检查（正面？双耳可见？清晰？光照？猫处于静息？）
  ├─ 通过 → 评分
  └─ 不通过 → 【拒绝评分】 + 给出拍摄指引（"请从正面、平视拍一张它趴着的照片"）
```

**绝不硬评**。这与已有的 `FeatureQuality` 概念一致——低质量就降低置信度或拒绝。

### 4.2 猫不是静止的

FGS 要求猫**未被干扰**。主人举着手机靠近拍照，本身就会改变它的表情与姿态。

**对策**：引导**远距离拍摄**，或在记录瞬间（Moment）的照片里顺带分析，
而不是让用户「来，拍一张让我分析」。

### 4.3 应激污染

摄像行为、拍摄时的靠近，都可能让猫进入轻微紧张状态，
使 FGS 出现**假阳性**（紧张 ≠ 疼痛，但面部表现相似）。

**这需要在评测中专门考察**，否则会出现大量误报，用户会很快卸载。

### 4.4 成本

视频分析 = 抽帧 × 单帧 VLM 成本，远高于单图。

**对策**：
- 单图优先（FGS 本身是设计给静态图像评分的）
- 视频只抽少量关键帧（猫静止且正面的帧）
- 呼吸频率用**计算机视觉信号处理**（胸廓运动周期检测）而不是逐帧 VLM——
  这是纯信号处理问题，不需要理解语义，成本低且更准确

### 4.5 个体差异

猫的脸型差异大，FGS 是绝对量表。可能需要个体基线辅助。
但注意：**不要用个体基线覆盖绝对量表**——量表是验证过的，基线是未验证的。

## 5. 最大风险：健康领域的过度承诺

**这比拟人化的风险严重得多。**

| 场景 | 后果 |
|---|---|
| 系统说「疼痛评分 2/10，看起来没问题」 | 用户**不去医院** → 延误治疗 |
| 系统说「检测到疼痛」但准确率未知 | 大量误报 → 用户焦虑 + 无谓就医 + 卸载 |
| 用户以为 App 能替代兽医 | 最坏情况 |

**这三条都必须由设计挡住**：

| 约束 | 内容 |
|---|---|
| C1 | 输出**永远不出现「没问题」「健康」「不用担心」**（已有 `FORBIDDEN_PHRASES`） |
| C2 | 数值评分**必须**附带拍摄质量与不可评分项 |
| C3 | 必须给 `limitations` 与就医建议阈值 |
| C4 | 定位是**筛查**（screening）不是诊断，且不可声称替代兽医 |
| C5 | 准确率未经验证前，**只输出原始观察描述，不输出分数** |

## 6. 优先级建议

| 顺序 | 项目 | 理由 |
|---|---|---|
| **P0** | **SRR（静息呼吸频率）** | ① 兽医已明确让主人在家做 ② 任务机械、自动化价值无争议 ③ 纯信号处理、成本低 ④ 不涉及诊断 ⑤ 天然纵向，契合时间线 |
| **P1** | **FGS（面部疼痛筛查）** | ① 有验证量表 ② 有自动化研究路径 ③ 价值高（疼痛是主人最焦虑的问题）④ 但需质量门禁 + 一致性验证 |
| **P2** | **BCS（体况）** | inter-evaluator bias 未定论，价值低于前两者 |
| P2 | 步态/活动量 | 需受控条件，手机视频噪声大 |
| **P0** | **场景标签**（睡觉/玩耍/进食/窗台） | 这是 S1 时间线的基础，不需要医学准确性，**技术风险最低** |
| **P1** | **呕吐/抽搐等事件录像** | 兽医会明确要求主人录像，价值直接 |

> 注意 **SRR 和「事件录像」都不需要 VLM 做医学判断**——
> 前者是信号处理，后者是「帮用户把视频存好、标好时间、方便就诊时给兽医看」。
> **这两个是最容易做出真实价值、风险最低的。**

## 7. 架构集成

### 7.1 节点设计

`pet_profile_analyzer` 职责过重，应拆分：

```
pet_profile_analyzer      身份建档（外貌特征，一次性）
        ↓
visual_state_assessor     状态评估（反复调用）  ← 新增
  ├─ scene_tagger         场景标签（S1 时间线基础）
  ├─ fgs_scorer           FGS 5 个动作单元评分
  ├─ bcs_estimator        体况评分
  └─ quality_gate         拍摄质量门禁（不合格则拒绝）
        ↓
respiratory_estimator     静息呼吸频率（视频，信号处理路径）  ← 新增
```

### 7.2 输出契约（复用行为解释器的证据模式）

```jsonc
{
  "assessment_type": "fgs",
  "evidence_mode": "acoustic_plus_history" 的字图像版: "visual_direct",   // 或 "insufficient_quality"
  "capture_quality": {
    "frontal": true, "ears_visible": true, "resting": false,
    "lighting": "fair", "overall": "fair"
  },
  "action_units": [
    { "name": "ear_position",         "score": 1, "note": "双耳略向外侧" },
    { "name": "orbital_tightening",   "score": 1, "note": "眼睑轻度半闭" },
    { "name": "muzzle_tension",       "score": 0 },
    { "name": "whiskers_position",    "score": 0 },
    { "name": "head_position",        "score": 0 }
  ],
  "unscorable_units": [],
  "total": null,                  // ← 验证前为 null
  "total_withheld_reason": "本功能尚未完成与兽医评分的一致性验证，暂不输出总分",
  "observations": ["耳朵略向外侧", "眼睑轻度半闭"],
  "limitations": "照片为单张静态；猫可能处于轻度紧张状态，面部表现与疼痛相似。",
  "suggested_action": "可再观察 1–2 天；若伴随食欲下降、躲藏或叫声改变，建议联系兽医。"
}
```

**注意 `total: null` + `total_withheld_reason`**：这是把 §3 的诚实原则**编码进契约**——
未验证前，结构上不允许输出总分。

### 7.3 与健康模块的关系

| 项 | 归属 |
|---|---|
| 视觉观察结果 | 作为 `HealthRecord` 写入（`source = VISION`） |
| 与行为/叫声信号融合 | 进 `HealthAssessment` 的 `signals_assessed` |
| 红线规则 | **视觉结果可以触发红旗**（如呼吸频率超阈值），但仍由 YAML 规则表决定 |
| 免责与覆盖率 | 完全复用健康模块的机制 |

## 8. 评测设计

| 指标 | 方法 | 门槛 |
|---|---|---|
| **FGS 一致性** | 与 ≥2 名兽医评分比对，weighted kappa / ICC | 达阈值才上线总分 |
| **动作单元级别一致率** | 逐单元比对 | 识别哪些单元模型判不准 |
| **质量门禁精度** | 人工标注「合格/不合格」照片 | 不得放行不合格照片 |
| **假阳性率（紧张 vs 疼痛）** | 用已知紧张的猫（如就诊前）测试 | 控制误报 |
| **SRR 准确率** | 与人工计数比对（同一段视频） | 误差 ≤1 次/分 |
| **场景标签准确率** | 人工标注 | 低门槛即可（S1 容忍度高） |

**SRR 的评测最容易做且最可信**——因为人工计数就是标准，且不涉及主观判断。
这是它应该排 P0 的技术原因之一。

## 9. 最终结论

| 问题 | 回答 |
|---|---|
| 可以用多模态分析猫吗 | **可以，且方向正确** |
| 它解决了拟人化的问题吗 | **不是解决，是缩小了知识缺口** |
| 它让「本喵饿了」变得可以接受吗 | **不。** 它扩展事实层，不扩展扮演层 |
| 最大的技术风险 | **把「文献验证的方法」误当成「我的实现已验证」** |
| 最大的产品风险 | **健康领域的过度承诺导致用户延误就医** |
| 先做什么 | **SRR（呼吸频率）+ 场景标签 + 事件录像**——三者风险最低、价值明确 |
| FGS 能做吗 | 能，但**必须先做一致性验证**；未验证前只输出原始观察，不输出总分 |
| 成本控制 | 单图优先；呼吸频率走信号处理而非逐帧 VLM |

> 一句话：**多模态的价值在于让系统「真的看到了」，
> 从而可以在更多事情上诚实地说话——而不是在更多事情上放肆地编造。**
