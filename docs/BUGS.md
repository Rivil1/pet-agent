# 失败案例集 · BUGS

> **这份文档是面试材料。** 面试官问「你遇到最大的技术困难是什么」时，
> 绝大多数候选人答不上来——因为他们没真正跑过自己的系统。
>
> 本项目自实现行为解释器以来共记录 **26 个实现级缺陷**，
> 每一个都有：症状（含实测数字）→ 排查 → 根因 → 修复 → **可迁移的教训** → 回归测试。
>
> **核心发现**：**26 个里有 15 个完全静默** —— 不报错、不崩溃，只是悄悄算错。
> 因为这是概率系统，没有「正确答案」能触发断言。
> 所以必须靠**机制性断言**（单调性、不变性、边界）去抓，而不是靠「看起来不对」。

## 2. 详细案例

### B1 · 「低质量 → 展宽似然」这个机制**方向不可控**

**类型**：机制性错误（想当然的设计被实测证伪）—— **最值得讲的一个**

#### 症状

设计意图：音频质量差 → 判别力下降 → 置信度下降。
实测（同一组特征，只改 `quality` 字段）：

```
                       isolation_distress 概率
quality = GOOD                0.269
quality = FAIR                0.334
quality = POOR                0.411      ← 质量越差，概率反而越高
```

与先验的总变差距离也是反向的：`GOOD 0.189 → FAIR 0.254 → POOR 0.331`。

#### 排查

先怀疑是符号写反，逐行核对后确认代码没问题。于是打印各情境在各质量下的对数密度：

```python
# 原实现
if inflation != 1.0:
    stat = GaussianStat(mean=stat.mean, std=stat.std * inflation)

# 对数密度
def log_density(value):
    z = (value - mean) / std
    return -0.5 * z * z - log(std)
```

**关键在这里**：把 `std` 乘上 `c` 后

```
-0.5·((x−μ)/(c·σ))² − log(c·σ)
  = -0.5·z²/c²  −  log σ  −  log c
```

- `−log c` 对所有情境是**同一个常数**，在 LLR 相减时抵消
- `−log σ` **完全不受 c 影响**
- 只有 `−0.5·z²/c²` 随 c 缩小

于是当 `c → ∞` 时，`z²/c² → 0`，似然退化成：

```
log p(f|k)  →  − log σ_k  + 常数
```

**即：判断完全由「哪个情境的标准差更窄」决定，与观测到的特征值无关。**

这就是「质量越差、某个分布较窄的情境概率越高」的原因。

#### 根因

> **用「扰动参数」来代替「表达不确定性」是危险的** ——
> 参数扰动的效果方向不可控，因为参数同时出现在多个项里（这里是 `z²` 和 `log σ`）。

#### 修复

质量应该作用于**证据力度**，不应该作用于似然本身：

```python
EVIDENCE_DISCOUNT = {GOOD: 1.0, FAIR: 0.75, POOR: 0.50}

contribution = clip(raw_llr, -CAP, CAP) * discount
```

所有 LLR 按比例缩小 → logit 按比例向先验收缩 → **单调、可解释、与数据无关的部分不受影响**。

修后验证：

```
quality = GOOD   TV=0.1892
quality = FAIR   TV=0.1494   ← 单调递减 ✓
quality = POOR   TV=0.1267
```

#### 可迁移的教训

1. **「听起来合理」的机制必须实测**。我原来的写法在文档里读起来完全正确。
2. **改动一个参数前，先看它出现在哪些项里**。`std` 同时出现在 `z²` 和 `log σ`，均匀缩放就必然引入非期望的偏置。
3. **需要「打折」时，直接打折，不要绕道扰动参数。**

#### 面试话术

> 「我设计里有一条『音频质量差就降低置信度』。实现方式是展宽高斯似然的标准差。
> 听起来没问题，但实测发现质量越差、某个情境概率反而越高。
>
> 排查后发现：对数密度是 `-0.5z² − log σ`，均匀缩放 σ 只让 `z²` 项变小，
> `log σ` 项不受影响。于是似然退化成『偏好标准差窄的情境』——**与观测数据无关**。
>
> 修法是：质量应该给**证据**打折，而不是扰动似然。改成对对数似然比整体乘一个折扣系数，
> 单调性就成立了——我从『与先验的总变差距离』这个指标上验证了它确实随质量下降而收敛。
>
> 这件事教给我的是：**参数扰动的效果方向不可控，因为它同时出现在多个项里。**
> 想表达『打折扣』就直接打折，不要绕道去动参数。」

### B2 · evidence 列表**静默丢弃**了最重要的两类证据

**类型**：静默丢弃

#### 症状

给解释器传了 `scene="它对着门叫"` 和一条相似历史样本，输出里**都没有出现**。
但 `logit` 确实被它们影响了——**证据消失了，影响还在**。

#### 排查

看构建顺序：

```python
for _mag, ctx, feat in ranked:
    if len(items) >= MAX_EVIDENCE_ITEMS:   # 先填满 measured
        break
    items.append(...)
if scene_ctx: items.insert(0, ...)          # 再插场景
for sample in used_samples[:2]: items.append(...)   # 再追加历史样本
return items[:MAX_EVIDENCE_ITEMS]           # ← 最后截断，把后加的截掉了
```

#### 根因

> **任何 `[:N]` 都是一次静默丢弃。** 尤其当「后加入的」恰好是优先级更高的类型时。

场景证据和历史样本证据**恰恰是用户最容易理解的证据类型**
（「你提到它对着门叫」比「基频跨度 281 Hz 高于参考值 140 Hz」有用得多），
却因为加入顺序靠后而被截掉。

#### 修复

**先算预算，再分配槽位**：

```python
reserved = (1 if scene_ctx else 0) + len(retrieved)
measured_budget = max(1, MAX_EVIDENCE_ITEMS - reserved)
```

#### 可迁移的教训

1. **截断必须显式设计**：问「按什么优先级截、谁保证重要的不被截」。
2. 这与项目里另一处设计同源：`PlanResult` 要求先验依赖**要么应用、要么说明跳过原因**——
   **不让任何东西静默消失**。同一原则在两个地方各犯/各防了一次。

### B3 · 测不出的特征被**零填充**

**类型**：静默编造

#### 症状

一段 0.5 秒的叫声片段，算出：

```
call_rate = 20.0 次/10s
ici_mean  = 0.052 s
```

猫不可能在 0.5 秒里叫 20 次。

#### 排查（两个独立原因）

**原因一：短窗口归一化放大噪声。**
`call_rate` 是「次/10s」的归一化指标。0.5s 里出现 1 次叫声，归一化后就是
`1 / 0.05 = 20`。**0.5 秒的窗口根本不足以估计速率。**

**原因二：分段没有间隔合并。**
合成信号的谐波拍频让包络出现深凹，被端点检测误判为多次独立叫声。

#### 根因

> **零填充是静默编造。** 下游会把「速率为 0」当成一个真实的测量值参与似然计算。
> 而实际上这个特征**根本没测出来**。

#### 修复

两处：

1. 加间隔合并

   ```python
   MIN_GAP_SECONDS = 0.08   # 短于此间隔视为同一次叫声
   ```

2. **契约层加 `unavailable` 字段**——测不出的特征必须被显式标记，而不是拿假值顶上

```python
class AcousticFeatures(BaseModel):
    ...
    unavailable: list[str] = Field(default_factory=list)
    """本次无法可靠测量的特征名。推理时**必须跳过**。"""
```

推理侧据此跳过：

```python
declared = set(features.unavailable)
for name in FEATURE_ORDER:
    if name in declared:
        continue
```

#### 可迁移的教训

> 这个 bug **直接印证了项目的核心原则**。
> 我在文档里写了「宁可显式标记缺失，也不给一个假数字」，
> 然后在实现里用零填充违反了它。
>
> **诚实性不是文档里的一句话，是会在实现里被违反的东西。**
> 所以它必须被编码进**契约**（`unavailable` 字段），而不是靠自觉。

#### 面试话术

> 「我在项目原则里明确写了『不能编造』。但实现时我把测不出的特征零填充了——
> 结果 0.5 秒的音频算出『20 次/10 秒』的荒唐速率。
>
> 这让我意识到的不是『我算错了』，而是：**诚实性必须被编码进类型系统**。
> 所以我给特征契约加了 `unavailable` 字段，测不出的特征显式标记，
> 推理时跳过——而不是给一个看起来正常的 0。
>
> 零填充最危险的地方在于它**不报错**。它只是让下游把假值当真值用。」

### B4 · 分段缺少间隔合并

**类型**：实现疏漏

见 B3 的「原因二」。谐波拍频造成的包络深凹被端点检测当成多次叫声的间隔。

**教训**：端点检测必须做间隔合并，这是标准做法。**用合成信号也没能掩盖它**——
反而正是合成信号（谐波丰富）暴露了这个问题。

### B5 · 把**估计器的局限**记在了**音频**头上

**类型**：归因错误

#### 症状

一段干净、完整、无噪声的合成叫声，被判为 `quality = POOR`。

#### 排查

```python
def _classify_quality(voiced_ratio, snr_db):
    if snr_db is None:
        return FeatureQuality.POOR      # ← 问题在这
```

而 `snr_db` 为 `None` 的原因：**整段都是叫声，没有静音段可作噪声底**。

#### 根因

> **`None` 的语义是「无法估计」，不是「质量差」。**
> 把两者混同，就是把「我的估计器做不到」误判为「数据有问题」。

#### 修复

改用**可测量**的 `voiced_ratio` 判定，同时**提高门槛作为补偿**（弥补缺失的那个信号）：

```python
if snr_db is None:
    if voiced_ratio >= 0.50: return GOOD
    if voiced_ratio >= 0.20: return FAIR
    return POOR
```

#### 可迁移的教训

> 区分**「数据差」**与**「我测不出」**。
> 前者是关于世界的判断，后者是关于自己能力的判断。混淆二者会产生系统性偏差。

### B6 · 后验退化成 one-hot → 每次判断都「高置信」

**类型**：校准缺失

#### 症状

```
logit 跨度 ≈ ±6    →    softmax 后 max(posterior) 接近 1.0
```

于是**每一次解释都落进「高置信」档**（≥0.65）——
这与项目的核心原则「不声称超出证据的确定性」**直接冲突**。

更隐蔽的是：它不会让任何测试失败，因为「高置信」本身是合法输出。

#### 根因

占位先验的标准差偏窄（U3：先验尚未用实测数据替换）+ `LLR_CAP=3` 允许单特征贡献 ±3

- 8 个特征累加 → logit 跨度远超合理范围。

#### 修复与遗留

加温度参数（softmax 前除以 T）：

```python
LOGIT_TEMPERATURE = 2.0    # ⚠️ 未经验证的校准参数
posteriors = _log_softmax(logits / LOGIT_TEMPERATURE)
```

并在 `limitations` 里**明确声明置信度未校准**：

> 「置信度尚未完成校准（详见 docs/DESIGN.md U1），请以候选排序与证据为主，不要依赖概率的绝对值。」

**注意**：温度只在归一化时施加，`log_odds` 保持原始值——这样「贡献之和 == logit」依然成立，
**可归因性没有被校准破坏**。

#### 可迁移的教训

1. **校准缺失是静默的**：它不违反任何契约，只是让输出系统性地过度自信。
2. **校准不应破坏可解释性**：我在 softmax 前加温度，而不是去缩放对数似然比，
   这样每个证据的贡献值仍然可复算。
3. **未校准就要说未校准**。加一个权宜值不是问题，**不声明才是问题**。

### B8 · 我的测试断言写反了（`misroute_cost` 参数语义）

**类型**：测试自身错误

#### 经过

价格矩阵的函数签名是 `misroute_cost(predicted, actual)`，我写测试时把语义读反了：

```python
# 我写的（错）
ask = misroute_cost(CHAT, AMBIGUOUS)         # 0.6 —— 其实是「该问未问」
not_asked = misroute_cost(AMBIGUOUS, CHAT)   # 0.15 —— 其实是「多问一句」
assert ask < not_asked                        # 0.6 < 0.15 → False
```

#### 处理

设计与实现都是对的，**是测试写错了**。修正断言，并**给函数补 docstring 举例说明参数语义**：

```python
def misroute_cost(predicted, actual):
    """⚠️ **参数语义容易读反**（实测确实会读反），举例说明：

        misroute_cost(AMBIGUOUS, CHAT)  → 0.15  多问了一句，便宜
        misroute_cost(CHAT, AMBIGUOUS)  → 0.60  该问未问，贵且用户不察觉
    """
```

#### 可迁移的教训

> **我自己都会读反的接口，别人一定会读反。**
> 修正测试只是修了症状；给接口加「容易读反」的显式说明才是修根因。

### B9 · 用不可能的输入去测一个分支

**类型**：测试自身错误

#### 经过

测置信度分档时我这样写：

```python
@pytest.mark.parametrize("posterior,tier", [(0.7,"high"), (0.5,"medium"), (0.3,"low")])
def test_confidence_tiers(self, posterior, tier):
    candidates = [IntentCandidate(posterior=posterior, ...),
                  IntentCandidate(posterior=1-posterior, ...)]   # 只有 2 个候选
    assert bi.confidence_tier == tier
```

`posterior=0.3` 时另一个候选是 0.7，所以 top 是 0.7 → 得到 `high`，测试失败。

#### 根因

**两个候选且归一化时，必然有一个 ≥ 0.5**，所以 `low` 档（< 0.45）**根本到不了**。
要测 `low` 必须用 ≥3 个候选。

#### 可迁移的教训

> 这是**设计的一个隐含性质**，而文档里没写。
> 测试失败暴露了它：「置信度分档只有在候选数 ≥3 时才可能出现 low 档」——
> 这个约束应该写进设计文档，因为它影响「什么时候该输出『无法判断』」。

**处理**：已修正测试（改用 3 个候选），并把这个隐含性质写进分档说明——
它影响一个实际决策：**什么时候系统应该输出「无法判断」**。

### B10 · 用含先验项的指标去度量一个与先验无关的效果

**类型**：测试自身错误

#### 经过

要验证「质量下降 → 判别力下降」，我这样度量：

```python
def spread_toward_prior(r):
    return max(abs(c.log_odds) for c in r.candidates)   # ← 错
```

但 `log_odds`（logit）**包含 `log_prior` 项**，而先验不受音频质量影响。
于是度量里混入了与待测效果无关的成分。

#### 修复

改用**后验与先验分布的总变差距离**——它直接度量「偏离先验多远」，与待测效果对齐：

```python
tv = 0.5 * sum(abs(posterior_k - prior_k) for k in contexts)
```

并且**控制变量**：用同一组特征值，只改 `quality` 字段
（原来还用了一个本身就是 POOR 质量的 fixture 当「good」，比较方向都是错的）。

#### 可迁移的教训

> **度量指标必须与待验证的效果对齐。**
> 如果指标里混入了不受实验变量影响的成分，信号会被稀释甚至反向。
> 这是实验设计问题，不是编码问题。

### B11 / B12 · 为「需要确认」而做的检测器**过宽**，把正常内容全部降级

**类型**：检测过宽（静默）—— 与 B3 同一类陷阱

#### 背景

设计意图（DESIGN.md §3.4）：语音转写会把「三点」听成「三只」这类错误，
**且事后无法察觉**。所以**含数量/时间**的内容应该降为 PENDING，等用户确认。

#### B11 · 用「含汉字数字」做判断

```python
_DIGITS = set("0123456789零一二三四五六七八九十百千万")
def _contains_digits(text): return any(ch in _DIGITS for ch in text)
```

汉语里「一」「十」在日常用语中极常见：

```
「它**一**开就跑」      → 判为含数字 → PENDING
「它**一**直这样」      → 判为含数字 → PENDING
```

**后果**：大量正常记忆全部落入 PENDING，**永远不会生效**。
因为 PENDING 不参与默认检索，用户看到的是「系统什么都不记得」。

#### B12 · 改成「数字 + 单位」后仍然过宽

```
「十**分**黏人」    → 「十分」匹配为「10 分钟」→ PENDING
「一**点**都不怕」  → 「一点」匹配为「1 点钟」→ PENDING
```

单字单位 `分` 与 `点` 的歧义太大。

#### 根因

> **为「需要确认」而设的检测器过宽时，代价不是多问一句，而是功能失效。**
>
> 这与 B1（展宽似然）、B3（零填充）是**同一类陷阱**：
> 用一个间接信号去代替目标判断，而间接信号在真实数据上命中率远高于预期。

#### 修复

单位表只保留**歧义小**的：

```python
_QUANTITY_PATTERN = re.compile(
    r"[0-9０-９]+"                                  # 阿拉伯数字
    r"|(?:[一二三四五六七八九十百千万两]+)"
    r"(?:分钟|小时|公斤|毫升|次|天|周|月|年|个|颗|粒|勺|克|斤|度|碗|遍)"
)
```

- **剔除 `分` 与 `点`**（「十分」「一点」「有点」歧义大）
- 时间点靠**阿拉伯数字**捕获（「早上 7 点」→ 匹配 `7`）
- 保留的单字单位（次/天/个…）单独出现时几乎总是量词

#### 可迁移的教训

1. **宽检测器的代价不对称**：漏判 = 多问一句；误判 = 功能失效。
   两者差异巨大，所以宁可窄、不可宽。
2. **中文字符级的启发式几乎总是不准**。改用**带上下文约束的模式**。
3. **同一类陷阱在三个地方各犯一次**（B1 参数扰动、B3 零填充、B11/B12 检测过宽）——
   说明这不是偶发失误，而是需要系统性自检的认知偏差：
   **问「这个间接信号在真实数据上会命中多少」，而不是「它能不能命中」。**

### B13–B18 · **写出来了但从未被执行过**

**类型**：未执行代码中的缺陷（七种表现，同一个根因）

#### 背景

契约层、解释器、记忆飞轮都有测试（186 项）。但**编排层（`app/graph/`）没有任何测试** ——
它被写出来，然后一直没被构建过。

第一次为它写测试时，三个缺陷同时暴露（B13–B15）。
然后写**真实模型客户端**时，同样的事又发生了一次：
代码写完了，但没有任何人（包括我自己）跑过它，又暴露两个（B16–B17）。

**两轮下来，这条教训被验证了五次。**

**第三轮（每日总结）又验证了第六次。**

**第四轮（案例推理接线）是第七次。**

#### B13 · 降级路径用了错的枚举

```python
from app.schemas import Severity          # 守卫的枚举：CRITICAL / MAJOR / MINOR
NodeError(node="companion_agent",
          kind="upstream_error",
          severity=Severity.DEGRADED)     # ❌ 不存在 → AttributeError
```

契约里**有两个「severity」枚举**：

| 枚举 | 取值 | 用于 |
| --- | --- | --- |
| `Severity` | CRITICAL / MAJOR / MINOR | `Violation`（守卫违规严重度） |
| `ErrorSeverity` | FATAL / DEGRADED / SILENT | `NodeError`（节点错误严重度） |

**所有降级路径都写错了**：LLM 失败、声学提取失败、记忆写入跳过、照片全失败 ——
八处。一旦真发生降级，系统不会优雅降级，而是抛 `AttributeError`。

**是 pyright 发现的**（`Cannot access attribute "DEGRADED" for class "type[Severity]"`）。

#### B14 · 图组装漏了一个节点 → **整张图无法编译**

```python
builder.add_edge("memory_extractor", "memory_writer")
builder.add_edge("memory_writer", "record_acknowledge")     # 加了边…
# ……但从未 add_node("record_acknowledge", …)              # ❌ 没加节点

ValueError: Found edge starting at unknown node 'record_acknowledge'
```

**不是「记录功能不可用」，是整个 `build_graph()` 抛异常** ——
所有意图都无法工作。

#### B16 · 把 frozen dataclass 当 Pydantic 模型用

```python
# app/profile/dashscope.py
return parsed.model_copy(update={"image_url": image_url})
#      ^^^^^^ VisualObservation 是 @dataclass(frozen=True)，没有这个方法
# AttributeError: 'VisualObservation' object has no attribute 'model_copy'
```

项目里两种数据对象混用：**契约层全是 Pydantic**，而 `VisualObservation` 是
冻结 dataclass（因为它是领域内的值对象，不需要校验）。
写代码时下意识用了 Pydantic 的 API。

**后果**：每一次真实视觉调用都会 `AttributeError`。
即「档案功能在真实环境里完全不可用」，而我以为它写好了。

**修法**：用 `dataclasses.replace`。

#### B17 · 关键字专用参数用位置展开调用

```python
def add(self, *, prompt: int, completion: int) -> None: ...   # 关键字专用

def _usage_of(payload) -> tuple[int, int]: ...

self.usage.add(*_usage_of(data))     # ❌ TypeError: takes 1 positional argument but 3 were given
self.usage.add(prompt=p, completion=c)   # ✓
```

**后果**：每一次真实 LLM 调用都会 `TypeError`。
比 B16 更广 —— 它让**整个文本生成路径**不可用。

> 有意思的是：这两个缺陷都在**第一行真实调用**就崩。
> 看着最“显然”的接线代码，恰恰因为没人跑过而全错。

#### B18 · 状态与来源不匹配 —— **“事后由路由层修正”是错的**

每日总结把候选转成记忆时，我无条件写了 `ACTIVE`，
心里想的是「反正飞轮的置信度路由会把 `SYSTEM_INFERENCE` 改成 `PENDING`」：

```python
return MemoryEvent(
    ...
    source=_SOURCE_MAP[candidate.source_layer],   # AI 归纳 → SYSTEM_INFERENCE
    status=MemoryStatus.ACTIVE,                    # ❌ 非法组合
    # 注释：“实际落库状态由路由层改成 PENDING，这里不预判”
)
```

**结果在构造那一刻就抛了：**

```
ValidationError: SYSTEM_INFERENCE 不得以 ACTIVE 状态存在（防自我强化）。
只能写入 PENDING_CONFIRMATION；用户确认后 source 改为 USER_CONFIRMATION 再转 ACTIVE。
```

**后果**：一条 AI 归纳的候选会让**整天的总结崩掉**。

#### 根因：非法组合在**构造**时就不存在，活不到路由层

我的假设是「先构造出来，后面再修正」。但契约的设计是
**非法状态根本不允许被构造**。两者直接冲突：

| | 我的假设 | 契约的设计 |
| --- | --- | --- |
| 非法组合何时被拒 | 路由层（事后） | **构造时（当下）** |
| 中间态是否存在 | 短暂存在，待修正 | **不存在** |

> **可迁移的教训**：当契约把不变量编码进构造器时，
> “先造出来再修”不是一个次优选择，而是**根本走不通**。
> 必须在上游就把状态算对。

**值得记下的一点**：这次是**契约拦住了我**，而不是测试。
不变量写在类型里，写错的那一刻就报错 —— 这正是把所有不变量
从文档搬进契约（I1–I18）的价值。

#### 修法与防复发

改成由来源直接决定初始状态：

```python
_STATUS_MAP: dict[ExtractionSource, MemoryStatus] = {
    ExtractionSource.OWNER_RECORD: MemoryStatus.ACTIVE,
    ExtractionSource.AI_INFERENCE: MemoryStatus.PENDING_CONFIRMATION,
}
```

并加一个**穷尽性断言**：`set(_STATUS_MAP) == set(ExtractionSource)` ——
将来新增来源层时，漏掉映射会直接失败，而不是静默给出错状态。

#### B22 · 工厂加了参数但上游没传 → **新能力永远走不到**

案例推理需要“这只猫已被标注的叫声记录”。我给节点工厂加了参数：

```python
def make_behavior_interpreter(
    prior, feature_extractor, similar_lookup=None, records_lookup=None
): ...
```

也把节点内部改成了 `interpret_meow`。但 `build.py` 里还是：

```python
builder.add_node("behavior_interpreter",
                 make_behavior_interpreter(prior, feature_extractor, similar_lookup))
#                                                                  ↑ records_lookup 没传
```

**后果**：`records_lookup` 永远是 `None` → 案例推理的候选集永远为空
→ **`case_based` 模式在真实链路里一次也不会生效**。

而它不报错、不崩溃：

```
decision.mode = measured_only
decision.reason = "相似案例 0 条，没有任何情境达到 3 条"
```

**理由看起来完全合理** —— 因为它确实“没有案例”——只是原因是**没人去取**。

#### 与 B15 是同一个形状

| | B15 | B22 |
| --- | --- | --- |
| 新能力 | 档档案加载 | 案例推理 |
| 表现 | LLM 从未被调用 | `case_based` 从未生效 |
| 静默原因 | 拿不到档案→返回兑底 | 拿不到记录→降级到冷启动 |
| 发现方式 | 断言“档案在最早一步加载” | 断言“记录够时应走到 case_based” |

> **新增一个可选参数时，要问一句：谁会给它传值？**
> 默认值是 `None` 的注入点是一个静默的失败通道 ——
> 没人传时，功能静静地不存在，而理由看起来像是数据问题。

#### 可迁移的教训

1. **“功能没生效”与“数据不满足”必须能区分。**
   本侧靠 `ModeDecision.reason` 把两者拆开了：
   - “未提供 records_lookup”→ 接线问题
   - “相似案例 0 条” → 数据问题
   没有这个字段，两者在日志里长得一模一样。
2. **可选注入参数需要一条“端到端已验证”的断言。**
   只测工厂函数本身（传了参数→行为对）不够 ——
   必须从 `build_graph` 出发测一次。

#### 共同根因

> **写在代码里 ≠ 被执行过。**
>
> 这六处都属于「写出来了、但从未跑过」的代码。而它们恰好都是**接线层**：
> 枚举映射、节点注册、上下文传递、类型 API、调用约定、**状态与来源的匹配** ——
> 这些地方没有业务逻辑，写的时候看起来最“显然”，也最容易漏。

**这与 B11/B12（检测过宽）是同一类错误的两种形态**：
都不是算错了，而是**构建出来的东西与实际运行的东西不一致**。

#### 修法与防复发

| 缺陷 | 修复 | 防复发 |
| --- | --- | --- |
| B13 | 改用 `ErrorSeverity` | 引入 **pyright** 作为常规检查（生产代码现 0 error） |
| B14 | 补 `add_node` | `build_graph` 编译后**自检** `ROUTE_TARGETS` 的每个目标都是真节点 |
| B15 | 新增 `load_context` 入口节点 | 测试断言「档案在最早一步加载」 |
| B16 | 改用 `dataclasses.replace` | mock transport 测试覆盖真实调用路径 |
| B17 | 改用关键字调用 | 同上 |
| B22 | 在 `build.py` 与 `app/api/main.py` 都传入 `records_lookup` | 从 `build_graph` 出发的端到端断言（`test_case_based_when_records_suffice`） |

**B16/B17 的发现方式值得单说**：它们不是靠真实 API 调用发现的，而是靠
**``httpx.MockTransport`` 离线测试** —— 用一个假的 HTTP 层把真实客户端代码
从头到尾跑一遍。这样既不需要密钥，又能验证「代码路径能跑通」。

两者分工明确：

| 手段 | 验证什么 | 能否自动化 |
| --- | --- | --- |
| MockTransport 测试 | **我的代码自洽**（请求组装、响应解析、错误分类） | ✅ 可以 |
| `scripts/live_check.py` | **我对 API 的理解正确** | ❌ 需人工跑一次 |

并新增一个直接针对 B14 的测试：

```python
def test_all_routes_map_to_real_nodes(graph):
    expected = {"load_context", "understand_input", ..., "response_guard"}
    assert expected <= set(graph.nodes)
```

#### 可迁移的教训

1. **接线层需要最基础的冒烟测试**：不需要验证业务逻辑，只需要「能构建起来」。
   B14 的修法成本是一条 `assert`。
2. **静态类型检查能拓到运行时崩溃**，尤其是枚举、属性名这类拼写级错误。
   降级路径平时不跑，测试很难覆盖到 —— 类型检查恰好弥补这一点。
3. **「功能全部退化成同一条兜底回复」是接线失败的特征信号**。
   如果发现所有输出都一样，先怀疑上下文没传过去，而不是去调 prompt。

#### 面试话术

> 「我的契约层、解释器、记忆飞轮都有测试，186 项。但编排层没有 ——
> 我把它写出来了，然后一直没构建过。
>
> 第一次为它写测试时，一次暴露了三个缺陷：降级路径用了错的枚举
> （契约里有两个叫 severity 的枚举）、图组装漏了一个节点导致整张图无法编译、
> 以及**没有任何节点去加载宠物档案**。
>
> 第三个最隐蔽：不报错、不崩溃、HTTP 200，只是所有回复都变成同一句
> 「请先上传照片」。因为 `companion_agent` 拿不到档案就直接返回了兜底文案，
> **LLM 从来没被调用过**。
>
> 这三处的共同点是：都属于**接线层** —— 枚举映射、节点注册、上下文传递。
> 这些地方没有业务逻辑，写的时候看起来最显然，也最容易漏。
> 所以我现在会为接线层单独写冒烟测试：不需要验证业务逻辑，只需要「能构建起来」。」

### B19 · 同义词互为子串 → **一次提及算成两次**

**类型**：静默编造（给出了一个假数字）—— 与 B3（零填充）同族

#### 症状

每日总结要展示「今天你提到吸尘器 3 次」。这是要给用户看的**计数**。

我的词表里为了兼容说法，收了 `("吸尘器", "吸尘", ...)`。
而实现是逐词累加：

```python
hits = sum(msg.content.count(kw) for kw in keywords)
```

于是「它怕**吸尘器**」→ `count("吸尘器")=1` + `count("吸尘")=1` = **2**。

#### 根因

> **同义词表内允许互为子串，但计数时没有去重。**
> 一次提及被算成两次。

它的隐蔽性在于：数字看起来完全合理。
「今天提到吸尘器 2 次」不会让任何人怀疑 —— 除非他恰好知道主人只提了 1 次。

#### 为什么这个 bug 比它看起来重要

这个计数是**要展示给用户并据以判断的事实**。
同一套代码算出来的「5 次里 4 次是门口」也是同一个量。

> **计数错了，整套「可机械验证」的承诺就没了。**
> 案例推理的全部价值建立在「计数是真的」上面 —— 这是它的地基。

#### 修法

从左到右贪心取**最长匹配**，匹配到就跳过该长度：

```python
def _count_mentions(text: str, keywords: tuple[str, ...]) -> int:
    ordered = sorted(keywords, key=len, reverse=True)   # 长的优先
    count = 0
    i = 0
    while i < len(text):
        for kw in ordered:
            if text.startswith(kw, i):
                count += 1
                i += len(kw)      # 跳过，不再重复计数
                break
        else:
            i += 1
    return count
```

#### 可迁移的教训

1. **「关键词计数」看起来不值得写测试，但它恰恰是展示给用户的数字。**
   凡是会成为用户可见事实的量，不管多简单，都要有用例钉住具体数值。
2. **发现方式是「断言精确值」而不是「断言大于 0」。**
   我写的是 `== 1`；如果当时写 `>= 1`，这个 bug 永远不会被发现。

> **能机械核对的量，测试就要写精确值。**
> `>= 1` 只能证明「有」，不能证明「对」。

### B20 · 匹配失败 → **静默退回默认值**

**类型**：静默丢弃（信息丢了但不报错）

#### 症状

「宠物的一天」要把节拍按早/午/晚/夜排序。端到端跑一次，输出是：

```
晚上  它喜欢在窗台晒太阳     ← 实际是早上 8 点的事
晚上  它梳毛时很放松
```

两条都是「晚上」。

#### 根因

时间分桶按 `content` 精确匹配：

```python
stamps = {msg.content: msg.at for msg in messages}
at = _time_of_day(stamps.get(candidate.content))   # ← 永远 get 不到
```

但 `content` 是**改写后**的句子，原文不是它：

| 字段 | 值 |
| --- | --- |
| `content`（改写） | 「它喜欢在窗台晒太阳」 |
| 原文消息 | 「它**早上**在窗台趴着晒太阳」 |
| `quote`（逐字复制） | 「它早上在窗台趴着晒太阳」← 能匹配上 |

匹配不上 → `stamps.get(...)` 返回 `None` → `_time_of_day(None)` 返回默认的 `EVENING`。

> **`dict.get()` 的默认值是一条静默的失败通道。**
> 它让「匹配不上」和「确实是晚上」变成同一个结果。

#### 为什么单测没拓到它

这一点最值得记：**单测掩盖了它，因为 fixture 的形状与生产数据不一致。**

```python
# 测试里的 fixture：quote == content == 原文
def _cand(content):
    return DigestCandidate(content=content, quote=content, ...)
```

于是 `content` 恰好能匹配 —— 测试全绿，生产全错。

> **用生成值当 fixture 时，要问一句「这个值在生产里长什么样」。**
> 真实的 `content` 与 `quote` **从来不相同**：前者是归纳后的句子，
> 后者是原文片段。fixture 把它们写成相等，就抹掉了两者的区别。

#### 修法

改用 **`quote`** 定位：

```python
def _stamp_for(candidate, messages) -> datetime | None:
    needle = _normalize(candidate.quote)   # quote 是按构造能在原文里找到的
    ...
```

**`quote` 是全文里唯一按构造就能在对话中找到的字段** ——
因为 `app/digest` 的校验已经强制了这一点。用它做定位是免费的。

#### 可迁移的教训

1. **`get(key, default)` 是静默失败的高发区**。凡是用它做分支的地方，
   问一句「匹配不上时会发生什么，我会知道吗」。
2. **fixture 必须与生产数据同形。** 把两个语义不同的字段写成同一个值，
   等于宣布它们无区别 —— 而它们恰恰有区别（这正是那个 bug 的成因）。
3. **端到端跑一遍的价值**：这个 bug 在 378 个单测全绿的情况下依然存在，
   是把它实际打印出来才看见的。

### B21 · 不变量**过宽** —— 它把危险的那个方向也拦了

**类型**：设计缺陷（不是实现缺陷）—— **契约本身写错了**

#### 症状

健康模块的覆盖率门限写的是：

> 覆盖率 < 0.3 时，级别**必须**为 `INSUFFICIENT_DATA`。
> 禁止把「没有数据」伪装成「没有异常」。

我的代码是「红旗命中 → `EMERGENCY`」。构造评估时直接抛：

```
ValidationError: 覆盖率 0.06 < 0.3，级别必须为 INSUFFICIENT_DATA。
禁止把「没有数据」伪装成「没有异常」。
```

#### 根因：把两个方向的约束写到了一条规则里

| 情形 | 正确输出 | 理由 |
| --- | --- | --- |
| 覆盖率低 + **无命中** | `INSUFFICIENT_DATA` | 「没测」不能变成「没事」 |
| 覆盖率低 + **有命中** | **保留命中级别** | 已存在的危险信号不因「别的没测」而失效 |

这条规则的**理由**（禁止伪装成「没有异常」）只适用于第一行，
但它**实现**成了对第二行也拦截。

而第二行才是危险的方向：

> `UrgencyLevel.INSUFFICIENT_DATA` 的 docstring 写的是
> 「绝不可**降级表述**为「未发现异常」」。
>
> **把 `EMERGENCY` 降级成 `INSUFFICIENT_DATA` 也是一次降级，
> 而且是危险的那个方向** —— 假阴性的代价是猫可能死亡（非对称代价）。

#### 它与 B11/B12 是同一类

| | B11 / B12 | B21 |
| --- | --- | --- |
| 防的是什么 | 含数字的内容须确认 | 低覆盖率不得声称没事 |
| 代价不对称 | 漏判 = 多问一句，误判 = 功能失效 | 漏判 = 没事，**误判 = 急诊被压掉** |
| 实际后果 | 功能失效 | **危险的假阴性** |

> **为了防住一个方向而把反方向也拦住** —— 这个模式在本项目里出现了三次。

#### 修法

只在**没有命中**时才施加门限：

```python
if self.coverage < MIN_COVERAGE_FOR_ASSESSMENT:
    if not self.red_flags_triggered and self.level != UrgencyLevel.INSUFFICIENT_DATA:
        raise ValueError(...)
```

同时保留「EMERGENCY 必须由红旗触发」那条 —— 它防的是模型自判急诊，方向是对的。

#### 一个值得注意的事实

**这个缺陷是被契约自己拓到的，不是被测试。**
契约写了理由，而理由与实现不一致 —— 于是它拦住了一段**正确**的代码。

> 把不变量写进契约会让错误在写下的那一刻就报错。
> 但契约也会写错，而且它写错时会**很自信地**拦住正确的东西。
> 所以每次契约报错都要问一句：**是代码错了，还是规则错了？**

### B23 · 同一类失败，三种表达

**类型**：错误处理不一致（混合了静默与崩溃）

#### 背景

多模态提取器的输入是**模型的自由输出**，所以「输出不可用」是常态而非异常。
它至少有四种形态：

| 输入 | 期望行为 |
| --- | --- |
| 空响应 | 返回 `ok=False` |
| 不是 JSON | 返回 `ok=False` |
| 词表外的动作 | 丢弃并记录 |
| 词表外的场景物体 | 丢弃并记录 |
| 含推断性表述 | 返回 `ok=False`（契约拒绝） |

#### 实际出现了三种不一致的表达

```python
# ① 词表外的动作 → 静默丢弃（continue）
except ValueError:
    continue          # ← 丢了，但没人知道丢了多少

# ② 词表外的场景物体 → **抛错**，整条观察失败
scene_objects = [o for o in ... if o in SCENE_OBJECTS]   # 后来改成抛错
# ③ 空响应 → **异常逃逸**（`_content_of` 在 try 块外）
content = _content_of(data)   # ← try 只包了 post_json
```

**同一个问题（模型给了不该有的东西）有三种行为**，
而调用方无从预设 —— 它得同时处理「返回失败对象」与「抛异常」两条路径。

#### 根因

> **把「容错」与「静默」的边界没划清。**
>
> 本项目有一条原则：**不让任何东西静默消失**（B2 的来源）。
> 但「容错」（继续处理）与「静默」（不告诉任何人）是两件事 ——
> 我写的时候把前者当成了后者的理由。

#### 修法

统一为两条规则：

| 情形 | 行为 |
| --- | --- |
| **模型整体输出不可用** | `ok=False` + `error` 写明原因（**不抛异常**） |
| **单个值是词表外的** | 丢弃，**并记入 `ignored_terms`** |

`ignored_terms` 是这一修的关键：**丢弃可以，但要留下痕迹。**
高频出现词表外的值说明 prompt 或词表要改 —— 静默丢弃会让这个信号永远看不到。

#### 第三个问题：`observed_at` 的默认值破坏可复现

`ModelObservation.observed_at` 默认 `now()`，于是「同一输入 → 同一输出」
这条本项目的硬要求（`DESIGN.md` §6.5）在解析层就破了。

测试拓到了它：

```
AssertionError: a.model_dump() != b.model_dump()   # 差 observed_at
```

**修法**：`observed_at` 改为**可显式传入**，并在测试里传入固定值。

> **数据模型里不要放非确定性的默认值。**
> 时间戳是「什么时候观察的」，不是「从输出推导的」——
> 它应该由调用方给定，而不是由解析器偷偷填上当前时间。

#### 可迁移的教训

1. **同一类失败只能有一种表达。** 混合「返回失败对象」与「抛异常」，
   会让每个调用方都要处理两条路径 —— 而总有一处会漏。
2. **容错 ≠ 静默。** 可以继续处理，但丢弃的东西要留下痕迹。
3. **非确定性默认值会默默地破坏可复现性。** 它不报错，
   只是让「同输入同输出」在某个字段上不成立。

> 这三个问题都是**我自己的测试拓到的**，不是运行时报错拓到的。
> 而它们都属于同一类：**我定义了「正常路径」，但没有定义「失败路径的契约」。**

### B24 · 「两件事看起来一样」—— **修它的时候又抹平了一次**

**类型**：区分度缺失（静默）

#### 症状

日报当天有对话、但提取失败时，输出是：

```
9 月 12 日 · 它的一天

（今天还没有可讲述的内容）
```

**与「当天真的没说话」完全一样。** 而这两件事的含义差别很大：

| 情形 | 含义 |
| --- | --- |
| 当天没说话 | **正常状态**，一句话都不用说 |
| 有对话但没提取出来 | **可能是系统的问题**，用户应该知道 |

#### 第一次修（错的）

在无内容时把 `digest_notes` 追加进去：

```python
render_story(story, digest_notes=digest.summary.notes)
```

结果：**「当天没对话」也显示了说明** —— 因为那条路径的 `skipped_reason`
（「当天没有对话，无需总结」）同样会进 `notes`。

> 我为了「让差异可见」，把两种情况又变成了同一种。

#### 真正的修法

用**「是否真的跑过提取」**来判定：

```python
digest_notes=(None if digest.skipped_reason else digest.summary.notes)
```

`skipped_reason` 非空 ⟺ 没调模型 ⟺ 当天真的没事，不必解释。

#### 可迁移的教训

1. **「让某个差异可见」的修法本身要检查。**
   最容易犯的错是「把所有情况都变成可见」，于是差异又被抹平了 ——
   而且这次是**朝另一个方向**抹平的。
2. **区分两个状态，靠的是它们之间那个真正不同的字段**，
   不是靠「有没有说明文字」。
   本例里那个字段是 `skipped_reason` —— 它恰好就是「有没有跑过提取」的直接表示。
3. 这个模式在本文件里已出现多次（B2 / B20 / B23 / B24）：
   **同一类问题会在相邻的两次修改里各出现一次。**

### B25 · 区分度缺失**复发** —— 记完 B24 的下一轮又犯了

**类型**：区分度缺失（静默）—— **与 B24 同一类**

#### 经过

B24 刚刚记下「两件事看起来一样」这个模式，紧接着做多模态接入时又犯了一次：

```python
def _extract_observation(media_extractor, raw):
    if media_extractor is None or not raw.audio_url:
        return None, None          # ← 未配置
    try:
        obs = media_extractor.extract(...)
    except Exception as exc:
        return None, NodeError(...)  # ← 失败，但也返回 None
    
# 于是 trace 里两者都显示：
#   obs=未提取
```

**「没配提取器」与「配了但失败」的排查方向完全不同**：
前者是配置问题，后者是上游问题。写成一样，这个 trace 字段就等于没有。

#### 修法：四种状态显式区分

```python
def _obs_note(observation, configured: bool) -> str:
    if not configured:      return " obs=未配置"   # 配置问题
    if observation is None: return " obs=失败"     # 上游问题
    if not observation.ok:  return " obs=不可用"   # 模型说看不出（正确行为）
    return f" obs={len(observation.actions)}动作/..."
```

#### 真正的教训

> **把一类错误写进文档，并不会让你不再犯它。**

B24 记完之后我立刻又犯了同一个错，而且是在**正在读那份文档的那一轮**。
因为「让两种状态看起来一样」不是知识缺口 —— 是**编码习惯**。

能拦住它的是**测试**，不是文档：

```python
assert "obs=未配置" in none_trace
assert "obs=失败" in fail_trace
assert "obs=未配置" not in fail_trace, "「失败」不得显示成「未配置」"
```

> 写进文档的价值在于**排查更快**（一看就知道是哪一类），
> 而防复发要靠断言。这两件事不能互相替代。

#### 一个可观察的信号

同一个错误模式在相邻两轮里各出现一次 —— 这说明它不是偶发，
而是我在「写降级路径」时的默认写法有问题：

**我习惯让失败返回 `None`，而 `None` 承载不了「为什么是 None」。**

对策：**降级路径的返回值要携带状态，不能只返回空值。**
（同一份修法也适用于 B23 —— 那里是三种失败表达。）

### B26 · **守卫自身的缺陷** —— 安全检查把 mock 报成 live

**类型**：守卫自身缺陷（静默）—— 与 B21 同类（契约/守卫本身写错）

#### 症状

为防「没配密钥时静默退到 mock」，我给 API 加了 provider 模式暴露。
初版推断逻辑：

```python
def infer_is_mock(llm, embedder, vision) -> bool:
    return all(isinstance(p, _MOCK_TYPES) for p in (llm, embedder, vision))
```

实测：

| 输入 | 初版结果 | 正确结果 |
| --- | --- | --- |
| `MockLLM` + `HashEmbedder` + `MockVision` | `mock` ✓ | `mock` |
| `OpenAICompatLLM` × 3 | `live` ✓ | `live` |
| **`MockLLM` + `HashEmbedder` + 自定义桩** | **`live`** ❌ | `unknown` |
| **三个自定义桩** | **`live`** ❌ | `unknown` |

第二行是发现的方式：我拿测试里那个 `_StubVision` 跑了一遍真实请求，
`/healthz` 报 `mode: live`、`mock_notice: None` —— 而实际只有一组占位实现。

#### 根因：报错的方向反了

```python
if all(flags):   return "mock"
if not any(flags): return "live"   # ← 「不是 mock」被当成了「是真实」
```

**`live` 是推出来的，不是验出来的。** 而推的方向是危险的那个：

| 误报方向 | 后果 |
| --- | --- |
| mock → live | **一次假演示看起来像真演示** |
| live → mock | 多一个警告，无实质损失 |

两者的代价不对称，而我的逻辑对危险方向更宽松。

#### 修法：两侧都用白名单

```python
_MOCK_TYPES = (MockLLM, HashEmbedder, MockVision, UnavailableVision)
_LIVE_TYPES = (OpenAICompatLLM, OpenAICompatEmbedder, OpenAICompatVision)

modes = {_classify_type(p) for p in (llm, embedder, vision)}
if modes == {"mock"}: return "mock"
if modes == {"live"}: return "live"
return "unknown"          # ← 其余一切
```

> `UnavailableVision`（显式缺失的占位）也计入 mock：否则 `MOCK_PROVIDER=1`
> 会被报成 `unknown`，把排查引向错误方向。
> 真实实现之后改名为 `OpenAICompat*`（见决策 D46）—— 同一个类会被用来调
> DashScope 与火山方舟，名字里带厂商就会说谎。

> **声称 `live` 需要有正面证据**（在已知真实实现的名单里），
> 不能从「它不是已知的 mock」推出来。

这与整个项目的 fail-closed 取向一致：无法确认时宁可说不知道。
`UNTRUSTED_MODES = {"mock", "unknown"}` —— **两者同等对待**。

#### 可迁移的教训

1. **给错误加一层守卫时，守卫本身要有测试。**
   否则守卫会成为新的静默失败点 —— 而且它比被守的东西更难发现，
   因为**它看起来就是在防这个**。
2. **安全检查的不对称代价要选对方向。**
   问一句：「这个检查误报时，会让我更谨慎还是更放心？」
   后者是危险方向。
3. **`unknown` 是一个必要的取值。** 两分法（是/否）在安全判断上
   常常不够 —— 它逼你在「不知道」时选一个，而选错的方向就是危险那个。

> B21 和 B26 是同一类：**用来防错的机制本身写错了。**
> 而它们都很难发现 —— 因为你在读它的时候，会觉得「它正是在防这个」。

## 3. 类型化规律

### 3.1 最重要的发现：**缺陷大多不会自己暴露**

```
26 个缺陷中：
  15 个完全静默          ← 不报错、不崩溃，只是悄悄算错
   4 个会崩但从未被触发   ← B13 / B16 / B17 / B18
   1 个编译失败           ← B14，反而是最容易发现的
   1 个崩溃               ← B7
   3 个测试自身错误
   2 个守卫自身缺陷       ← B21（契约写宽）、B26（安全检查报错方向）
   1 个错误处理不一致     ← B23（同一类失败三种表达）
       （B24/B25 归入「静默」：它们让两件事看起来一样）
```

**「会崩但从未被触发」这一类最危险**：它比静默错误更难发现（静默至少会表现为
结果不对，而它连结果都没有），因为在它被触发之前，一切看起来都正常。

**原因是结构性的**：这不是一个「有正确答案」的系统。
`p=0.411` 和 `p=0.269` 都是合法的概率分布，没有任何断言会失败。

**而接线层的缺陷（B13–B18）靠另一种方式隐蔽**：写出来了但从未被执行过。
它们不在「算得对不对」的层面，而在「有没有接上」的层面。

**所以必须主动构造「机制性断言」，而不是等它出错：**

| 断言类型 | 例子 | 抓到的 bug |
| --- | --- | --- |
| **单调性** | 质量下降 → 向先验收缩 | B1 |
| **不变性** | 标记 `unavailable` 后，该特征的荒谬值不影响结果 | B3 |
| **边界** | 后验不得退化成 one-hot（`max < 0.99`） | B6 |
| **确定性** | 同一输入 → 同一输出 | （可复现性要求） |
| **完备性** | 证据预算不得让 PRIOR/RETRIEVED 消失 | B2 |
| **归因正确性** | 无法估计 ≠ 质量差 | B5 |

> **面试要点**：「我会主动为概率/评分系统写单调性和边界断言，
> 因为它们不会像空指针那样自己报错。」

### 3.2 六类反复出现的失败模式

| 类型 | 特征 | 案例 |
| --- | --- | --- |
| **区分度缺失** | 两种不同状态输出一样 | B24（日报两种「空」）、**B25（trace 两种「没观察」）**、B23（同一失败三种表达——反向） |
| **静默丢弃** | 数据消失但不报错 | B2（evidence 截断）、**B20（匹配失败→退回默认值）**、以及设计层的先验依赖 |
| **静默编造** | 用假值顶替缺失数据 | B3（零填充）、B19（重复计数）、设计层的「未检测到异常」当「健康」 |
| **归因错误** | 把自己的局限记在数据头上 | B5（SNR）、B4（分段） |
| **想当然的机制** | 听起来合理但方向/范围不可控 | B1（展宽似然）、B6（未校准即默认可信） |
| **检测过宽** | 为「需要确认」而设的检测器命中过多 | B11 / B12（数字检测）、**B21（不变量拦了反方向）** |
| **接线错误** | 写出来了但**从未被执行过** | B13–B18、**B22**（枚举映射 / 节点注册 / 上下文传递 / 类型 API / 调用约定 / 状态匹配 / **参数透传**） |

**注意前三类在本项目的设计文档里都有对应的防守**：

- 静默丢弃 → `PlanResult` 要求先验依赖必须被处置
- 静默编造 → 健康模块禁止「未发现异常」，特征契约加 `unavailable`
- 归因错误 → 区分「观测事实 / AI 推测 / 拟人化设定」

> **同一批失败模式在设计和实现两个层面各出现了一次。**
> 这说明它们不是偶然的编码失误，而是**需要系统性防守的认知陷阱**。

### 3.2.1 两类不同性质的缺陷

上面六类可以归为两半，它们的**探测手段完全不同**：

| | 算法层（B1–B12, B19） | 接线层（B13–B18） |
| --- | --- | --- |
| 位置 | 概率计算、检测器、检索 | 枚举映射、节点注册、上下文传递 |
| 有业务逻辑吗 | 有 | **没有 —— 看起来最「显然」** |
| 靠什么发现 | 机制性断言（单调性 / 不变性 / 边界） | **冒烟测试 + 静态类型检查** |
| 失败表现 | 数值微妙错位 | 要么完全不可用，要么**全部退化成同一条兑底** |
| 典型误判 | 「测试过了应该没事」 | 「写完了就是对的」 |

> **两类都需要主动检查，但检查方式不同。**
> 算法层要构造机制性断言（数值不会自己报错）；
> 接线层要写最基础的冒烟测试（能不能构建起来）并跑类型检查（枚举名 / 属性名）。
>
> B13 甚至是 **pyright** 发现的 —— 降级路径平时不跑、测试很难覆盖，
> 而类型检查恰好能拓到这类拼写级错误。

### 3.3 一个反直觉的观察

**B1 和 B6 都是「我的实现比设计更自信」**：

- B1：质量差时反而给出更极端的判断
- B6：每次判断都落进「高置信」档

两者的方向都是**过度自信**——恰是项目最想避免的失败模式。

> **「不声称超出证据的确定性」这个原则，不仅文档里要写，实现里要有断言守。**

## 5. 维护约定

| # | 规则 |
| --- | --- |
| M1 | 每个缺陷必须**附回归测试**。没有测试的修复不算修完。 |
| M2 | 必须记录**实测数字**（`0.269 → 0.334 → 0.411`），不要只写「行为异常」。 |
| M3 | 必须写**可迁移的教训**，而不只是「我改了什么」。 |
| M4 | 区分「设计错」「实现错」「测试写错」——**混为一谈会掩盖真实问题**。 |
| M5 | 静默缺陷（不报错）单独标记——它们最危险。 |
| M6 | 若同一失败模式在设计与实现各出现一次，**合并成一条规律**（见 §3.2）。 |
| M7 | **验证必须确认対象正确**（见 §5.1）。 |

### 5.1 一个关于「验证」本身的教训

在接入真实模型时，静态检查报了 `tests/test_memory_store.py` 的两处问题。
我核验了那个文件 —— 干净、测试通过、检查器对该文件 0 errors ——
于是判定为「陈旧快照」，并在**连续五个回合**里反复如此确认。

**结果证明：发现是真的，但不在我一直在查的那个文件里。**
它们实际在 `tests/test_contracts.py`（同样的 `dict(...)` 写法与 `**` 解包），
而我把文件名映射错了，之后每一次「核验」都在强化这个错误假设。

更糟的是：**我的核验方式本身看似很严谨** —— 跑了检查器、对了行号、
看了文件内容、跑了测试。但**每一步都针对错误的文件**，所以结论稳定地错。

> **看起来严谨的核验，如果対象错了，比不核验更危险** ——
> 因为它会产生「已经查过了」的确定感。

修正后的做法：

| # | 规则 |
| --- | --- |
| V1 | 核验前先**回引原文确认文件名与行号**，不凭记忆或转述 |
| V2 | 若发现「报告位置与实际不符」，先怀疑自己的映射，**不要先怀疑工具** |
| V3 | 整个项目跑一遍检查器（`pyright` 无参数），再按文件分组看分布 |
| V4 | 当同一发现反复出现时，**换一种探测手段**（如全局 grep 该模式），而不是重复同一种 |

当时若跑一句全局搜索就能立刻定位：

```bash
# 找所有“把字典解包进构造函数”的地方（真正的缺陷形态）
grep -rn "= dict(" tests/
```

它会同时输出两个文件 —— 而我一直在看的那个是已经修好的那个。
