# 10 · 需求与设计自审报告

> 审查方法：**逐条核实，不凭记忆**。所有结论都有 grep / ls 证据。
> 目的：找出可以优化的地方，包括矛盾、缺失、过度设计与未验证假设。

## 0. 总评

设计在**表达力**上是完整的，但审查暴露出一个贯穿性问题：

> **多处出现了「高级概念先落地、支撑机制后补」的模式。**

具体表现为四类：

| 类型 | 数量 | 例 |
|---|---|---|
| A. 自相矛盾 / 理由不成立 | 2 | `CHAT` vs `MEMORY_QUERY` 的区分理由实际不存在 |
| B. 引用了不存在的产物或方法 | 3 | `plan.task()`、`state["_wave"]`、`data/priors/` |
| C. 高级概念缺实现机制 | 2 | 先验依赖只有声明没有接口 |
| D. 关键假设未验证 | 2 | 整个阈值体系建立在 LLM 自报置信度上 |

这不是致命的——但**面试官如果能查出 A 和 B，杀伤力很大**，因为它们是「文档与代码不一致」，
会直接质疑项目的严谨性。

## 1. P0：矛盾与不成立的论证（必须修）

### A1 · `CHAT` 与 `MEMORY_QUERY` 的区分理由**不成立**

**文档声称**（`docs/01` §5.2、`docs/09` §3）：

> `CHAT` 与 `MEMORY_QUERY` 走同一条链路，但分开——因为后者有**强制的拒答约束**
> （检索不到必须说「没有记录」）且禁止把系统推断写回记忆。

**核实结果**：`retrieval_note` 是 `ContextInjectionBlock` 的字段，**带默认值**：

```python
# app/schemas/memory.py:369
retrieval_note: str = Field(
    default="以上为检索到的记录。未在其中的信息即为没有记录，不要推测或使用常识补全。"
)
```

而 `ContextInjectionBlock` 被 `companion_agent` 统一使用——**所有意图都带这条约束，包括 `CHAT`**。

**所以「后者有强制拒答约束」是错的：两者都有。** 这条区分理由不成立。

**影响**：这是本项目「意图边界按下游行为差异划分」这一核心论点的**唯一举证**。
举证不成立，整个论点就悬空了。

**修法（二选一）**：

| 方案 | 内容 | 代价 |
|---|---|---|
| ① **改论证**（推荐） | 把区分理由改为真实存在的差异：`MEMORY_QUERY` 的 `top_k` 更大、拒答阈值更严、**且禁止把本轮推断写回记忆** | 小，需补一张参数差异表 |
| ② **合并两者** | 合并为 `RECALL`，用 slot `strict: bool` 表达严格程度 | 违背「两个意图下游行为一致就该合并」的判据——参数差异不构成行为差异 |

**推荐 ①**。因为「禁止把本轮推断写回记忆」是**约束差异**（行为差异），不是参数差异，
判据仍然成立，只是举证要换成它。

### A2 · `RECORD_EVENT` 的写入时机与守卫归属**自相矛盾**

**文档现状**（`docs/01` §2.2）同时表达了三件互相冲突的事：

```
RECORD_EVENT ──► memory_writer（执行 + 明确反馈）        ← 直接写
response_guard → tts_output → memory_writer → END        ← 公共尾部也写
> RECORD_EVENT 走独立路径，不经过 guard                  ← 绕过守卫
```

**矛盾点**：

1. `RECORD_EVENT` 到底是**自己写**，还是**产出候选由尾部 `memory_writer` 统一写**？
2. 如果自己写，公共尾部的 `memory_writer` 会不会**重复写**？
3. 如果绕过 `response_guard`，那条「已记录：…」的确认文本**完全不受守卫约束**——
   这与「prompt 是建议，节点是强制」原则冲突。

**更严重的连带问题**：`docs/01` §2.3 的复合示例里，`T1 = record_event` 是**子任务**，
而尾部又有 `memory_writer`。同一个语义在两处有**两套执行路径**，且语义不同。

**修法（推荐）**：

> **统一为「子任务只产出候选，`memory_writer` 是唯一写入点」。**

| 路径 | 行为 |
|---|---|
| `RECORD_EVENT`（快路径） | 产出 `candidate_memory` → 尾部 `memory_writer` 写入 → 确认文本由 guard 检查 |
| `record_event`（子任务） | 同上，语义完全一致 |
| 执行 + 明确反馈 | 保留在**措辞层**：写入后明确回显「已记录：…。记错了请告诉我」 |

好处：写入只有一个入口（便于审计与不变量检查）、守卫覆盖全部输出、两条路径语义统一。

### A3 · 文档用了契约中**不存在**的方法与字段

| 位置 | 用了什么 | 实际 |
|---|---|---|
| `docs/01` §7.1 | `plan.task(tid)` | `Plan` 无 `task()` 方法（只有 `prior_dependencies()` / `max_parallelism` / `serial_depth`） |
| `docs/01` §7.1 | `state["_wave"]` | `AgentState` 无此字段，`Plan` 也无 wave 游标 |

**修法**：给 `Plan` 补 `task(task_id)` 与 `ready_tasks(wave_idx)` 方法；
`AgentState` 补 `current_wave: int`，或把 wave 游标放进 `Plan`。

> 这类问题本身很小，但**「文档里的代码跑不通」在面试现场演示时是硬伤**。

## 2. P1：高级概念缺实现机制

### C1 · 先验依赖**只有声明，没有接口**

**文档声称**（`docs/01` §6.2）：

> T3 的结论应**上调 T2 中 `door_attention` 的场景先验**，因此二者不能并行。

**核实结果**——`Dependency` 只有三个字段：

```python
class Dependency(BaseModel):
    on_task_id: str
    kind: DependencyKind     # data / prior / resource
    note: str                # 说明，供审计
```

**没有定义「上调多少」「如何传递」「谁来应用」**。而 `SubTaskResult.output` 是无类型的 `dict`。

**这是本次审查最值得修的一处**：先验依赖是「任务分解」这一能力最核心、最出彩的论点，
但它目前**只是一个名词**，落不了地。

**修法**：新增 `PriorAdjustment` 契约：

```python
class PriorAdjustment(BaseModel):
    """一个子任务产出的、对其他子任务先验的调整量。"""
    target_task_id: str
    target_field: str                 # 如 "scene_prior"
    target_key: str                   # 如 "door_attention"
    operation: Literal["scale", "delta", "set"]
    value: float
    rationale: str                    # 必须说明依据，供审计
    confidence: float
```

并规定：`PRIOR` 依赖的产出方**必须**在 `SubTaskResult.output["prior_adjustments"]`
中给出该结构；应用方在开始执行前读取并应用到自己的先验表；
`PlanResult.applied_prior_dependencies` 记录实际生效项。

**这样「先验依赖」才从名词变成了可测试的机制**——评测可以断言
「T3 产出的 adjustment 确实改变了 T2 的后验」。

### C2 · 时间表达解析**没有归属节点**

`RouteSlots.time_range` 是 `str | None`（如「上个月」），
但 `MemoryEvent.valid_from/valid_to` 是 `datetime`。

**谁负责把「上个月」转成 `[上月1日, 上月30日]`？没有定义。**

而 `docs/04` §3.3 把「时间范围重叠」定为冲突判定的**必要条件**——
解析错了，冲突判定就全错。

**修法**：在 `understand_input` 的职责中显式加入**时间归一化**，
并把它列为可独立评测项（时间解析准确率）。这是一个被漏掉的、影响核心正确性的子能力。

## 3. P1：关键假设未验证

### D1 · 整个阈值体系建立在 **LLM 自报置信度**上

`INTENT_POLICIES` 的 `min_confidence` 取 0.35–0.6，意图路由依赖 LLM 输出 confidence。

**问题**：LLM 自报置信度**普遍未校准**——同一个模型可能对不同难度的问题都给 0.9，
也可能对简单问题给 0.4。一套基于 0.35/0.4/0.5/0.55/0.6 的精细阈值，
如果输入本身未校准，**这些阈值就是装饰**。

**这是设计里最大的隐藏假设**，而它没有被写进任何一篇文档。

**修法（三选一，按成本排序）**：

| 方案 | 内容 | 成本 |
|---|---|---|
| ① **分箱校准** | 在评测集上画 reliability diagram，用 isotonic / Platt scaling 把自报置信度映射为校准置信度，**再**用它做阈值判定 | 中，且可评测（ECE 指标） |
| ② **多采样一致性** | 同一输入采样 k 次，用投票一致性作为置信度。代价是 k 倍成本 | 高 |
| ③ **改用 logprobs / 枚举打分** | 不用自然语言 confidence，改为对每个意图候选打分并归一化 | 中 |

**推荐 ①**：它本身就是一个可展示的技术点（**置信度校准 + ECE 评测**），
且直接解决「阈值是否可信」这个根本问题。

**面试价值**：主动说出「我知道 LLM 自报置信度不可信，所以我做了校准并报告了 ECE」，
比设置一堆没有依据的阈值强得多。

### D2 · 引用了**不存在的数据产物**

| 声称 | 实际 |
|---|---|
| `data/priors/catmeows_stats.json`（`docs/03` §3.5） | **目录不存在** |
| 「用文献中的 7 情境分布补充」（`docs/03` §9 L2） | **没有这个分布的数据来源**；我引用的文献只提供了上下文类别的存在性，未提供可直接使用的概率分布 |

**修法**：

1. 要么真去下载 CatMeows（Zenodo 公开）并计算统计量，产出 `catmeows_stats.json`
2. 要么**诚实降级**：把先验标记为「待构建」，当前仅使用**场景先验**
   （用户描述的场景），并在 `limitations` 中说明「群体先验尚未接入」

**推荐 2 起步、1 作为后续**。因为 2 是诚实的，且不阻塞主链路；
而 1 是一个独立的数据工程任务，可以作为一个明确的 TODO 列出来。

## 4. P2：过度设计与范围问题

### E1 · 规划层是**面试驱动**，不是产品驱动（诚实标注）

**必须承认**：我在 `docs/09` 推荐加规划层的理由是「任务分解是面试高频考点」。

**但如果只看产品**：猫咪陪伴场景里，一句话包含 3 个子任务的复合请求**频率很低**。
绝大多数输入是单意图的。为一个低频场景引入
`planner` + `Send` fan-out + wave 调度 + 计划校验 + 结果合并 + 部分失败处理，
**复杂度不低，产品收益有限**。

**这不是说不该做**——面试项目的目标函数和真实产品不同，这本身是合理的。
但**必须在文档里标注清楚**，否则会被问「你这个 planner 的调用占比是多少」而答不上来。

**修法**：
1. 在 `docs/01` 与 `docs/09` 标注：`规划层为能力展示引入，实际触发率预期 <10%`
2. 在评测中**实际测量复合意图占比**（这本身也是一个数据点）
3. 明确降级路径：若 planner 失败或超预算 → 取第一个子意图走快路径

### E2 · 无**成本与延迟预算上限**

复合路径约 4s + 多次 LLM 调用。当前设计**没有预算约束**：
没有单请求 token 上限、没有延迟上限、没有超预算的降级策略。

**修法**：定义 `RequestBudget { max_tokens, max_latency_ms, max_subtasks }`，
超限时按 `optional` 标记裁剪子任务（优先保留非 optional 的）。

### E3 · 「多用户隔离」在**无鉴权**时不可执行

`docs/06` 说「只做数据层隔离，不做完整 auth」。但 `user_id` 若由客户端提供，
**任何人都能伪造 `user_id` 读别人的宠物记忆**——隔离主张直接失效。

**修法（最小可行）**：至少一个**不依赖客户端自报**的身份来源。
哪怕是最简的签名 token / 会话 cookie，也比 `user_id` 直接从请求体读强。
或者诚实表述为「**隔离是存储层的正确性设计，但端到端强制依赖鉴权，本期未实现**」。

### E4 · 会话生命周期未定义

`MemoryLayer.SESSION` 说「会话结束即失效」，但**何时算结束**？
TTL 多长？跨会话的「最近情绪」是否保留？未定义。

## 6. 审查方法反思

这次审查之所以能发现问题，靠的是**grep 核实而非凭记忆**。
其中最隐蔽的两条（A1、A2）都是「文档之间互相引用，但都没回去验证前提」。

**建议固化为流程**：每写完一篇文档，回头 grep 一遍它引用的所有产物、方法、字段，
确认存在且语义一致。这可以作为一个 skill 或检查清单。

**具体的可执行检查**：

```bash
# 契约层方法是否都存在
grep -o 'plan\.[a-z_]*(' docs/*.md | sort -u
grep -n 'def ' app/schemas/plan.py

# 文档引用的数据产物是否存在
grep -o 'data/[a-z/]*\.[a-z]*' docs/*.md | sort -u | xargs -I{} ls {} 2>&1

# 文档引用的字段是否在契约里
grep -o 'state\["[a-z_]*"\]' docs/*.md | sort -u
```
