# 11 · 陪伴产品化设计

> 本文档回应一个质疑：**当前设计能满足陪伴情绪价值吗？**
>
> 答案是「不能」。本文档定义缺失的场景根基，并据此重做优先级。

## 0. 问题诊断

### 0.1 根本矛盾：诚实性与情感价值的张力

前面所有文档都在强化诚实性——守卫、拒答、置信度、证据链、局限说明、覆盖率门禁。
这些都对，**但它们与情感陪伴是反向的**：

```
用户想听到的：   「团团当然想你啦」
当前设计产出的： 「可能是想让你开门（置信度 0.68）。仅凭叫声无法确定真实意图，
                若伴随持续焦躁建议就医观察。」
```

第二句在陪伴语境下是**冷场的**。

**根源不是诚实性做多了**，而是**把两类需求用同一套严谨度处理了**：

| 用户在做的事 | 真实需求 | 应有严谨度 |
|---|---|---|
| 「团团今天怎么不理我」 | **求安慰** | 温度优先 |
| 「它刚才为什么一直叫」 | **求答案** | 证据优先 |

### 0.2 四个产品级缺口

| # | 缺口 | 后果 |
|---|---|---|
| G1 | **从未定义用户场景** | 功能优先级全靠拍脑袋 |
| G2 | **100% 被动响应** | 用户不来，产品不存在。陪伴产品的核心机制缺失 |
| G3 | **拟人化无明示机制** | 用户会怀疑「这是不是猫的真实意思」→ 把扮演包装成事实 |
| G4 | **冷启动期无留存理由** | 数据飞轮要 21 天，前 21 天凭什么留下用户 |

### 0.3 诊断：这是两个产品被焊在一起

```
A. 高可信度行为/健康分析工具
   → 现有设计非常契合 ✅

B. 情感陪伴产品
   → 几乎没覆盖 ❌
```

用 A 的严谨度要求 B，结果 B 的体验被 A 的约束杀死。

## 1. 场景定义（补上 G1）

**聚焦两个场景，其余明确排除。**

### 场景 S1 · 想猫时（分离焦虑）

| 维度 | 内容 |
|---|---|
| 触发 | 上班间隙、午休、下班前、出差在外 |
| 心理状态 | 想它、轻微担心、需要确认它好好的、需要被连接 |
| 行为特征 | **高频、短时长、打开是为了「看一眼」而非「问问题」** |
| 成功标准 | 打开后 30 秒内获得情绪满足 |

**硬约束：系统没有摄像头，无法知道猫此刻在做什么。**

这条约束决定了 S1 的价值**不能是「实时看到它」**，只能是：

| 真实价值 | 实现方式 |
|---|---|
| **情感确认** | 「它的近况有人替你记着」——时间线 + 变化提醒 |
| **投射出口** | 你想它，有个地方可以说，且会被认真回应 |
| **累积记录** | 每天一张照片 → 时间线 → 日后翻回来 |
| **被连接感** | 主动触达（§4） |

**因此 S1 的核心功能是「记录 + 时间线 + 主动回顾」，不是聊天。**

### 场景 S2 · 看不懂它时（求解释）

| 维度 | 内容 |
|---|---|
| 触发 | 猫叫得奇怪、行为反常、怀疑不舒服 |
| 心理状态 | 困惑、轻微焦虑、想确认「要不要紧」 |
| 行为特征 | 低频、高意图、愿意上传音频/描述 |
| 成功标准 | 得到可理解的解释 + 知道下一步该做什么 |

**这是现有设计最强的部分**（`docs/03` 行为解释器），主要补**低摩擦入口**与**解释后的情绪收尾**。

### 明确排除

| 场景 | 理由 |
|---|---|
| 实时监控 / 远程看家 | 需要硬件，非软件可解 |
| 宠物社交 / 内容社区 | 是完全不同的产品 |
| 电商 / 问诊撮合 | 商业模式另论 |

## 2. 场景 S1 设计：想猫时

### 2.1 核心动作：记录一个瞬间（MOMENT）

**当前设计的 `RECORD_EVENT` 门槛太高**——它要求用户「说一件事」。
S1 需要的是**更低门槛的动作**：

```
用户：上传 1 张照片（可选配一句话）
系统：不需要用户描述，自己抽取「这一瞬间是什么」
```

**为什么门槛是关键**：用户想猫时是情绪状态，不想打字、不想被问问题。
每多一个输入字段，转化率就掉一截。

| 项 | 设计 |
|---|---|
| 输入 | 1 张照片 / 1 段短视频 + **可选**一句话 |
| 系统抽取 | 场景标签（睡觉 / 玩耍 / 进食 / 窗台 / 与人互动 / 其他）、可见情绪、外貌一致性检查 |
| 输出 | `Moment` 一条，进时间线 |
| 不做 | 不强制用户填描述、不要求选择分类、不弹确认框 |

### 2.2 时间线（MomentsFeed）

```
MomentsFeed
  ├─ 按时间倒序
  ├─ 自动归类（场景 tag）
  ├─ 支持「上周 / 上个月」聚合
  └─ 周回顾：自动生成「团团这周」
```

**周回顾是情绪价值的密度峰值**——它把碎片记录变成叙事。
且它恰好复用规划层已有的 `aggregate_query` 子任务类型（见 `docs/01` §2.3）。

### 2.3 变化提醒（轻量版 Track B）

```
「最近它趴窗台的次数变多了」
「这周它比上周叫得少一些」
```

**注意**：这类提示是**中性的观察**，不是健康告警。措辞必须温和且非诊断。
数据不足时**不输出**（而非输出「无变化」）。

### 2.4 关系近况摘要（"它最近怎么样"）

S1 最常见的输入其实是**「团团最近怎么样」**这类宽泛问题。

**当前设计处理不了它**——`MEMORY_QUERY` 是检索"某条记忆"，而这需要的是**聚合 + 叙事**：

```
「团团最近怎么样」
  → 聚合：近 7 天的记录数、场景分布、行为变化
  → 对比：与再前 7 天比较
  → 叙事：生成一段有温度的近况描述
  → 素材：全部来自真实记录（不可编造）
```

这是 S1 的**旗舰交互**，也是「记忆系统」在这条产品线里的真正价值兑现点。

## 3. 场景 S2 设计：看不懂它时

现有行为解释器保留，补三件事：

### 3.1 低摩擦入口

| 入口 | 说明 |
|---|---|
| 录音直传 | 首页一个按钮，录 5 秒即得解释，不填任何表单 |
| 常见行为速查 | 「踩奶」「呼噜」「半夜跑酷」等高频疑问，直接给通用解释 + 个性化补充，**不要求上传** |
| 从记录里问 | 在时间线某条记录上点「它当时怎么了」→ 带上下文进入解释 |

### 3.2 解释后的情绪收尾

当前输出以 `limitations` 结尾——**诚实但冷**。应补一段**可操作的温暖收尾**：

```
❌ 结尾：「仅凭叫声无法确定真实需求；若伴随持续焦躁，建议就医观察。」

✅ 结尾：「大概率是想让你陪它玩一会儿。今晚试试拿逗猫棒，
        如果它还是这样叫，再看是不是别的原因。」
```

**注意**：温暖收尾**仍然不许编造**——建议必须由后验结果推出，不是随口安慰。
`response_guard` 检查建议是否与 top candidate 一致。

### 3.3 与 S1 的衔接

S2 得到的解释**应当作为一条记录沉淀进时间线**——
这样「看不懂它」的困惑会变成「读懂了它」的积累，反哺 S1 的情感价值。

## 4. 主动触达引擎（补 G2）

**陪伴产品的核心机制是主动性。** 之前把「主动提醒」评为「可考虑」是错误判断。

### 4.1 触发条件

| 类型 | 条件 | 内容示例 |
|---|---|---|
| **互动空窗** | 超过 N 小时未互动 | 「今天还没听到你的消息，团团一切都好，记录还在」 |
| **记录积累** | 本周 ≥3 条记录 | 周回顾「团团这周」 |
| **模式变化** | 某场景频率显著变化 | 「最近它趴窗台的次数变多了」 |
| **健康到期** | 疫苗 / 驱虫到期 | 「团团的疫苗该补了」 |
| **异常叫声** | 连续多次异常叫声模式 | 「刚才它叫得比较频繁，要不要看看？」 |

### 4.2 防打扰（留存的关键）

**推送过多会被卸载**，这是主动触达最大的风险：

| 规则 | 值 |
|---|---|
| 每日推送上限 | ≤ 2 条 |
| 静默时段 | 用户配置（默认 22:00–08:00） |
| 连续忽略降频 | 连续 3 次未互动 → 自动降频至每日 1 条 |
| 连续忽略停推 | 连续 7 次未互动 → 暂停主动推送，需用户主动唤醒 |
| 一键关闭 | 必须提供，且关闭后不反复引导重开 |

### 4.3 空窗推送的诚实边界

**不能假装知道猫在干什么。** 正确的措辞是：

```
✅ 「今天还没听到你的消息。团团最近 3 天的记录都挺好的。」
   → 陈述的是【系统知道的】，不是【猫此刻的状态】

❌ 「团团今天很想你哦，一直在门口等你。」
   → 编造事实。系统不知道这些。
```

这条边界必须在 `response_guard` 里强制，`InteractionMode.COMPANION` 也不例外。

## 5. 对话分轨（核心机制改造）

### 5.1 InteractionMode

```python
class InteractionMode(str, Enum):
    COMPANION = "companion"
    """情绪轨：温度优先。只讲已知事实，温暖措辞，不主动暴露不确定性。"""

    ANALYSIS = "analysis"
    """分析轨：证据优先。完整呈现证据链、置信度与局限。"""
```

### 5.2 判定方式：**规则特征优先，不用 LLM 自报置信度**

这恰好规避了自审报告中的 D1 问题（LLM 置信度未校准）：

| 信号 | 倾向 |
|---|---|
| 上传音频（`CAT_MEOW`） | ANALYSIS |
| 含疑问词（为什么 / 怎么回事 / 是不是） | ANALYSIS |
| 含情绪词（想你 / 难过 / 担心 / 好久没） | COMPANION |
| 短会话高频（<30 秒，日多次） | COMPANION |
| 无明确诉求的问候 | COMPANION |

**默认 COMPANION，倾向 ANALYSIS 需明确信号。** 理由：陪伴产品里误判为分析轨的代价
（冷场、说教）高于误判为情绪轨（少给一次证据，用户会追问）。

### 5.3 守卫分模式配置

| 检查项 | COMPANION | ANALYSIS |
|---|---|---|
| 禁止编造事实 | ✅ 保留 | ✅ 保留 |
| 过度确定性 | 放宽（不说概率是刻意的） | ✅ 严格 |
| 必须给替代解释 | ❌ 不要求 | ✅ 要求 |
| 必须给 `limitations` | ❌ 不要求 | ✅ 要求 |
| 建议须与 top candidate 一致 | ✅ | ✅ |
| 拟人化明示（§6） | ✅ 必须 | ✅ 必须 |

**关键**：两轨都诚实，区别在**表达策略**而非**事实标准**。

> 情绪轨不是「可以编」，而是「**只讲已知的正面事实，且不主动补免责声明**」。

## 6. 拟人化明示（补 G3）

### 6.1 问题

用户看到「团团说：本喵饿了」时会怀疑这是不是猫的真实意思——
**这就是把扮演包装成了事实**，违反 `docs/00` §3.3 自己定的三层分离。

### 6.2 输出结构强制分层

```jsonc
{
  "fact_layer": {
    "content": "团团的档案里记录着它喜欢趴窗台；今天下午你在 15:20 记录了一张它趴窗台的照片",
    "sources": ["memory:evt_123", "moment:m_456"]
  },
  "companion_layer": {
    "is_roleplay": true,
    "roleplay_notice": "以下为团团角色扮演，不是它的真实想法",
    "text": "本喵今天在窗台守了你一下午呢"
  }
}
```

**强制规则**：

| # | 规则 |
|---|---|
| R1 | `is_roleplay` 与 `roleplay_notice` 为**必填**，不可省略 |
| R2 | `companion_layer.text` 中的每个事实性断言**必须能追溯到 `fact_layer.sources`** |
| R3 | UI **必须**对两层做视觉区分（不同样式/图标/标注），不可混淆呈现 |
| R4 | `roleplay_notice` 不可被 LLM 改写或省略 |

**R2 是防止扮演层夹带私货的关键**——「本喵今天在窗台守了你一下午」只有在
`fact_layer` 里真有对应记录时才成立。

## 7. 数据模型新增

| 实体 | 用途 | 备注 |
|---|---|---|
| `Moment` | 一条瞬间记录 | 照片/视频 URL + 场景 tag + 可见情绪 + 外貌一致性结果 |
| `MomentScene` | 场景枚举 | 睡觉 / 玩耍 / 进食 / 窗台 / 与人互动 / 其他 |
| `TimelineDigest` | 周/月回顾 | 汇总统计 + 生成叙事 + 素材引用 |
| `ChangeObservation` | 变化观察 | 中性观察，非健康告警 |
| `ProactiveMessage` | 主动消息 | 类型 + 触发条件 + 发送状态 + 用户反馈 |
| `InteractionMode` | 对话模式 | 见 §5.1 |
| `CompanionResponse` | 分层输出 | `fact_layer` + `companion_layer` |

**对象存储**：照片/视频需要对象存储，当前设计未覆盖。需评估直接存文件系统还是接 OSS。

## 8. 优先级重排（诚实调整）

之前 `docs/06` 的优先级是**面试导向**的。按真实场景重排：

### 8.1 上调

| 能力 | 原优先级 | 新优先级 | 理由 |
|---|---|---|---|
| **记录动作 + 照片时间线** | 未列入 | **P0** | S1 的核心，无此则产品不成立 |
| **对话分轨（情绪/分析）** | 未列入 | **P0** | 决定 S1 体验成败 |
| **主动触达引擎** | P3 | **P0** | 陪伴产品的核心机制 |
| **关系近况摘要** | 未列入 | **P0** | S1 旗舰交互 |
| 周/月回顾 | 未列入 | **P1** | 复用 `aggregate_query`，成本低 |

### 8.2 下调

| 能力 | 原优先级 | 新优先级 | 理由 |
|---|---|---|---|
| **规划层 planner** | P2（已实现设计） | **P2**（不变，但降期望） | 复合请求在 S1/S2 中都罕见。保留设计，实现可延后 |
| **消融实验 / 参数敏感性** | P1 | **P2** | 面试向，不影响产品可用性 |
| **健康分诊** | 已定本期 Track A | **P2** | 在 S1/S2 中触发频率极低 |
| TTS | 本期 | **P1** | 在 S1 中价值提升（"听到它的声音"有情绪价值） |

> **注意 TTS 的重新评估**：之前建议砍掉，但 S1 场景下「听到它的声音」有真实情绪价值。
> 但必须是**用户自己录制/上传的猫叫**，而不是合成的假猫叫——合成会强化 G3 的欺骗问题。

### 8.3 修正后的路线

```
P0（产品成立的最小集）
  1. Moment 记录 + 时间线
  2. InteractionMode 分轨 + 守卫分模式
  3. CompanionResponse 分层输出（拟人化明示）
  4. 主动触达引擎（含防打扰）
  5. 关系近况摘要

P1（体验强化）
  6. 周/月回顾
  7. 变化提醒（轻量 Track B）
  8. S2 低摩擦入口 + 情绪收尾
  9. TTS（用户自录猫叫）

P2（可信度与工程）
 10. 行为解释的证据链打磨
 11. 评测跑批 + 不变量 CI（docs/06 的 P0，此处降级）
 12. 健康分诊 Track A

P3（可延后）
 13. 规划层实现
 14. 消融实验 / 参数敏感性
```

**评测跑批虽然降到 P2，但它仍是「含金量」的核心**——
只是对**产品可用性**不是前置条件。两者目标不同，不必强行统一。
