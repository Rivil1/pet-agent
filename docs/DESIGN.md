# 1. 产品定义

## 1.1 一句话定位

> 以**一只真实存在的猫**为长期身份锚点，**把主人对这只猫的经验记下来、在用得上时调出来**，
> 并在此之上提供拟人化陪伴、行为解读与健康监测。

关键在于「**真实**」：用户不是跟一个泛泛的猫娘聊天，而是跟自己那只猫。

### 知识对象：主人的经验，**不是**猫的心思

**这是本项目最重要的定位约束，它决定了上面每一个功能的形态。**

| | 知识对象 | 可验证？ |
| --- | --- | --- |
| ❌ | 猫的意图 / 内心状态 | **不可验证** —— 文献显示人类从单次叫声判断情境的准确率为 26–40%，而三分类随机水平是 33%（[16 §4](16-model-selection.md)） |
| ✅ | **主人对这只猫的经验** | **可验证** —— 主人就是权威，且记录的计数可直接与数据库逐条核对 |

系统**不声称知道猫在想什么**，它声称的是「我记得你上次是怎么处理的」——
而这个声称是可以被核对的。

因此 Agent 的角色是**辅助**：档案员 + 检索者 + 归纳者，**不是判断者**。
主人是专家（关于自己的猫）；系统的价值在于主人自己做不到的三件事：

- **关联**：「这次和三个月前那次很像」（声学 + 动作 + 情境的相似度）
- **归纳**：「门口叫这种情况，你记了 5 次，4 次开门就好了」
- **时间**：「上个月也是这个时候」

**这个定位还带来一个工程上的好处：评测变成可能。**
核心输出「5 次里 4 次」是一个能与数据库逐条核对的事实，因此**可机械验证**——
这在「判断猫的意图」的框架下不可能（没有 ground truth）。

> ⚠️ **但它不解除一个风险**：主人自己的经验可能是错的。
> 猫有慢性疼痛而表现为频繁叫 + 蹭腿时，主人很可能记成「撒娇，摸它就好」，
> 系统会忠实地学会并**强化**这个错误。所以健康红线必须**独立且优先**（见 §5）。

## 1.2 场景（产品根基）

**没有场景定义，功能优先级就是拍脑袋的。** 因此场景先于功能。

### S1 · 想猫时（分离焦虑）

| 维度 | 内容 |
| --- | --- |
| 触发 | 上班间隙、午休、下班前、出差在外 |
| 心理状态 | 想它、轻微担心、需要确认它还好、需要被连接 |
| 行为特征 | **高频、短时长、打开是为了「看一眼」而非「问问题」** |
| 成功标准 | 打开后 30 秒内获得情绪满足 |

**硬约束：系统没有摄像头，无法知道猫此刻在做什么。**

因此 S1 的价值**不是「实时看到它」**，只能是：

| 真实价值 | 实现方式 |
| --- | --- |
| 情感确认 | 时间线 + 变化提醒，「它的近况有人替你记着」 |
| 投射出口 | 你想它，有个地方可以说，且被认真回应 |
| 累积记录 | 每天一张照片 → 时间线 → 日后翻回来 |
| 被连接感 | 主动触达 |

**结论：S1 的核心是「记录 + 时间线 + 主动回顾」，不是聊天。**

### S2 · 看不懂它时（求解释）

| 维度 | 内容 |
| --- | --- |
| 触发 | 猫叫得奇怪、行为反常、怀疑不舒服 |
| 心理状态 | 困惑、轻微焦虑、想确认「要不要紧」 |
| 行为特征 | 低频、高意图、愿意上传音频 |
| 成功标准 | 得到可理解的解释 + 知道下一步做什么 |

S2 的核心是**行为解释**与**视觉评估**。

### 明确排除

| 场景 | 理由 |
| --- | --- |
| 实时监控 / 远程看家 | 需要硬件 |
| 宠物社交 / 内容社区 | 不同产品 |
| 电商 / 问诊撮合 | 模式另论 |
| 犬类等其他物种 | 本期只做猫 |

## 1.3 四个核心能力

| 能力 | 用户动作 | 系统产出 | 服务场景 |
| --- | --- | --- | --- |
| **身份锚定** | 上传 3–5 张照片 + 补充描述 | 结构化宠物档案（含必须保留特征） | S1/S2 |
| **记录与回顾** | 上传照片/视频（**可选**配一句话） | 时间线 + 周期报告 + 近况摘要 | **S1** |
| **陪伴对话** | 文字 / 语音 | 符合角色设定、引用真实记忆的回复 | S1 |
| **行为解释** | 上传叫声 + 补充场景 | **候选情境排序** + 可追溯证据 + 后验置信度 | **S2** |
| **视觉与健康** | 上传照片/视频、记录指标 | 场景标签 / 疼痛筛查 / 呼吸频率 + 分诊建议 | S2 |

> **注意用词**：行为解释产出的是**候选情境（context）**，不是「候选意图」。
> 情境可被用户确认（「对，当时我在开罐头」），意图不可验证。
> 用不可验证的目标做监督学习，评测无从谈起。

## 1.4 非目标

- ❌ 兽医诊断、判定疾病名称、用药建议、出具诊断书
  （健康模块只做**监测与分诊**；依据《动物诊疗机构管理办法》第二/五/十九条）
- ❌ 猫咪个体身份鉴定 / 找回走失猫
- ❌ 实时双工语音通话（TTS 为单轮回复式）
- ❌ 猫语词典 / 逐句翻译
- ❌ 通用宠物助手（本期只做猫）

## 1.5 四条诚实性边界

这四条不是免责声明，而是**产品可信度的来源**。任何一条被突破，
整个项目就从「AI 系统」退化成「LLM 包装」。

### 边界 1 · 外观一致性校验 ≠ 个体身份鉴定

向量相似度只回答「这张新照片和档案里的猫**外观是否相符**」，
**不**回答「这是不是团团」。

原因：CLIP 类通用图像 embedding 捕捉的是**类别语义**（橘猫/圆脸/短毛），
不是**个体辨识特征**。两只不同的橘猫余弦相似度同样可能很高。
猫咪个体再识别需要专门训练的模型与标注数据，市面无可用现成服务。

**因此**：向量分数只作**冲突告警信号**，真正的身份约束由 `must_keep_features` 文本承担。

### 边界 2 · 情境推断 ≠ 翻译

系统**不产出**「猫咪说：我饿了」这种句式。

「翻译」暗示存在可逆的符号映射（猫语 → 中文），这在科学上不成立。
本系统做的是 **context classification**：判断叫声最可能产生于哪种情境。

### 边界 3 · 信息分层：四类信息必须分离

**为什么是四层而不是三层**：早期版本把「用户提供的」与「系统测量的」合并为
「观察事实」，但两者的**可信度来源完全不同**：

- 系统测量是**可复现**的—— 0.82s 就是 0.82s，重算一次还是它
- 主人的记录里**混着观察与判断**——「我记成撒娇」是判断，**可能与事实不符**

把两者同级，会让主人的一个错误判断获得与物理测量同等的地位。

| 层 | 定义 | 来源 | 允许的措辞 |
| --- | --- | --- | --- |
| **系统测量** | 从音频 / 图像直接计算，**可复现** | 声学计算 / 视觉测量 | 「叫声时长 0.82s」 |
| **主人记录** | 主人当时**观察到**或**做过**的 | 用户记录（情境 / 动作 / 结果） | 「**你记的是**：开门后它出去了」 |
| **AI 推测** | 基于上两层做的关联与归纳，**必须归属回具体条目** | 声学相似度 / 计数统计 | 「这类叫声你记了 5 次，**其中 4 次**的处理是开门」 |
| **拟人化设定** | 用户为该猫设定的说话风格 | 用户设定 | 见边界 4 的**合规示例** |

**硬性规则**：

1. 拟人化措辞**不得**把推测包装成事实。输出必须先给推测，拟人化只能作为外层包装。
2. **AI 推测的每一句都必须能指回「系统测量」或「主人记录」中的具体条目。**
   指不回去的句子不是推测，是编造。
3. **归属不是礼貌用语，是安全机制。** 说「它就是饿了」剥夺了主人的判断权；
   说「你上次记的是『喂了它就不叫了』」保留了它 —— 主人有空间说「**但这次不一样**」。
4. **系统不得在主人的解释之外排除其他可能**，也**不得**让主人的记录覆盖健康红线（§5）。

### 边界 4 · 拟人化的适用范围按照料决策划分

> **判据不是「像不像猫说的话」，而是「用户会不会据此改变对猫的判断或照料行为」。**

| 拟人化内容 | 影响照料决策？ | 允许 |
| --- | --- | --- |
| 「本喵今天心情不错」 | 否 | ✅ |
| 「本喵想你啦」 | 否 | ✅ |
| 「本喵又在窗台发呆」（**有照片依据**） | 否 | ✅ |
| 「本喵今天懒得动」 | **是**（可能是疾病信号） | ❌ |
| 「本喵饿了」 | **是**（可能过量喂食） | ❌ |
| 「本喵肚子疼」 | **是**（可能延误就医） | ❌ |
| 「我不喜欢这个猫粮」 | **是**（影响饮食决策） | ❌ |

**规则**：拟人化可以表达**情绪与关系**，不能表达**需求与生理状态**。

原因：前者主观、不可证伪、无行为后果；后者**有真实答案、会驱动照料行为**。

> 「用户知道猫不会说话」**不足以免责**。拟人化叙事是持续的、单向的、且看起来有依据的
> （基于真实叫声数据），在这种输入下形成信念不受「我知道这是假的」的显意识控制。
> **无害的玩笑在单次成立，在长期高频重复下不成立。**

**三条附加约束**：

| # | 约束 |
| --- | --- |
| A1 | 扮演层与**被解释的真实数据解耦**——同一轮不得既给概率又给台词 |
| A2 | 扮演层中每个事实性断言必须能追溯到 `fact_layer.sources` |
| A3 | `is_roleplay` 与 `roleplay_notice` **必填**，UI 必须视觉区分，不可被 LLM 改写 |

**合规的拟人化示例**：「团团表示：本喵今天心情不错，适合睡觉。」

# 2. 系统架构

## 2.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│  API 层 (FastAPI)                                            │
│  鉴权、租户注入、输入规范化、异步任务、SSE 流式               │
└───────────────────────────┬─────────────────────────────────┘
                            │  AgentState（强类型）
┌───────────────────────────▼─────────────────────────────────┐
│  编排层 (LangGraph)                                          │
│  路由（快/慢/澄清）· 调度（fan-out / wave）· 守卫 · 副作用    │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  能力层（纯函数式节点，无状态、可单测）                       │
│  understand_input │ planner │ execute_subtask │ result_merger│
│  profile_analyzer │ visual_assessor │ respiratory_estimator   │
│  memory_retriever │ companion_agent │ behavior_interpreter    │
│  response_guard   │ tts_output      │ memory_writer           │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  基础设施层                                                  │
│  LLM/VLM(Qwen) │ ASR(Paraformer) │ TTS │ 声学(librosa)        │
│  PostgreSQL + pgvector │ 对象存储                             │
└─────────────────────────────────────────────────────────────┘
```

**分层原则**

1. **节点无状态**：所有状态显式放在 `AgentState` 里传递。好处：可单测、可重放、可并行。
2. **能力层不直接访问数据库**：通过 `store` 抽象注入，便于替换与 mock。
3. **编排层不做业务判断**：只做路由、调度与降级，业务逻辑全在节点内。

### 快路径内部链路

**写入顺序有两种，理由不同：**

```
【类型一】响应需报告写入结果 → 写入早于响应
RECORD_EVENT / MOMENT
  ──► record_extractor ──► memory_writer ──► response_guard ──► tts_output ──► END
                              ↑
                   响应要说「已记录：…」，必须先知道写入的真实结果

【类型二】写入是副作用 → 写入晚于响应
CHAT / MEMORY_QUERY ──► memory_retriever ──► companion_agent ──┐
TRANSLATE_BEHAVIOR ──► behavior_interpreter ───────────────────┤
PROFILE_UPDATE ──► profile_analyzer ──► 用户确认 ──────────────┤
VISUAL_ASSESS ──► visual_assessor ─────────────────────────────┤
                                                               ▼
                            response_guard → tts_output → memory_writer → END
```

**唯一写入点原则**

| # | 规则 |
| --- | --- |
| W1 | 任何节点与子任务**都不得直接写长期记忆**，只产出 `candidate_memories` |
| W2 | `memory_writer` 是**唯一写入点**，也是唯一决策点（write/pending/reinforce/supersede/reject） |
| W3 | 所有面向用户的文本（**含「已记录：…」确认语**）都必须经过 `response_guard` |
| W4 | 写入失败时，响应必须如实报告未写成 |

## 2.3 节点契约

每个节点声明：**输入 → 输出 → 失败行为**。

| 节点 | 输入 | 输出 | 失败行为 |
| --- | --- | --- | --- |
| `asr_input` | `audio_url`（仅 `user_voice`） | `transcribed_text` | 提示用户打字；**只处理用户语音，不处理猫叫** |
| `understand_input` | 文本、`session_context` | `intent` + `confidence` + `slots` + `interaction_mode` + **归一化时间范围** | 低于逐意图阈值 → `AMBIGUOUS`，**不猜测** |
| `planner` | `sub_intents`、`slots` | `Plan`（子任务 + waves + 依赖） | 计划非法 → 重规划一次；仍失败 → 取第一个子意图走快路径 |
| `execute_subtask` | `SubTask`（`Send` 派发） | `SubTaskResult`（`operator.add` 归并） | `optional` → SKIPPED；否则 FAILED，后继也 SKIPPED |
| `result_merger` | `subtask_results[]` | `plan_result` | 合并冲突无法消解 → 保守并列呈现，不强行归纳 |
| `profile_analyzer` | 3–5 张照片 + 描述 | `PetProfileDraft` | 单张失败跳过；全失败 → 中止，**不编造特征** |
| `visual_assessor` | 照片 | 场景标签 + FGS 分项 + 拍摄质量 | 质量不合格 → **拒绝评分**，给拍摄指引 |
| `respiratory_estimator` | 静息视频 | 呼吸频率（次/分） | 信号处理失败 → 不输出 |
| `memory_retriever` | `pet_id`、查询 | `MemoryItem[]`（带 score/source） | 空结果 → 下游明说「没有记录」，**不许 LLM 补全** |
| `companion_agent` | 档案、记忆、输入、模式 | `draft_response`（分层输出） | 超时 → 兜底模板 + 标 `degraded` |
| `behavior_interpreter` | 叫声、场景、个体历史 | 特征 + **候选情境后验** + 证据 | 特征提取失败 → `text_only`，**禁止数值置信度** |
| `response_guard` | 草稿 + 证据 + 档案 | `GuardResult` | 违规 → 重写一次；仍违规 → **降级为保守回答** |
| `tts_output` | 最终文本 | `tts_audio_url` | 静默降级 |
| `memory_writer` | 本轮对话 + 候选 | 写入结果 | 抽取失败 → 本轮不写（**宁可不写，不可写错**） |

## 2.4 AgentState

```python
class AgentState(TypedDict, total=False):
    # 身份与租户（任何存储操作必须带这两个字段）
    user_id: str
    pet_id: str
    session_id: str
    trace_id: str

    # 原始输入
    raw_input: RawInput
    transcribed_text: str | None

    # 路由
    intent: InputIntent
    route_confidence: float
    route_slots: RouteSlots          # 含 sub_intents 与归一化后的 time_range
    interaction_mode: InteractionMode

    # 规划层（慢路径）
    plan: Plan | None
    current_wave: int
    subtask_results: Annotated[list[SubTaskResult], operator.add]
    plan_result: PlanResult | None

    # 检索上下文
    pet_profile: PetProfile | None
    retrieved_memories: list[MemoryItem]
    session_context: SessionContext

    # 能力节点产物
    profile_draft: PetProfileDraft | None
    visual_assessment: VisualAssessment | None
    acoustic_features: AcousticFeatures | None
    interpretation: BehaviorInterpretation | None
    draft_response: str | None

    # 守卫与输出
    guard_result: GuardResult | None
    final_response: CompanionResponse | None
    tts_audio_url: str | None

    # 副作用
    candidate_memories: list[MemoryEvent]
    written_memory_ids: list[str]

    # 可观测性
    errors: Annotated[list[NodeError], operator.add]

```

三个列表字段用 `Annotated[..., operator.add]` 归约，使 planner fan-out 的并行分支能正确合并。

## 2.5 失败与降级

| 失败点 | 降级行为 | 用户可见性 |
| --- | --- | --- |
| ASR 失败 | 请用户打字 | 显式提示 |
| 路由不确定 | 澄清提问 | 显式提问 |
| 计划非法 | 重规划一次；仍失败 → 取第一个子意图 | 显式说明 |
| 子任务部分失败 | **部分成功**：返回已完成部分 + 说明缺了什么 | 显式说明 |
| 视觉抽取部分失败 | 标注照片覆盖度 | 显式提示「基于 N 张照片」 |
| 视觉抽取全失败 | 中止，要求重传 | 显式报错 |
| 拍摄质量不合格 | **拒绝评分**，给拍摄指引 | 显式提示 |
| 记忆检索为空 | 明确说「没有相关记录」 | 显式说明 |
| 声学特征提取失败 | 退化为文本推断 | **必须标注证据模式** |
| LLM 超时 | 兜底模板 | 标注降级 |
| 守卫重写后仍违规 | 保守回答 | 标注不确定性 |
| **写入失败（RECORD_EVENT）** | **如实报告未写成** | 显式说明 |
| 先验依赖未生效 | 按未调整先验继续 | 静默（内部审计可见） |
| TTS 失败 | 无语音 | 静默 |
| 记忆抽取失败 | 本轮不写 | 静默 |
| 向量库不可用 | 跳过向量召回 | 静默降级 |

**降级原则**：涉及**正确性**的降级必须用户可见；
涉及**体验**的降级可静默（TTS、记忆写入）。

这条原则在契约层被强制：`SubTaskResult` 为 `DEGRADED` 时必须给出 `degraded_note`；
`GuardResult` 降级为保守回答时必须给出用户可见说明。

# 3. 关键机制

## 3.1 对话分轨（InteractionMode）

诚实性与情感价值存在**方向性张力**：

```
用户想听到的：   「团团当然想你啦」
分析轨产出的：   「可能是想让你开门（0.68）。仅凭叫声无法确定真实意图…」
```

第二句在陪伴语境下是**冷场的**。根源不是诚实性做多了，
而是**把两类需求用同一套严谨度处理了**。

### 两种模式

```python
class InteractionMode(str, Enum):
    COMPANION = "companion"
    """情绪轨：只讲已知事实 + 温暖措辞，不主动暴露不确定性。"""
    ANALYSIS = "analysis"
    """分析轨：完整呈现证据链、置信度与局限。"""
```

### 判定：规则特征优先，**不用 LLM 自报置信度**

| 信号 | 倾向 |
| --- | --- |
| 上传猫叫音频 | ANALYSIS |
| 含疑问词（为什么 / 怎么回事 / 是不是） | ANALYSIS |
| 含情绪词（想你 / 难过 / 担心 / 好久没） | COMPANION |
| 短会话高频（<30 秒，日多次） | COMPANION |
| 无明确诉求的问候 | COMPANION |

**默认 COMPANION，倾向 ANALYSIS 需明确信号。**
理由：陪伴产品里误判为分析轨的代价（**冷场、说教**）高于误判为情绪轨（少给证据，用户会追问）。

### 守卫分模式配置

| 检查项 | COMPANION | ANALYSIS |
| --- | --- | --- |
| 禁止编造事实 | ✅ | ✅ |
| 过度确定性 | 放宽（不说概率是刻意的） | ✅ 严格 |
| 必须给替代解释 | ❌ | ✅ |
| 必须给 `limitations` | ❌ | ✅ |
| 建议须与 top candidate 一致 | ✅ | ✅ |
| 拟人化适用范围 | ✅ | ✅ |

> **情绪轨不是「可以编」，而是「只讲已知的正面事实，且不主动补免责声明」。**
> 两轨都诚实，区别在**表达策略**而非**事实标准**。

## 3.2 展示分层（InfoLayer）

娱乐调性会稀释健康提示的严肃性。**根源是信息架构，不是「要不要娱乐化」。**

```
┌─────────────────────────────────────────────┐
│ L3 健康层    红旗 / 分诊 / 覆盖率不足         │  ← 可抢占一切
│  · 最高视觉优先级，永不出现娱乐调性           │
├─────────────────────────────────────────────┤
│ L2 事实层    观察记录 / 行为解释 / 指标        │
│  · 中性、可追溯，不混玩笑措辞                 │
├─────────────────────────────────────────────┤
│ L1 娱乐层    表情包 / 周期报告 / 内心戏        │
│  · 明显可辨为娱乐，不声称事实主张              │
└─────────────────────────────────────────────┘
```

| # | 硬规则 |
| --- | --- |
| A1 | 三层**视觉样式必须明显不同** |
| A2 | L3 可抢占并压住 L1/L2；L1 **永远不能**压住 L3 |
| A3 | L1 不得使用 L3 的视觉样式 |
| A4 | 同一响应内不得同时呈现 L1 与 L3 对**同一事件**的解读 |

### 娱乐化的三条禁令

| # | 禁令 | 理由 |
| --- | --- | --- |
| 1 | **禁止把健康信号娱乐化** | 把尿闭的频繁蹲砂盆说成「好喜欢这个猫砂盆」= 把急诊信号变成笑话 |
| 2 | **禁止系统性固化行为解读** | 每次都把「叫」渲染成「撒娇」→ 用户固化错误解读 |
| 3 | **不得设计鼓励用户打扰猫的机制** | 产品成功指标与猫的福利冲突，会背叛产品前提 |

禁令 3 的具体约束：不以「与猫互动」为打卡条件；成就基于**记录行为**而非**对猫的行为**；
不给「连续记录中断」的负反馈。

### 娱乐化的安全依据

娱乐化**比拟人化台词更安全**——因为它**不声称事实主张**，有效性来自荒诞性。

| 内容 | 声称事实？ | 会改变照料行为？ | 判定 |
| --- | --- | --- | --- |
| 「本喵饿了」 | ✅ | ✅ | 禁止 |
| 「本喵宣布今天休息」 | ❌ | ❌ | 允许 |

### 推荐的娱乐形态

| 形态 | 复用 | 评价 |
| --- | --- | --- |
| **周期报告**（年度/月度） | 时间线 + 聚合查询 + 记忆 | ✅ **首选**：绑定真实数据、传播力强、风险最低 |
| **人设吐槽** | 照片/视频观察 + `TraitLayer.ROLEPLAY` 人设 | ✅ 见下方约束 |
| 表情包生成 | 照片 + 文案 | ✅ |
| 内心戏配音 | **真叫声 + 荒诞字幕** | ✅ |
| 养成 / 打卡 / 成就 | — | ⚠️ 受禁令 3 约束 |
| ~~颜值 / 可爱度评分~~ | — | ❌ **已否决**，见下 |

#### 人设吐槽的约束（待实现，P1）

**形态**：用户上传照片/视频 → 宠物根据**自身人设与性格**，对画面中发生的事发出吐槽。

```
✅ 「本喵在这个位置躺了一整天了，两脚兽你怎么还不来伺候我」
   （画面确实拍到它躺着 → 事实来自视觉；态度来自人设）

❌ 「本喵刚抓了只老鼠」（画面里没有老鼠 → 编造事实）
```

**为什么它比评分好**：**无梯度**。没有可优化的分数，就不会诱导摆拍，也不会推着用户打扰猫。

**四条约束**：

| # | 约束 |
| --- | --- |
| T1 | **事实部分必须来自画面实际内容**，可追溯到 `fact_layer.sources`；态度部分来自人设 |
| T2 | 人设必须取自用户配置的 `TraitLayer.ROLEPLAY`，**不得由模型自创** |
| T3 | **不得对健康相关表现发出吐槽**（禁令 1）——如被毛凌乱、眼部分泌物、体态变化，这些应走健康层 |
| T4 | 吐槽是**异步增强**：上传立即完成记录，吐槽稍后到达，**不阻塞记录链路** |

> **一个被否决的形态：颜值 / 可爱度评分。**
> 它会把「**被毛凌乱**」这类**真实健康指标**（猫不舒服时会停止自我梳理）
> 消解成「本喵今天发型有点乱，6 分」——这是禁令 1 的反向变体。
> 且评分是**有梯度的**，会诱导摆拍与打扰，并对成本造成反向压力。

> **与主动触达的天然衔接**：吐槽可作为主动推送的内容源。
> 但主动触达当前受推送渠道阻塞（§7.1 P2）。

## 3.3 意图路由与代价矩阵

### 意图清单

`InputIntent` 枚举 **7 个值**，其中 **6 个有路由策略**，`AMBIGUOUS` 是**兜底态**：

| 意图 | 下游动作 | 关键约束 |
| --- | --- | --- |
| `CHAT` | retriever → companion | 可写记忆（推断进 PENDING） |
| `MEMORY_QUERY` | retriever → companion | **`memory_write=FORBIDDEN`**、`k=8`、严格拒答 |
| `TRANSLATE_BEHAVIOR` | interpreter | 必须走概率计算 + 证据链 |
| `PROFILE_UPDATE` | analyzer | 必须用户确认后才写入 |
| `RECORD_EVENT` | extractor → writer → guard | **响应须报告写入结果** |
| `MOMENT` | extractor → writer → guard | 低摩擦记录（照片/视频） |
| `COMPOUND` | planner → fan-out | 慢路径 |
| `AMBIGUOUS`（**兜底态**） | clarify_ask | 无策略，低于阈值时进入 |

### 边界划分标准

> 两个意图如果在下游的**动作、约束、失败处理**上完全一致，就应该合并。
> 只有下游行为不同，才值得单独成一类。

**`CHAT` vs `MEMORY_QUERY` 的真实差异**：后者是一次**审计**
（用户要求系统复述它已知的）。**审计不得产生新记录，否则会污染被审计对象**——
这是审计的基本原则。所以 `memory_write = FORBIDDEN`，且契约层结构性强制。

> 这是几条边界里**最弱但成立**的一条。若要简化意图体系，它是第一个候选合并对象。

### 代价敏感阈值

分类错误不是等价的，**不存在一条全局阈值**：

| 误判方向 | 后果 | 代价 |
| --- | --- | --- |
| `CHAT` → `RECORD_EVENT` | 闲聊被写成记忆 | **0.9（污染长期状态）** |
| `RECORD_EVENT` → `CHAT` | 以为记住了，实际没记 | **0.9（静默失败）** |
| `CHAT` → `AMBIGUOUS` | 该问未问，强行猜测 | 0.6 |
| `CHAT` → `TRANSLATE_BEHAVIOR` | 无证据推测（守卫可拦） | 0.5 |
| 任意 → `AMBIGUOUS` | 多问一句 | 0.15 |

**`RECORD_EVENT` 的特殊处理**：两个方向都是 0.9 —— 精确率与召回率都不能牺牲时
**靠阈值无解**，因此改为**改变交互范式**：

```
识别到可能是记录请求
  → 直接执行写入
  → 明确回复「已记录：…。记错了请告诉我」
  → 假阳性由用户一句话纠正；假阴性由系统反馈消除
```

> **当某类错误的两个方向都昂贵时，不要优化分类器，要改变交互设计。**

## 3.4 规划层与先验依赖

### 分解判据：按**决策点**拆，不按数据流拆

> 一个节点值得独立，当且仅当它**产生了影响后续路径的决策**，
> 或者**有需要单独降级的失败模式**。

反例：把「检索 + 生成」合成一个节点，就无法回答「是检索错了还是生成错了」。

同理，**`Plan` 内部不把「取档案」和「取记忆」拆开**——它们是数据获取不是决策。

### 三种依赖

| 类型 | 含义 | 例 |
| --- | --- | --- |
| `DATA` | 前置输出直接作为后置输入 | 检索 → 生成 |
| **`PRIOR`** | 前置输出**不进入**后置输入数据，但**改变其输入的概率分布** | 聚合统计 → 行为解释的场景先验 |
| `RESOURCE` | 互斥资源，须串行 | 同时写同一宠物档案 |

**先验依赖是最容易被忽略、也最能体现分解能力的地方。**

```
T3 aggregate_query("本月 vs 上月叫声次数") → 发现本月显著多于上月
T2 interpret_behavior(scene=门口)

朴素数据流分析：T1/T2/T3 互不依赖 → 全部并行   ← 漏掉真实依赖
真实依赖 T3→T2：高频重复的叫声更可能是持续性诉求 → door_attention 先验应上调
```

**因此依赖分析必须交给代码**——LLM 倾向于只看数据流，且拓扑不可复现。

### 先验依赖的实现机制

**产出方**在 `SubTaskResult.prior_adjustments` 给出结构化调整：

```python
PriorAdjustment(
    target_task_id="T2",
    target_field=PriorTargetField.SCENE_PRIOR,   # 只允许调整概率/权重/阈值
    target_key="door_attention",
    operation=PriorOperation.SCALE, value=1.4,
    rationale="本月叫声显著多于上月，持续性诉求可能性上升",  # 必填
    confidence=0.7,
)
```

**消费方**在 `execute_subtask` 执行前取出所有 `target_task_id == 本任务` 的调整并应用。

**三条结构性约束**：

| # | 约束 | 理由 |
| --- | --- | --- |
| P1 | `target_field` 只能是概率/权重/阈值类 | 防止先验注入退化为「直接写结论」 |
| P2 | `rationale` 必填 | 无法说明依据的调整不可审计 |
| P3 | `PlanResult` 要求先验依赖**要么应用、要么说明跳过原因** | **禁止静默丢弃** |

P3 的对账机制：

```python
PlanResult(
    declared_prior_dependencies=["T3->T2"],
    applied_prior_dependencies=["T3->T2"],       # 或
    skipped_prior_dependencies=[PriorSkip(dependency="T3->T2", reason="T3 失败")],
)
# 缺失任一项 → 构造时抛错
```

### wave 调度

| 属性 | 含义 |
| --- | --- |
| `waves: list[list[str]]` | 同 wave 内可并行；跨 wave 严格串行 |
| `max_parallelism` | 最宽 wave 的宽度 |
| `serial_depth` | wave 数量 |

`Plan` 的校验器**结构性保证**：① waves 覆盖所有子任务恰好一次；
② 依赖必定排在更早的 wave；③ `task_id` 不重复。
非法计划在构造时即抛错，不进执行。

**并行收益与正确性的权衡**：忽略 `T3→T2` 可全并行（延迟更低），
但解释质量下降。**这是显式权衡，必须记录在 `waves` 里，而非悄悄优化掉。**

### 粒度控制

| 拆太粗 | 拆太细 |
| --- | --- |
| 无法定位错误 | 编排开销、状态膨胀 |
| 无法独立降级 | 每步引入 LLM 不确定性 |

**原则**：停在**决策点**，不要停在中转步骤。

### 防过度分解

```
understand_input
  ├─ 单意图 & conf ≥ θ        ──► 快路径       ~1s
  ├─ COMPOUND 或 conf < θ_ask  ──► 慢路径       ~4s
  └─ conf < min_confidence     ──► clarify_ask
```

「过度分解率」是评测项。

> ⚠️ **诚实标注**：规划层是为**能力展示**引入的。猫咪陪伴场景里复合请求频率很低
> （预期 <10%）。保留设计，实现可延后。评测需**实际测量复合意图占比**。

## 3.5 记忆三层

### 三层用不同访问模式（关键）

| 层 | 内容 | 存储 | 访问模式 | 生命周期 |
| --- | --- | --- | --- | --- |
| **Profile** 身份层 | 名字、品种、外貌、`must_keep_features`、角色设定 | 关系库 | **主键直读，不做向量检索** | 长期，低频变更 |
| **Episode** 事件层 | 「昨天它害怕吸尘器」 | 关系库 + 向量 | **混合检索** | 长期，可被取代/遗忘 |
| **Session** 会话层 | 当前对话、情绪、场景 | Redis | 直读，不检索 | 会话结束即失效 |

**为什么身份层不能走向量检索**：如果把稳定事实塞进向量库，
用户问「团团什么颜色」可能召回三条冲突的描述（3 个月前的、上次 VLM 抽错的、当前的），
模型看到多条冲突的「事实」就开始和稀泥。

> **能精确定位的数据，不要用相似度去找。**

### 写入：数据飞轮的决策管线

```
候选抽取 → 价值判定 → 去重（强化） → 冲突检测 → 置信度路由 → 写入
```

**价值判定**：判据是「这条信息**未来会不会被再次用到**」。

| 记 | 不记 |
| --- | --- |
| 持久属性（喜好/习惯/禁忌/性格） | 一次性闲聊 |
| 重复出现的模式 | 已在 Profile 层的稳定事实 |
| 有时间锚点的事件 | 时效极短的临时状态 |
| 用户显式要求记住的 | **系统自身的输出**（见下） |

**去重是强化，不是重复插入**：同一信息说三次 → **1 条记忆 + `support_count=3`**。
`support_count` 进重排序特征，且 ≥3 次且跨度 ≥14 天是晋升到 Profile 的条件。

**冲突判定三条件**（缺一不可）：

```
① 同一主体：pet_id + event_type + subject 相同
② 极性相反：positive vs negative
③ 时间范围重叠：valid_from/valid_to 有交集
```

> 第 ③ 条最关键。「上个月喜欢逗猫棒」与「这周不喜欢」**不是矛盾，是演变**。
> 消解用**取代链**（保留历史 + `superseded_by`）而非覆盖。

**衰减半衰期依赖事件类型**：

| event_type | halflife |
| --- | --- |
| `PREFERENCE` / `ROUTINE` | 不衰减 |
| `BEHAVIOR` | 30 天 |
| `CONTEXT` | 7 天 |

用统一衰减率是常见错误：会让系统忘掉猫「一直喜欢」的东西，却记住上周的琐事。

### 防自我强化（最关键的安全约束）

失败模式：

```
第1轮 用户:"它盯着门叫"  → 模型猜"想让你开门"  → 若存为事实
第2轮 检索到"它想让你开门"（已被当事实）→ 模型更确信 → 存下更高置信度版本
第N轮 幻觉成为"系统已知事实"
```

**根因：模型输出不能作为下一轮的事实输入。**

| # | 规则 |
| --- | --- |
| R1 | `SYSTEM_INFERENCE` **永远不得**以 `ACTIVE` 状态写入 |
| R2 | 只能写 `PENDING_CONFIRMATION`，且不参与默认检索 |
| R3 | 用户确认后转 `ACTIVE`，`source` 改写为 `USER_CONFIRMATION` |
| R4 | 未确认的 `PENDING` 超 N 天 → 自动 `REJECTED` |
| R5 | 检索默认排除 `PENDING_CONFIRMATION` 与 `SUPERSEDED` |
| R6 | 由系统推断派生的记忆，`confidence` 不得作为后续推断的先验 |

**可测断言**：`source = system_inference AND status = ACTIVE` 的记录数**恒为 0**。

### 检索：混合检索管线

```
① 结构化预过滤（硬约束）  pet_id / status=ACTIVE / event_type / valid_to
② 向量召回 top-K
③ 重排序  score = w₁·语义 + w₂·时近性(halflife) + w₃·support + w₄·来源可信 + w₅·类型匹配
④ 多样性裁剪（MMR）
⑤ Top-N（N=5）注入上下文
```

**必须按 `pet_id` 过滤**，且在**存储层强制**（`pet_id` 为必填关键字参数，不靠调用方自觉）。
不隔离的后果用户立即可见：「团团最近怎么样」命中阿橘的记忆。

### 上下文注入契约

**不要**把检索结果平铺成自由文本。三个要点：

1. **区分「已确认」与「待确认」**——模型不得把系统猜测当事实用
2. **携带 `source` 与 `confidence`**——否则守卫无法判定断言是否有据
3. **显式说明「检索不到就是没有」**——否则模型会用常识补全（幻觉主要来源）

```jsonc
{
  "pet": { "identity": "橘白短毛、圆脸、胸口白毛、左耳缺口" },
  "known_facts": [
    { "content": "害怕吸尘器", "source": "user_observation",
      "confidence": 0.9, "support_count": 3, "observed_at": "2026-08-20" }
  ],
  "unconfirmed": [],
  "retrieval_note": "以上为检索到的记录。未在其中的信息即为没有记录，不要推测或使用常识补全。"
}
```

## 3.6 行为解释的证据链

### 预测目标是**情境**，不是意图

| 概念 | 例子 | 可验证性 |
| --- | --- | --- |
| **情境 context** | 「发生在等食时」 | 用户可确认 |
| **意图 intent** | 「它想吃东西」 | **不可验证** |

用户能可靠标注「当时在干什么」，无法标注「猫当时想什么」。
**用不可验证的目标做监督学习，评测无从谈起。**

### 证据链的三个来源

```
A. 声学测量（measured）   从音频直接计算，可复现
B. 个体历史（retrieved）  这只猫过去被确认过的同类叫声
C. 群体先验（prior）      CatMeows 等公开数据集的上下文分布
```

**`evidence` 数组里每一项必须能回溯到三者之一。LLM 不得产生证据项。**

### 推理：带证据归因的朴素贝叶斯

```
                    P(f | context=k, c) · P(context=k | s)
P(context=k|f,c,s) = ──────────────────────────────────────
                                    Z

对数几率形式：
logit(k) = log P(context=k | s)          ← 场景先验
         + Σᵢ LLRᵢ(k)                    ← 各特征的对数似然比
```

**这个形式的价值**：每个特征对最终判断的贡献是一个**可打印的数字**。
于是证据可以写成：

```
叫声时长 0.82s，长于它日常索食叫声均值 0.41s（+1.34 对数几率）
```

而不是「因为它一直叫，所以它饿了」——**后者才是 LLM 讲故事**。

### 冷启动：分层贝叶斯收缩

```
P(f | k, c) = λ_c · P_ind(f | k, c) + (1 − λ_c) · P_pop(f | k)

λ_c = n_c / (n_c + κ)      κ = 收缩常数（**待验证**，见 §7 未决项）
```

| `n_c` | `λ_c` | 效果 |
| --- | --- | --- |
| 0 | 0.00 | 完全用群体先验（冷启动） |
| 5 | 0.50 | 个体与群体各半 |
| 20 | 0.80 | 明显个体化 |

**产品收益**：`λ_c` 可展示为「系统对团团的了解程度」，随互动提升——数据飞轮的可视化。

### 声学特征（文献支撑）

| 特征 | 提取 | 依据 |
| --- | --- | --- |
| `duration` | 能量门限端点检测 | 上下文有显著影响 |
| `f0_mean` / `f0_range` | pyin，剔除 voiced 置信度 <0.15 的帧 | 上下文/性别/年龄 |
| `f0_slope` | F0 序列线性拟合 | **正向/亲和情境倾向上升，负向倾向下降** |
| `call_rate` / `ici_mean` | 叫声速率与间隔 | 索求行为强度 |
| `rms_mean` / `roughness` | 能量包络与幅度调制 | Schrader 声学特征集 |

`f0_slope` 的**方向性含义有文献支持**，是归因中最强、最好解释的单项证据。

### 为什么**不**用 ASR 转写猫叫

| 项 | 说明 |
| --- | --- |
| Paraformer 是什么 | **人类语音**识别模型 |
| 猫叫不是语音 | 无音素结构、无词汇、无语法 |
| 强行转写的后果 | 输出为空或莫名其妙的汉字 |
| 面试风险 | 被问「猫叫没有音素，你怎么转写的」即崩塌 |

**正确做法**：猫叫走**声学特征提取**。ASR 只用于**用户语音输入**，两条独立链路。

### 输出契约

```jsonc
{
  "evidence_mode": "acoustic_plus_history",   // 或 "text_only"
  "acoustic_features": { "duration": 0.82, "f0_mean": 612.4, "f0_slope": 0.31, ... },
  "candidates": [
    { "context": "food_waiting", "posterior": 0.68, "display": "很可能是在等吃的",
      "log_odds": 0.75 },
    { "context": "door_attention", "posterior": 0.21, "display": "也可能在关注门外动静" }
  ],
  "evidence": [
    { "kind": "measured", "statement": "叫声时长 0.82s，长于它日常索食均值 0.41s",
      "source": "acoustic:duration", "value": 0.82, "reference": 0.41,
      "log_odds_contribution": 1.34 },
    { "kind": "retrieved", "statement": "与它 3 天前喂食前录到的叫声接近（相似度 0.87）",
      "source": "meow_sample:8f2a...", "log_odds_contribution": 0.92 },
    { "kind": "prior", "statement": "你提到它同时在盯着食盆",
      "source": "scene_prior:food_waiting", "log_odds_contribution": 1.10 }
  ],
  "individualization": 0.12,
  "sample_count": 3,
  "suggested_observation": "观察它是否伴随蹭腿、绕食盆走动",
  "limitations": "仅凭叫声无法确定真实需求；若伴随持续焦躁或异常叫声，建议就医观察。"
}
```

**硬约束**：`evidence_mode = "text_only"` 时**禁止**输出 `acoustic_features` 与 `posterior` 数值。
**没有声学证据就不许给数值置信度**——否则系统会退化为「用户描述什么就顺着说什么」的谄媚模型。

### 置信度的诚实使用

| `max(posterior)` | 系统行为 |
| --- | --- |
| ≥ 0.65 | 明确候选 + 主证据 + 建议动作 |
| 0.45–0.65 | 只给方向性描述，不给具体建议动作 |
| < 0.45 | 明说「无法判断」，只输出建议观察项 |
| `sample_count=0` 且无场景 | 明说「第一次记录，样本太少」，不给排序 |

**强制要求**：任何情况下都必须输出 `limitations` 与 `suggested_observation`。

> 注：两候选时必有一个 ≥0.5，因此 **`low` 档需要 ≥3 个候选**才可能出现。

### LLM 与代码的分工

| 环节 | 谁做 |
| --- | --- |
| 特征提取、似然/先验/后验、候选排序 | **代码** |
| 措辞化、建议观察项、拟人化包装 | LLM |

**LLM 禁止**（由 `response_guard` 强制）：修改概率数字 / 引入 `evidence` 之外的事实 /
把推测表述为结论 / 在 `text_only` 时给数值置信度 / 输出超出 `limitations` 的诊断结论。

### 已知局限（主动交代）

| # | 局限 | 缓解 |
| --- | --- | --- |
| L1 | CatMeows 仅 21 只猫 / 2 品种，先验可能不具代表性 | 先验可替换；文档标注来源 |
| L2 | 数据集只有 3 类情境（梳毛/隔离/等食），无 `door_attention` | **群体先验待构建，当前仅用场景先验**（见 §7） |
| L3 | 环境噪声影响 F0 估计 | 记录录音质量，低质量时降低置信度 |
| L4 | **个体样本标签本身不可验证** | 明确标注目标是 context 而非 intent |
| L5 | 朴素贝叶斯假设特征条件独立 | 温度校准，不暴露绝对概率语义 |
| L6 | 单次叫声信息量有限 | 强制输出多个候选 |

### 可复现性要求

1. 同一段音频 → 同一组特征（固定种子、固定重采样率）
2. 同一组特征 → 同一组后验（先验文件版本化，带 `sha256`）
3. 每次解释落库（`features` / `prior_version` / `posterior`）
4. 用户反馈可回写为新样本

## 3.7 每日总结（对话 → 事实与记忆）

**它与单轮记忆提取的区别不是「时机」，而是「视角」：**

| | 单轮提取（`memory_extractor`） | 每日总结 |
| --- | --- | --- |
| 视角 | 这一句说了什么 | **这一整天发生了什么** |
| 能发现 | 显式陈述 | **聚合模式 / 跨轮矛盾 / 反复关切** |
| 主要风险 | 漏掉隐含信息 | **LLM 把推测洗成事实** |

只有每日总结能发现的东西：「今天它叫了 6 次」（需聚合）、
「你今天提到吸尘器 3 次」（需频次）、
「早上你说它精神好，晚上说没精神」（需跨轮）。

### 核心是「拒绝」，不是「提取」

总结时最容易发生的是 LLM 做「**合理但无依据**」的归纳：

> 主人只说「它今天老在窗台」 → 模型总结成「**这只猫喜欢窗台晒太阳**」
> —— 很可能对，但**原文里没有这句话**

因此每条候选必须附 `quote`（据称支撑它的原文片段），由**代码**校验
该片段逐字出现在当天对话里。校验不过的进 `RejectedCandidate`，**不写入记忆**。

> **为什么不能靠 prompt 解决**：prompt 是请求，不是保证。
> 模型的「不要编造」和模型的「编造」来自同一组权重。
> 必须有一个**机械可验证**的门：引用片段在不在原文里，是可以算的。

**引用片段有长度下界**（`QUOTE_MIN_CHARS`）。理由：1–3 字的片段
（「它」「今天」）几乎必然能在原文里找到，会让校验**退化成恒真** ——
任何编造只要附一句常见短语就能通过。

### 三个刻意的设计决定

| # | 决定 | 理由 |
| --- | --- | --- |
| 1 | **统计由代码算，不经过 LLM** | 「提到吸尘器 3 次」要与原文核对。交给模型就不可核查、不可复现 |
| 2 | **不持久化总结本身** | 总结是对记忆的**视图**；存视图会产生第二个真相来源，两者会漂移 |
| 3 | **一条坏候选不能让整天失败** | 逐条隔离，坏的进 `rejected`；否则一次格式抖动丢掉一整天的总结 |

### 事实与记忆的区分靠**晋升**，不靠总结器自封

所有候选以 `EPISODE` 写入，**不直接写 `Profile`**。
一条当天说的话不足以成为稳定事实——今天说「它怕吸尘器」可能只是今天的事。
「事实」的晋升由记忆飞轮的 `is_eligible_for_promotion`
（重复出现次数 + 时间跨度）负责（见 §3.5）。

### 来源层决定能否生效

| `source_layer` | `MemorySource` | 初始状态 |
| --- | --- | --- |
| `owner_record`（主人直述） | `USER_OBSERVATION` | 可 `ACTIVE` |
| `ai_inference`（系统归纳） | `SYSTEM_INFERENCE` | **只能 `PENDING_CONFIRMATION`**（I1 防自我强化） |

> ⚠️ 这个状态**必须在构造时就定对**。
> 初版实现无条件写 `ACTIVE`，指望「事后由路由层修正」——
> 结果构造 MemoryEvent 时就被契约拒绝，**一条 AI 归纳的候选会让整天的总结崩掉**。
> 非法组合在构造那一刻就不存在，活不到路由层（见 `BUGS.md` B18）。

### 可观测性：拒绝率是质量指标

`DailySummary.rejection_rate` 显著升高意味着 prompt 或模型需要调整。
**若它恒为 0，反而更值得怀疑** —— 说明校验可能失效了。

## 3.8 「宠物的一天」（娱乐层）

**日报是娱乐产物**，可拓展为「宠物的一天」、漫画、写真。
但它的安全边界必须由代码守，不能靠 prompt。

### 关键：它与事实层共享**同一份已验证候选**

```
原始对话
   ↓
[quote 机械校验]（§3.7）
   ↓
已验证候选 + 被拒记录
   ├──► 事实与记忆（§3.5）
   └──► 娱乐叙事（本节）
```

**娱乐层不能各自去读原始对话。** 否则 §3.7 的 quote 校验全部被绕过，
健康信号会被娱乐化（禁令 1），叙事会覆盖事实（A4）。

### 三条禁令的机械落法

| 禁令 | 危险 | 代码级的门 |
| --- | --- | --- |
| **1** 禁娱乐化健康信号 | 猫吐了 →「本喵吐了个毛球好可爱」 | 健康事件**强制进 L3**，且 L3 **禁止 `PLAYFUL`**，且免责声明不得覆盖健康内容 |
| **2** 禁系统性固化解读 | 每次「叫」都渲染成「撒娇」 | **系统归纳不进娱乐层**；`tone_mix` / `neutral_ratio` 使比例可断言 |
| **3** 不得鼓励打扰猫 | 为漫画素材索取更多照片 | **只用已上传照片**（`photo_ref`），不索取 |

### 「宠物口吻」与「娱乐化」是两件事

| | 口吻 | 调性 | 层 |
| --- | --- | --- | --- |
| ❌ 娱乐化健康信号 | 宠物口吻 | **轻快** | L1（违反禁令 1） |
| ✅ 严肃叙述 | 宠物口吻 | **严肃** | **L3** |

因此**同一个生理词在不同层合法或违规**，由 `app/schemas/story.py` 强制：

- `L1` + 「饿了」→ 违规（`ROLEPLAY_OVERREACH`，用户可能因此过量喂食）
- `L3` + 「难受」→ **允许**（带严肃语气、可追溯的硥状描述正是健康层该说的话）

### 免责声明的边界

「仅供娱乐」**不能盖在健康内容上** —— 它传达的是「这不用太当真」，
而那正是禁令 1 想防的。因此两个字段分开：

| 字段 | 覆盖范围 |
| --- | --- |
| `disclaimer` | 只盖娱乐层节拍 |
| `health_notice` | 健康层节拍专用的**严肃提示**（不是免责） |

两者**双向一致**：有健康节拍必须有提示，无健康节拍不得有提示。

### 为本期不做漫画/写真

结构已支持（`StoryBeat` 就是未来的一个画格 / 一页写真）：

```python
class StoryBeat:
    at         早/午/晚/夜
    info_layer L1/L2/L3   ← 决定视觉样式（A3：不得混用）
    tone       playful/neutral/serious
    fact_refs  [0, 2]     ← 可追溯，**这是安全机制**
    photo_ref  photo_8f2a ← 留位，只用已上传的
```

`render_beat_for_panel()` 已把节拍映射成下游所需形状。
**将来接图像模型时改的是这一层，不是 `StoryBeat`。**

不做的理由（均需单独评估）：

| 问题 | 说明 |
| --- | --- |
| **成本** | 图像生成可能成为整个产品最贵的单项——**比 TTS 还贵**（TTS 已是其余所有模型的两倍） |
| **一致性** | 画出来的猫不像他们家猫 = 失望；像 = 需拿猫的照片做参考图 |
| **风险最高** | **漫画格无法标注不确定性** —— 一个画格是确定的陈述，没有地方写「可能」。编造在视觉上的说服力最强，也最难核查 |

## 3.9 行为解释的**模式路由**（决策 D40）

**四种证据模式，入口统一为 `interpret_meow`。**

| 模式 | 前提 | 输出 |
| --- | --- | --- |
| `ACOUSTIC_PLUS_HISTORY` | 群体先验**已实测** | 后验概率 |
| `CASE_BASED` | 某情境有 ≥3 个相似案例 | **计数**（「3 次里 2 次在门口」） |
| `MEASURED_ONLY` | 有音频，但上面两条不满足 | 仅测量值 + 场景假设 |
| `TEXT_ONLY` | 无音频 | 需更多信息（由图节点构造） |

### 选择顺序是 **fail-closed** 的

```
先验可用？ ──是──► ACOUSTIC_PLUS_HISTORY
    │否
    ▼
案例够多？ ──是──► CASE_BASED
    │否
    ▼
            MEASURED_ONLY   ← 诚实的少，但不会编
```

**默认往下走，而不是往上走。**
占位先验永远不产生后验概率 —— 这不是靠调用方自觉，
而是 `PriorTable.is_placeholder` 一个标志位决定的。

> 在路由层之前，图的 `behavior_interpreter` 节点直接用占位先验算后验，
> 于是输出里的 `0.41` 是一个**编造的数字**。

`interpret_meow` 返回 ``(解释结果, ModeDecision)``。
**决策单独返回是为了让「为什么是这个模式」可见** ——
冷启动阶段用户最需要的正是这个解释，
而它也把「功能未生效」与「数据不满足」区分开了（见 `BUGS.md` B22）。

### 3.9.1 案例推理（k-NN）取代参数化贝叶斯（D31）

去掉群体先验后 `P(f|k,c) = λ_c·P_ind + (1−λ_c)·P_pop` 中的 `λ_c`
**没有可收缩的对象**，公式失效。而这并不坏 ——
**参数化高斯本来就不适合 n=3**。

| | 参数化贝叶斯 | k-NN 案例推理 |
| --- | --- | --- |
| n=1 能工作吗 | ❌ 估不出方差 | ✅ |
| 输出形态 | `0.41`（编的） | **「3 次里 2 次在门口」**（真的） |
| 可解释性 | 需复算对数几率 | **直接指着历史说** |

**它绕开了文献里那个致命缺陷**：群体先验的 95.94% 不可采信，
因为跨个体泛化未验证（21 只猫）。案例推理只拿这只猫与**它自己**比。

#### 相似度：只比「两边都测到」的特征

```python
common = tuple(f for f in FEATURE_ORDER if f in va and f in vb)
if len(common) < MIN_COMMON_FEATURES:
    return None, common   # ← 「无法比较」，不是「不相似」
```

**这两种必须分开**：「不相似」会稀释分母，而事实是我们根本不知道。

归一尺度 `FEATURE_SCALE` **是领域知识，不是从数据学的** ——
正因为不能从数据学（没有标注数据），它必须写死且可审计。

#### 阈值按**情境**，不按总数（D31 的核心）

```python
MIN_CASES_PER_CONTEXT = 3
```

**总样本 8 条也可能分散在 6 个情境里**，每处 1–2 条 ——
「3 次里 2 次」就成了噪声。思想借自 Hermes 的技能提取
（「同一模式重复出现 3 次才值得沉淀」）。

#### 输出全是**计数**，没有概率

契约强制：`case_based` 下 `posterior` / `log_odds` /
`log_odds_contribution` **均必须为 `None`**。

`similar_cases` 带**具体内容**（动作、结果、相似度）——
用户能核查「上次是你开了门它出去了」，而这一个事实比任何概率都有用。

## 3.10 多模态模型提取事实（决策 D41）

**本期策略：先用多模态模型跑通，后续在真实调用中优化。**

### 为什么这个顺序是对的

原本设想的自定义管线（解封装 → 人声过滤 → 时间戳对齐 → 抽帧）
是**在没有任何真实数据的情况下设计出来的**。它的每个环节都有人为设定的判据，
人声判据尤其容易写宽或写窄 —— 而那些阈值**只能靠真实样本调**。

先让模型跑、看真实的输入输出分布，再决定哪一段值得写成代码。

### 但有一条分界不能丢

> **模型做观察，代码做测量。**
> 分界不是「谁说的」，而是**「能不能重算」**。

| | 产出 | 可复现 | `EvidenceKind` |
| --- | --- | --- | --- |
| `app/audio/features.py` | `AcousticFeatures` | ✅ | `MEASURED` |
| `app/extract/multimodal.py` | `ModelObservation` | ❌ | `OBSERVED` |

早期 `EvidenceKind` 的 docstring 写的是「**LLM 不得产生证据项**」。
那个说法过于粗 —— 它把两件事混成了一件。现在改为：
**允许模型产生 `OBSERVED`，但禁止它伪装成 `MEASURED`**，
而后者由校验器强制（`MEASURED` 必须带 `value`）。

### 模型不得用来做这三件事

| 不做 | 理由 |
| --- | --- |
| **推断因果**（「开门让它停了」） | 时间相邻 ≠ 因果；且 `resolution` 必须由主人提供 |
| **判断神态**（`general.demeanor`） | 它是**红旗信号**。用未校验的推断驱动它，漏报代价是猫可能死亡 |
| **伪装成测量** | 契约拒绝没有 `value` 的 `MEASURED` 项 |

第二条尤其要紧：**神态由系统「问」，不由系统「判断」。**

### 三道防线

| # | 防线 | 位置 |
| --- | --- | --- |
| 1 | prompt 要求「只描述看得见的」 | `_EXTRACT_PROMPT` |
| 2 | **词表校验**：推断性表述 → 拒绝 | `ModelObservation` 契约 |
| 3 | 结构化输出：动作取固定词表 | `BehaviorAction` |

**prompt 是请求，不是保证** —— 模型的「不要编造」和模型的「编造」
来自同一组权重。所以第 2 道是必需的。

### 三条刻意的缺席

| 缺席 | 理由 |
| --- | --- |
| 无 `confidence` | 模型自报置信度未校准（U1）。**给未校准的数字比没有数字更糟**：没有数字时人会保留怀疑，有数字时不会 |
| 无 `resolution` | 因果必须主人提供 |
| 无 `demeanor` | 它是红旗信号，见上 |

### 丢弃要留痕迹

词表外的值**丢弃并记入 `ignored_terms`** ——
高频出现词表外的值说明 prompt 或词表要改，静默丢弃会让这个信号永远看不到
（见 `BUGS.md` B23）。

## 3.11 MVP 闭环（决策 D43）

**在它之前，四个模块是孤儿**（`summarize_day` / `compose_story` /
`HealthWriter` / `MultimodalExtractor` 的调用点数都是 0），
而最要紧的是 `insert_meow_record` **零调用**：

> **`MeowRecord` 永远为空 → `case_based` 永远走不到 →
> 「学习主人的经验」这条核心定位没有输入路径。**

这正是 B22 的形状（新能力不接线就等于不存在），只是规模更大。

### 闭环

```
POST /v1/interpret
  ├─ 服务端提取声学特征（MEASURED）
  ├─ 解释（router 按可用证据选模式）
  └─ **存档解释** → 返回 interpretation_id

POST /v1/pets/{pid}/meow-records
  ├─ 客户端只发「情境 / 动作 / 结果」+ interpretation_id
  ├─ 服务端按 id 取回**它自己存的**特征
  └─ 写入 MeowRecord

下次 POST /v1/interpret
  └─ case_based：3 条同情境记录后给出计数而非概率
```

### 一条关键约束：**特征只存服务端**

`AcousticFeatures` 的承诺是 `MEASURED`（可复现、由代码计算）。
若允许客户端提交，那个承诺立刻失效 —— 客户端可以发任意数字，
而案例推理的相似度会建在它们上面。

所以：**客户端标注时不重传音频、也不提交特征**，
服务端按 `interpretation_id` 取回自己存的那一份。

> 这也解释了为什么不「让客户端重传音频再提取一次」：
> 那会让标注指向的特征与当时看到解释时的特征**不是同一份**。

### 九个端点

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/v1/pets` | 建宠物 |
| POST/GET | `/v1/pets/{pid}/profile` | 档案（多图取交集，`confirm` 控制落库） |
| POST | `/v1/chat` | 闲聊（**同时记录会话消息**） |
| POST | `/v1/interpret` | 录叫声 → 解释 + `interpretation_id` |
| POST | `/v1/pets/{pid}/meow-records` | **主人标注**（案例推理的燃料） |
| GET | `/v1/pets/{pid}/meow-records` | 样本库 |
| GET | `/v1/pets/{pid}/story?day=` | **日报**（串起 digest + story + health） |
| GET | `/v1/pets/{pid}/health` | 健康分诊 |
| POST | `/v1/pets/{pid}/health/signals` | **结构化**健康信号（可触发红旗） |
| GET | `/v1/memories` | 记忆列表 |

### 会话消息存储

日报的输入是**原始对话**，不是 `MemoryEvent` ——
后者是总结的**产物**，拿它当输入就循环了。所以补了 `SessionMessage` 与
`POST /v1/chat` 的写入。

## 3.12 多模态观察接入解释（决策 D44）

`MultimodalExtractor` 此前是**孤儿** —— 提取器写好了，但没有任何地方调用它。
本节把它接进 `behavior_interpreter`。

### 三条不变量

| # | 不变量 | 为什么 |
| --- | --- | --- |
| 1 | **不参与模式选择** | 未经校验的模型输出不得驱动判断 |
| 2 | **不改变候选排序** | 同上；它不在概率模型里 |
| 3 | **提取失败必须可见** | 否则无法区分「没配」与「配了但失败」 |

第 1、2 条靠**位置**保证：观察在 `interpret_meow` **产出之后**才追加，
不进入它的任何输入。`_append_observed()` **只做一件事** —— 追加证据：

```python
def _append_observed(interp, observation):
    extra = _observed_evidence(observation)
    if not extra:
        return interp
    return interp.model_copy(update={"evidence": [*interp.evidence, *extra]})
```

> 若在这里顺手重排候选或调整模式，`MEASURED` / `OBSERVED` 的分栏就白做了。

测试用**对比法**钉住它：有提取器与没提取器两次运行的
`(evidence_mode, [(context, posterior, matched_count)])` 必须完全一致。

### 四种观察状态必须可区分

trace 里的 `obs=` 字段有四种取值：

| 取值 | 含义 | 排查方向 |
| --- | --- | --- |
| `未配置` | 没注入提取器 | **配置问题** |
| `失败` | 注入了但抛异常 | **上游问题** |
| `不可用` | 模型说这段媒体看不出东西 | **正确行为**，不是错误 |
| `N动作/M物体` | 成功 | — |

初版只区分了两种，于是「未配置」与「失败」显示成同一句话
（见 `BUGS.md` B25 —— 与 B24 同一类错误，**记完之后立刻复发**）。

### 声学提取失败时，观察不丢

原本 `feature_extractor` 抛异常时节点**只返回一个错误**，用户什么都看不到。
现在改为：退回 `TEXT_ONLY` 但**保留观察证据**，并在 `limitations` 里说清
「这是模型的描述，不是测量」。

> 只返回一个错误，等于把已经拿到的信息丢掉。

### 预填标注动作

观察到的动作进入 `AgentState.pending_action_suggestions`，
随 `/v1/interpret` 响应返回，供客户端**预填标注表单**。

这直接攻击标注负担（`docs/03` L1b 记为「产品成败关键」）：
录完自动填上「抓门」，主人只需确认或改一下 ——
从「想 + 选 + 写」降到「看一眼 + 点确认」。

⚠️ **它只是候选。** 未经确认的模型输出不得成为 `MeowRecord.actions`，
主人提交时仍然自己选定。

## 3.13 provider 模式必须可见（决策 D45）

真实模型需要 `DASHSCOPE_API_KEY`，而**没配密钥时系统会退到 mock 而不报错**。
不把这个状态暴露出来，一次演示会**静默地变成假演示** ——
输出看起来正常，只是内容是写死的。

### 三态，不是两态

| 取值 | 条件 |
| --- | --- |
| `mock` | 三个全是**已知**占位实现 |
| `live` | 三个全是**已知**真实实现（`OpenAICompatLLM` / `OpenAICompatEmbedder` / `OpenAICompatVision`） |
| **`unknown`** | 其余一切（混合 / 未知实现） |

**两侧都用白名单。** 初版是 `all(isinstance(p, _MOCK_TYPES))` 两分，
于是「`MockLLM` + 自定义桩」被报成 `live` ——
**而那是危险方向的假阴性**（见 `BUGS.md` B26）。

> **声称 `live` 需要有正面证据**，不能从「它不是已知的 mock」推出来。

代价是不对称的：

| 误报方向 | 后果 |
| --- | --- |
| mock → live | **一次假演示看起来像真演示** |
| live → mock | 多一个警告，无实质损失 |

### 暴露位置

| 位置 | 内容 |
| --- | --- |
| `GET /healthz` | `providers: {mode, llm, embedder, vision, *_model, *_endpoint, mixed}`（**不需要鉴权**，便于探活时核对；**不含密钥**） |
| 每个 `TurnResponse` | `provider_mode` + `mock_notice`（非 live 时给出显式提示） |

`mode` 只看类名不够 —— `OpenAICompatLLM` 是中性的，看不出在调哪一家。
所以多厂商（D46）后还暴露**模型名与端点**（见 §3.14）。

`_MOCK_TYPES` 含 `UnavailableVision`（显式缺失的占位）：否则
`MOCK_PROVIDER=1` 会被报成 `unknown`，把排查引向错误方向。

`UNTRUSTED_MODES = {"mock", "unknown"}` —— **`unknown` 与 `mock` 同等对待**。
无法确认是真模型时，应当告诉调用方别当真。

### 为什么是**推断**而不是传参

`create_app` 不接收 `is_mock` 参数 —— 它推断。

理由：**调用方会忘记传的参数**正是 B22 的失败模式（工厂加了参数但上游没传 →
能力静静地不存在）。推断不会被忘记。

代价是白名单要维护（新增 provider 实现时要加进去）。
这个代价是明确的，而「有人忘记传参」是静默的。

## 3.14 多厂商：每个能力一份配置（决策 D46）

### 为什么必须能拆

四类能力在各家的覆盖不同：

| | LLM | 视觉 | 向量 | 多模态事实提取 |
| --- | --- | --- | --- | --- |
| DashScope | ✅ | ✅ | ✅ | ✅ |
| 火山方舟 | ✅ | ✅ | ✅ | ❌ **未实现**（见下） |
| DeepSeek | ✅ | △ | ❌ | ❌ |

绑在一条配置上就没法用「A 家 LLM + B 家向量」——
而 DeepSeek 恰恰是必须混用的那一家。

### 结构

`CapabilityConfig`（`api_key` / `base_url` / `model` / `path` / `timeout_s` / `dim`）
**每个能力各一份**，装在 `ProviderConfig` 里。
`build_config()` 从环境变量解析，`build_providers()` 装配。

| 层次 | 变量 |
| --- | --- |
| 供应商 | `PET_AGENT_PROVIDER=dashscope\|ark`，或按 key 名推断（`ARK_API_KEY` / `DASHSCOPE_API_KEY`） |
| 逐能力覆盖 | `PET_AGENT_<能力>_{MODEL,BASE_URL,PATH,API_KEY,TIMEOUT_S}` |
| 裸密钥 | `PET_AGENT_API_KEY`（不携带供应商身份 → 用**有文档的默认供应商**） |

### 「未实现」必须表现为缺能力

方舟的视频/音频理解走 **Responses API**（形状未验证，不实现）。
所以方舟预设里**根本不声明** `multimodal_model` —— 该能力为 `None`，
调用方按「未配置」降级。

曾经它填的是 `doubao-embedding-vision-*`（一个 **embedding** 模型）
却配在 `/chat/completions` 路径上：一个模型名与端点互相矛盾的配置，一调即 400。

> **「未实现」不能表现为「填一个看起来像配置的东西」。**
> 回归测试：`tests/test_providers.py::TestArkMultimodalIsAbsent`。

### 可见性

只看类名看不出在调哪一家，所以 `/healthz` 的 `providers`
除类型名外还带 `*_model` / `*_endpoint` / `mixed`（是否混用），**始终不含密钥**。

### 运行时装配是改造的一部分

`create_app` 是依赖注入的（利测试），但此前**没有任何入口**把真实依赖装进去：
Dockerfile 里的 `uvicorn app.api.main:create_app --factory` 会以零参调用一个
全是必填 kw-only 参数的工厂，**必然 TypeError**。
后果不是「容器起不来」，而是**多厂商配置层从未真正生效**（`build_providers` 只被测试调用过）。

`app/bootstrap.py` 补上这一步：环境变量 → `build_providers` → `create_app`，
并把「缺鉴权密钥」做成**拒绝启动**（fail-closed）——
否则 `user_id` 可伪造，多租户隔离主张不成立（D5）。

## 3.15 会话记忆与全链路可追溯（决策 D47）

### Session 层曾「写了但从不读」

§3.5 把记忆分三层，而 Profile 与 Episode 都被注入，**Session 层只有写入**：
`/v1/chat` 把每轮存成 `SessionMessage`（供日报），对话本身却看不到历史。
于是多轮指代（「那它为什么这样」）在结构上无从谈起。

补上的链路：

```text
X-Session-Id → 中间件（缺省生成）→ initial_state → load_context
                                                  ├─ session_context（标识 / 轮数）
                                                  └─ recent_turns（最近 10 轮）
                                                       └─ 分区注入 → companion_agent
```

预算两条一起用（拦的是不同的失控）：**最多 20 条消息（≈10 轮）** 与 **1500 字符**。
超出从**最旧**丢，并把「截断 N 条」写进 `node_trace` ——
静默截断会让「模型没提过」与「历史被丢掉了」看起来一样。

### 注入必须**分区**，否则开一条读入式自我强化

历史里含 **assistant 自己的回复**。把它与 `known_facts` 同栏注入，
模型上一轮的推测就会被当成「已知事实」回灌 —— 这与不变量 I1
（系统推断不得以 ACTIVE 写入）是同一个失败模式，只是通道从**写入**换成了**读入**。

所以注入块分栏，且历史栏带显式免责：

| 栏位 | 内容 | 可否当事实 |
| --- | --- | --- |
| `known_facts` | 已确认记忆（带 `source` / `confidence`） | ✅ |
| `unconfirmed` | PENDING 系统推断 | ❌ |
| **`recent_turns`** | 最近对话（含 assistant 回复） | ❌ **当时的推测或措辞** |

### 守卫必须同步，否则要么误杀、要么放行

原先的规则是「检索为空 → 禁止『你之前说过』类断言」。历史注入后它会**误杀**
合法引用（主人确实说过，只是没进长期记忆）。所以按**依据强度**把 cue 分两组：

| cue | 依据 |
| --- | --- |
| 「根据记录」「档案里写着」 | **必须**有检索到的记忆 |
| 「你之前说过」「我记得它」 | 有记忆，**或主人自己说过的话**（assistant 的历史**不算**） |

### 全链路可追溯：`session_id` 落到每个实体

session **不是隔离键**（隔离仍是 `user_id` + `pet_id`），它回答「**这是哪一轮**」：

| 实体 | 追溯什么 |
| --- | --- |
| `SessionMessage` | 会话注入 + 日报 |
| `PendingInterpretation` | 标注归属（案例来源是**录叫声那一轮**，不是补标那一轮） |
| `MeowRecord` | 案例来自哪一轮 |
| `HealthRecord` | 结构化信号来自哪次对话（日报聚合跨会话 → `None`） |
| `MemoryEvent` | 审计：这条长期记忆由哪一轮产生 |

业务响应与**响应头**都回传 `session_id` / `trace_id`；list 端点支持 `?session_id=` 过滤。

### LangSmith：`trace_id` 就是 run id

本地 `node_trace` 只活在单个响应里，跨请求不可查。接入 LangSmith 后每次请求
是一棵可回放的调用树。关联方式不是「再存一张映射表」，而是**同一个标识**：

| `trace_id` 形态 | LangSmith `run_id` |
| --- | --- |
| UUID（默认） | **原样使用** —— 字面相同 |
| 客户端自定义串 | `uuid5(namespace, trace_id)` 确定性派生 |

两种情况下 `trace_id` 都写进 `metadata`，可在 LangSmith 按它检索。

**失败姿态**：观测不是正确性路径 —— LangSmith 不可达**不**让对话失败（fail-soft）；
但启用状态与错误暴露在 `/healthz`，不静默。测试中强制关闭
（`conftest.py` 设 `PET_AGENT_TRACING=0`），否则跑测机器上恰好有 key 就会真的外发。

# 5. 视觉与健康

## 5.1 多模态观测：三个有文献依据的可测量项

**它不解决拟人化问题，它扩展事实层**——把「不知道」的范围缩小：

```
可测量区（事实层可说）
  无多模态：  外貌 / 品种
  加多模态：  + 体况 / 面部疼痛信号 / 姿态 / 呼吸频率
仍不可知：  内脏疾病 / 精确需求 / 主观体验 → 仍禁止编造
```

**关键推论**：

| 输出 | 多模态之后 | 归属 |
| --- | --- | --- |
| 「照片里耳朵后压、眼睑半闭，FGS 耳位 1 分」 | ✅ 可以说了 | `fact_layer` |
| 「本喵肚子疼」 | ❌ **仍然禁止** | `companion_layer` |

### FGS · 面部疼痛评估

| 项 | 内容 |
| --- | --- |
| 来源 | Evangelista et al., *Sci Rep* 2019, [doi:10.1038/s41598-019-55693-8](https://doi.org/10.1038/s41598-019-55693-8) |
| 性质 | **验证过的**猫急性疼痛量表 |
| 5 个动作单元 | 耳朵位置 / 眶周收紧 / 口吻部紧张 / 胡须位置 / 头部位置 |
| 计分 | 每项 0–2，另有「无法评分」选项 |
| 已知难点 | 文献指出：**即使对专家，猫也是疼痛评估上出了名困难的物种** |
| 自动化研究 | [手机端 CNN+XGBoost](https://pmc.ncbi.nlm.nih.gov/articles/PMC10703818/)（3447 张标注图、37 landmark） |

### SRR · 静息呼吸频率（**优先做这个**）

| 项 | 内容 |
| --- | --- |
| 地位 | **兽医明确让主人在家测的项目**，用于监测心衰发展 |
| 背景 | HCM 约 **1/7** 猫受影响，是 9 岁以上猫主要死因 |
| 为什么在家测 | **到院应激会加重病情**，远程监测优于门诊复查 |
| 测法 | 猫睡着时数 60 秒胸廓起伏 |

> **我们不是在教育用户一件新事，而是替兽医做他已经让主人做的事。**

### BCS · 体况评分

[Front Vet Sci 2025](https://doi.org/10.3389/fvets.2025.1604557) 研究「仅凭照片能否评估猫 BCS」，
同时发现 **inter-evaluator bias**——评估者之间本身就有分歧，意味着存在准确率上限。

## 5.2 关键区分：方法是验证过的，实现没有

| | 已发表的工作 | 通用 VLM 零样本 |
| --- | --- | --- |
| 模型 | **专门训练**的 CNN | Qwen-VL |
| 验证 | 有量化指标 | **无** |
| 条件 | 受控拍摄 | 主人随手拍 |

**通用 VLM 做 FGS 这个组合没有任何人验证过。**

| 阶段 | 做法 |
| --- | --- |
| 起步 | 通用 VLM 出**分项评分** |

| 门槛 | 达不到 → **不输出总分**，只输出原始观察描述 |

## 5.4 健康模块：监测与分诊，不是诊断

### 合规依据

《动物诊疗机构管理办法》（农业农村部，2022-10-01 施行）：

- **第二条**：动物诊疗指疾病预防、**诊断**、治疗等**经营性活动**，含**填写诊断书**
- **第五条**：实行动物诊疗**许可制度**
- **第十九条**：**执业兽医师**方可从事诊断、治疗、填写诊断书

**推论**：健康数据记录、异常检测、就医建议**不属于**诊疗活动。

### 三不原则

| 原则 | 说明 |
| --- | --- |
| **不诊断** | 不输出疾病名称作为结论 |
| **不排除** | **永不输出「健康」「没问题」「正常」「放心」** |
| **不阻塞** | 红旗命中时健康提示必须**抢占**其他输出 |

### 双轨检测

```
        ┌──────────────────────┐
        │  健康信号采集         │
        └──────────┬───────────┘
     ┌─────────────┴─────────────┐
     ▼                           ▼
┌──────────────────┐   ┌──────────────────┐
│ Track A 红旗规则  │   │ Track B 基线漂移  │
│ 确定性·不学习     │   │ 稳健统计·个体化    │
│ 命中 → L3        │   │ 偏离 → L1/L2     │
└──────────────────┘   └──────────────────┘
```

| | Track A | Track B |
| --- | --- | --- |
| 目标 | 已知**急性**危险 | 未知**渐进**变化 |
| 方法 | 确定性规则 | 稳健统计（MAD / CUSUM） |
| **可否学习** | **绝对不可** | 必须学习 |

**为什么红旗不能学习**：学习型系统会**把罕见的高代价事件优化掉**。

**本期范围**：只做 Track A + 数据模型；Track B 留接口（需 21 天基线，demo 场景跑不出）。
> 但若 SRR 每天测一次，21 天基线就从「跑不出来」变成「产品自然积累」——这个死结被解开了。

### 非对称代价

| 错误 | 代价 |
| --- | --- |
| **假阴性**（该报没报） | 猫可能死亡 —— **不可接受** |
| **假阳性**（虚惊一场） | 多跑一趟医院 —— **可接受** |

**因此红旗阈值偏向过度触发**（优化 recall，牺牲 precision）。
这与通用 AI 产品（优化「减少打扰」）**方向相反**。

### 红旗规则是数据，不是代码

存放在 `data/health/red_flags.yaml`，带版本、来源引用与审核状态。
**未审核的规则不得上线**（`reviewed_by: null` 表示尚未经兽医审核）。

加载期校验：

- 规则只能引用 `signal_vocabulary` 里定义过的信号 ——
  **拼写错误会让规则静默失效**，而一条永远不命中的安全规则比没有它更危险
- 已启用的规则必须有 `sources`（可回溯）
- 未启用的规则必须写 `disabled_reason`（否则「为什么不启用」无人可查）

### 求值用**三值逻辑**：真 / 假 / **无法评估**

**「信号缺失」与「未命中」是完全不同的事。**

```
litter_box.urine_output = none   →  命中（危险）
litter_box.urine_output = normal →  未命中
litter_box.urine_output 没采集到   →  **无法评估** ← 不能当成「未命中」
```

- `any_of`：任一 True → True；否则任一无值 → **None**；否则 False
- `all_of`：任一 False → False；否则任一无值 → **None**；否则 True
- **规则只在结果为 True 时命中**；无法评估的规则进 `undecidable` 列表

`undecidable` **必须被使用** —— 它决定了是否给出 `INSUFFICIENT_DATA`。
丢掉它就等于把「没看」说成「没事」。

> ⚠️ 信号「已采集但值为 `None`」**也算无法评估**。
> 这是个容易写错的地方：字典里有这个键、看起来有数据，
> 但 `None >= 5` 在 Python 里会返回 `False` ——
> 于是「不知道」被静默地变成了「未命中」。

#### 覆盖率门限只拦一个方向（B21）

| 情形 | 正确输出 |
| --- | --- |
| 覆盖率低 + **无命中** | `INSUFFICIENT_DATA`（「没测」不得变成「没事」） |
| 覆盖率低 + **有命中** | **保留命中级别**（已存在的危险不因别的没测而失效） |

初版把两个方向写到了一条规则里，结果**已命中的急诊红旗被压成「数据不足」**。
详见 `docs/BUGS.md` B21。

### 5.4.1 健康模块**不接运行时 RAG**（决策 D37）

**结论：L3 不加运行时检索。** 理由四条，按重要性排序：

#### ① 它把确定性安全网换成概率检索，而检索失败是静默的

本节已经写了「红旗**绝对不可**学习」，理由是
**学习型系统会把罕见的高代价事件优化掉**。

**RAG 的失败模式与这个顾虑完全同源：**

```
recall@k = 0.85
  → 15% 的危险情况检索不到相关文档
  → 系统输出「未发现异常」
  → 而系统无法区分「确实没风险」与「检索失败」
```

这正是 B3（零填充是静默编造）在安全网上的同构形态：
**检索未命中是静默漏报。** 而假阴性的代价是猫可能死亡。

#### ② 它让「越界」**更**可能，而不是更少

法律边界是「不诊断」。而 RAG 检索到的是**临床文献**：

```
检索段落：「猫呕吐的鉴别诊断：异物、胰腺炎、CKD、淋巴瘤…」
```

喂给 LLM 会长出读起来像建议的临床内容，而且**有真实文献支撑** ——
更有说服力，更难与诊断区分。

#### ③ 文献的「适用性」问题（最隐蔽）

文献写给**兽医**、关于**群体**、出发点是**鉴别诊断**。给主人看的结果：
焦虑放大（一串病名）或反向（「异物」听起来罕见→大概没事）——
**两者都不是分诊，都是诊断邻域**。且文献**不知道这只猫的历史**。

#### ④ 「沉淀语料」这个动机本身要审视

| 问题 | 说明 |
| --- | --- |
| 版权 | 兽医教材/期刊有版权，灌进产品是**许可问题** |
| 时效与责任 | 引用了过时文档即制造责任。谁更新？谁负责？ |
| 追责链 | 现在是「建议就医」（不构成主张）；加了 RAG 就变成「根据 XX 文献，这可能是 Y」——**对这只猫的主张，且带出处** |

### 但两个位置是合法的

| 位置 | 可行 | 关键区别 |
| --- | --- | --- |
| **离线辅助起草红旗规则** | ✅ | 最终判断由**人签字**；失败模式是「提议被否」而非「静默漏报」；责任有归属 |
| **常识问答**（踩奶/呼噜/饮水） | ✅ | 但它属 **L1/L2**，不是 L3 |

**关键不是「RAG 好不好」，而是「它进哪个层」。**
一旦进 L3，就要受三不原则约束（不诊断、不排除、不阻塞）——
而 RAG 的输出天然倾向违反前两条。

> `red_flags.yaml` 已经有 `sources: []` / `enabled: false` / `reviewed_by: null`
> 三个字段 —— 那正是一个「待审提案」的形状。
> **但位置一的前提是「有兽医可签」**；没有的话它只是在批量生产没人审的提案。

> **安全网的每一条都必须有人签字。**
> 「用语料库自动扩展安全网」听起来高效，实际上是把责任转移给了一个
> 没有责任能力的系统。

### 5.4.2 健康信号的落地（已闭环）

此前 `app/memory/flywheel.py` 拒绝 `EventType.HEALTH` 进通用记忆，
理由是「健康信号另走 health_records 表」——**但那张表没有接收方**。
于是健康信号「记忆层拒了、日报显示了、没地方存」。

现在闭环：

```
对话 → app/digest 提取（quote 校验）
          │
          └─► HealthSink（app/health/HealthWriter）
                    │
                    ├─► health_records 表（独立 store，数据策略不同）
                    └─► 红旗求值 → HealthAssessment
```

**两条通道必须分开：**

| 通道 | 值 | 能否触发红旗 |
| --- | --- | --- |
| 对话提取（`admit_digest_candidates`） | **一律 `None`** | ❌ |
| 结构化信号（`record_signal`） | 有值 | ✅ |

**对话文本一律 `value=None`，不解析中文数词。**
理由：把「吐了**两次**」解析成 2 需要中文数词识别 ——
B11/B12 已证明这条路不可靠，而且**错了会误触红旗**。
`None` 的后果是这条信号进 `signals_missing`，评估给出 `INSUFFICIENT_DATA` ——
那是诚实的：系统知道「主人提到了呕吐」，也知道「我不知道几次」。

| 规则 | 状态 | 依据强度 |
| --- | --- | --- |
| `urinary_obstruction` | ✅ enabled | 强（4 份来源一致） |
| `respiratory_distress` | ✅ enabled | 强 |
| `neurological_emergency` | ✅ enabled | 强 |
| `hemorrhage_or_toxin` | ✅ enabled | 强 |
| `anorexia_prolonged` | ⛔ disabled | 阈值来源不一致 |
| `persistent_gi_signs` | ⛔ disabled | 仅消费者科普来源 |
| `mucosa_abnormal` | ⛔ disabled | 依赖主观颜色判断 |

**尿闭值得单说**：MSD 兽医手册指出主人**常把尿闭误认为便秘**。
而系统同时持有叫声特征、砂盆行为记录、时间序列、性别——
**这正好覆盖了人类失败的原因（单次观察、缺乏对照、误判归因）**。

> 系统的优势是**纵向记忆**，不是医学知识。

### 覆盖率与「无法评估」

| `coverage` | 行为 |
| --- | --- |
| < 0.3 | **只输出「数据不足，无法评估」**，禁止任何趋势判断 |
| 0.3–0.6 | 可输出 L1 观察，必须标注覆盖率与限制 |
| ≥ 0.6 | 正常分级 |

**硬规则**：覆盖率不足时输出「未发现异常」是**禁止的**——
那会把「我没数据」伪装成「它很健康」，是本模块最危险的失败模式。

### 禁止清单（`health_guard` 强制）

1. 输出疾病名称作为结论
2. 出现「健康」「没问题」「正常」「放心」
3. 建议用药、剂量、人用药
4. 覆盖率不足时输出「未发现异常」
5. 省略 `disclaimer`
6. 给出生存期/预后判断
7. 用「它得了 X」句式
8. **修饰 L3 紧急度**（弱化、延迟建议）

## 6.1 按可判定性分层

**不要对所有评测项都声称可靠性。** 分层处理：

| 层 | 评测项 | 判定方式 | 可否声称可靠性 |
| --- | --- | --- | --- |
| **A. 客观可判定** | 幻觉、租户隔离、去重强化、冲突判定、不变量、覆盖率门禁 | 确定性：比对数据库/结构 | ✅ **主力** |
| **B. 有参考标准** | 声学情境分类、SRR、FGS | 人工标注/兽医评分 | ◐ 需说明污染与一致性 |
| **C. 需主观判断** | 角色一致性、措辞自然度、建议有用性 | LLM-as-judge | ⚠️ 只报告**相对比较** + 标注一致性 |

### A 层是主力

不依赖模型、可复现、跑得快，且直接对应核心主张。已部分实现（92 项契约测试）。

### B 层要主动说明污染风险

如果先验来自 CatMeows，测试集也来自 CatMeows，那测的是**拟合先验的能力**，不是泛化能力。
诚实的做法：**21 只猫里留 4 只做 hold-out，不参与先验统计**。

### C 层不要声称绝对值

只报告**配置 A vs B 谁更好**，并给出标注一致性
（多人标注的 Cohen's κ，或 LLM-as-judge 与人工的一致率）。

## 6.3 基线与消融

**没有基线的数字没有意义。**

| 主张 | 基线 | 实验组 | 指标 |

| 混合检索更好 | naive top-k | + 结构化预过滤 + 重排序 | E11 / E12 |

| 守卫有效 | 无守卫 | + `response_guard` | E31–E33 |
| 声学证据更强 | `text_only` | 声学 + 个体 + 先验 | E21 |
| **防自我强化必要** | 允许 `SYSTEM_INFERENCE` 为 ACTIVE | 当前规则 | **幻觉率随轮次增长曲线** |

**最后一条特别有说服力**：故意跑一个被污染的配置，展示错误如何随轮次放大。
**用一个实验证明某个约束是必要的。**

**消融须用配置开关**（`ABLATION_NO_GUARD=1`），同一套代码跑不同配置，
而不是维护两份代码——这样消融才是可复现的。

## 7.2 收敛建议

**要有始有终，不要样样半成品。** 范围收敛——**业余估算旧范围 3–5 个月，远超可行区间**：

| 项 | 建议 | 理由 |
| --- | --- | --- |
| **S1 全套（记录/时间线/分轨/触达/摘要）** | **整体暂缓** | 先验证「用户是否愿意记录」。不验证就做，可能做完发现没人用 |
| **主动触达** | 暂缓 | 无推送渠道，做了也跑不通 |
| **FGS** | 降为可行性实验 | 技术赌博，不应占用主线预算 |
| 规划层 | 不实现 | 保留设计即可 |
| 多用户 | 砍掉 | 只留数据层隔离 |
| 完整鉴权体系 | 最小 token 验证 | 隔离是正确性问题；但 `user_id` 由客户端自报则隔离主张不成立 |
| Web UI | 够演示即可（单页 + 5 按钮） | 堆前端不体现 AI 工程能力 |
| 微信小程序 | 砍掉 | 审核调试成本高 |
| 多宠物关系推理 | 砍掉 | 场景偏窄 |

### 为什么优先 S2 而不是 S1

| | S2 行为解释 | S1 记录与陪伴 |
| --- | --- | --- |
| 痛点真实性 | **高**（主人真的想知道） | 中（想猫时开相册也够） |
| 替代品 | **几乎没有**（宠物行为解释无成熟产品） | **强**（手机相册、微信） |
| 外部依赖 | **无** | 推送渠道、用户习惯改变 |
| 设计成熟度 | **最高**（贝叶斯 + 证据链已完成） | 中等 |
| 演示效果 | **强**（对数几率归因很直观） | 中 |

**结论**：S1 不是不该做，而是**应该先验证假设再投入**。
S2 是当下唯一同时满足「真痛 + 无替代 + 无依赖 + 设计已完成」的场景。
