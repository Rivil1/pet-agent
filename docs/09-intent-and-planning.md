# 09 · 意图识别与任务分解

> 本文档回答两个能力的体现方式，并**如实指出当前设计的差距**。
>
> 结论先行：
>
> - **意图识别**：当前设计有，但只到 L1–L2，还有明显加深空间
> - **任务分解**：**当前设计基本没有**，只有单意图路由，需要补一个规划层

## 1. 两个能力的深度标志

它们常被一起问，但深度标志完全不同：

| | 意图识别 | 任务分解 |
| --- | --- | --- |
| 本质 | **分类 + 路由** | **规划 + 调度** |
| 浅层做法 | LLM 分到几类 | 拆成几个节点 |
| 深层标志 | 意图边界怎么定、错误代价不对称 | 依赖怎么判、粒度怎么定、并行怎么用 |
| 当前状态 | L1–L2 | **未做** |

# 第一部分：意图识别

## 2. 深度阶梯

| 级别 | 特征 | 典型说法 |
| --- | --- | --- |
| L0 | LLM 分类到 N 类 | 「我用大模型做意图识别」 |
| L1 | + 槽位抽取 + 置信度阈值 | 「低于阈值就问用户」 |
| L2 | + 多轮上下文（指代消解、省略补全） | 「我做了查询改写」 |
| L3 | + **意图边界按下游行为差异划分** + **代价敏感阈值** + 复合意图 | 见下 |

## 3. L3 要点一：意图边界**按下游动作差异**划分

**这是最被低估的一点。** 多数人按「语义主题」划分意图：

```
❌ 按主题：咨询类 / 记录类 / 闲聊类 / 翻译类
   → 边界模糊，且无法解释为什么这么分
```

**正确的划分标准**：

> 两个意图如果在下游的**动作、约束、失败处理**上完全一致，就应该合并。
> 只有下游行为不同，才值得单独成一类。

### 用本项目验证这个标准

当前 6 个意图：

| 意图 | 下游动作 | 关键约束 | 是否值得独立 |
| --- | --- | --- | --- |
| `CHAT` | retriever → companion | 可写记忆（推断进 PENDING） | 基准 |
| `MEMORY_QUERY` | retriever → companion | ① `retrieval_k=8` ② `rejection_strict` ③ **`memory_write=FORBIDDEN`** | ✅ |
| `TRANSLATE_BEHAVIOR` | interpreter | **必须走概率计算 + 证据链**；无音频时禁止输出数值置信度 | ✅ |
| `PROFILE_UPDATE` | analyzer | **必须用户确认后才写入** | ✅ |
| `RECORD_EVENT` | extractor → writer → guard | **响应须报告写入结果**，故写入早于响应 | ✅ |
| `COMPOUND` | planner → fan-out | 走慢路径，需分解、依赖分析与调度 | ✅ |

### 边界修正：`CHAT` vs `MEMORY_QUERY` 的真实差异

**原文档的论证是错的。** 曾声称 `MEMORY_QUERY` 有「强制的拒答约束」而 `CHAT` 没有——
但 `retrieval_note` 是 `ContextInjectionBlock` 的默认字段，**所有意图都带**
（见 [10-self-review.md](10-self-review.md) A1）。

**真实差异在「动作许可」：**

| 维度 | `CHAT` | `MEMORY_QUERY` |
| --- | --- | --- |
| 性质 | 对话 | **审计** |
| `memory_write` | `ALLOWED` | **`FORBIDDEN`** |
| `retrieval_k` | 5 | 8 |
| `rejection_strict` | False | True |

`MEMORY_QUERY` 的本质是**用户要求系统复述它已知的**——这是一个**审计**动作。
而审计不得产生新记录，否则会污染被审计对象。**这是审计的基本原则。**

所以差异是**动作许可**（行为差异），不是参数差异，判据仍然成立。
这条约束已被编码为结构性校验：`IntentPolicy` 会拒绝
`MEMORY_QUERY + memory_write=ALLOWED` 的组合。

> 面试表述：
> 「我的意图边界不是按语义主题划的，是按**下游行为差异**划的。
> 比如闲聊和记忆查询走同一条链路，但它们分开——
> 因为记忆查询是一次**审计**：用户要求系统复述它已知的信息。
> 审计不得产生新记录，否则审计就污染了被审计对象，
> 所以我禁止这个意图把推断写回记忆，而闲聊允许。
> 这是动作许可的差异，不是参数差异。
>
> 两个意图如果下游动作、约束、失败处理都一样，我就把它们合并。
> 而这条边界是我几条里最弱的，如果要简化意图体系，它是我第一个会合并的。」

## 4. L3 要点二：代价敏感阈值（不是一条阈值）

**分类错误不是等价的。** 不同误判的代价差异极大：

| 误判方向 | 后果 | 用户何时发现 | 代价 | 策略 |
| --- | --- | --- | --- | --- |
| `RECORD_EVENT` → `CHAT` | 用户以为记住了，实际没记 | **很久以后，或永远不发现** | 🔴 高（静默失败） | 需高召回 |
| `CHAT` → `RECORD_EVENT` | 闲聊内容被写成记忆 | 可能很久以后 | 🔴 高（**污染长期记忆**） | 需高精确 |
| `TRANSLATE_BEHAVIOR` → `CHAT` | 少一次解释机会 | 立刻，用户会再问 | 🟡 中 | 中阈值 |
| `CHAT` → `TRANSLATE_BEHAVIOR` | 对无音频输入走解释链路 | 立刻 | 🟡 中 | 中阈值 |
| 任意 → `AMBIGUOUS` | 多问一句 | 立刻 | 🟢 低 | 宁可问 |

**结论：不存在一条全局阈值，每个意图对都有自己的阈值。**

### `RECORD_EVENT` 的特殊处理

注意上表：`RECORD_EVENT` 的**两个方向代价都高**——
误判成它 → 污染记忆；被误判走 → 静默丢失。

**精确率和召回率都不能牺牲时，靠阈值是解决不了的。**
正确做法是**改变交互范式**：

```
❌ 靠阈值二选一
✅ 执行 + 明确反馈：
   识别到可能是记录请求 → 执行写入 → 明确回复「已记录：…. 记错了请告诉我」
   → 假阳性由用户一句话纠正，假阴性由系统反馈消除
```

**这是一个重要设计原则**：

> 当某类错误的两个方向都昂贵时，不要优化分类器，要**改变交互设计**——
> 让用户能以极低成本纠正错误。

**面试表述**：

> 「我发现记录类意图的误判代价在**两个方向上都高**：
> 误判成它是污染记忆，漏判是静默丢失。
> 精确率和召回率都不能牺牲时靠阈值是解决不了的，
> 所以我改成了『执行 + 明确反馈』——直接写入并明确告知已记录内容，
> 用户一句话就能纠正。这比调分类器有效。」

## 5. L3 要点三：多轮指代与省略

单轮分类不够，宠物场景大量出现省略和指代：

| 用户输入 | 缺失信息 | 如何补全 |
| --- | --- | --- |
| 「它今天怎么样？」 | `它` = 哪只猫 | 从 `SessionContext` 的当前宠物解析 |
| 「那它为什么这样？」 | `这样` = 什么行为 | 从上一轮解释结果解析 |
| 「还有呢？」 | 查询对象 | 沿用上一轮意图与槽位 |

**这需要 `understand_input` 读取会话上下文，而不是只看当前轮。**

这也是查询改写（query rewriting）在 RAG 侧的落点——
「它为什么这样」改写为「团团在门口叫的原因」才能检索对。

## 6. 意图识别的评测

**不能只看 accuracy。** 要报告三样：

| 指标 | 用途 |
| --- | --- |
| **混淆矩阵** | 看出错在哪些意图对上 |
| **per-class F1** | 小类别（`RECORD_EVENT`）是否被淹没 |
| **代价加权错误率** | 用 §4 的代价表加权，才是真实业务指标 |

以及一条专用的安全指标：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| **污染率** | `CHAT` 被误判为 `RECORD_EVENT` 且实际写入记忆的比例 | 越低越好（记忆污染不可逆） |
| **静默丢失率** | `RECORD_EVENT` 被误判为 `CHAT` 的比例 | 越低越好 |
| **该问未问率** | 应为 `AMBIGUOUS` 但被强行分类的比例 | 关键指标——**该问的时候有没有问** |

> 「该问未问率」是这套评测里最有价值的一项。
> 它直接度量系统是否遵守了「宁可多问一句」的设计原则。

# 第二部分：任务分解

## 7. 诚实的现状评估

**当前设计只有单意图路由，没有任务分解。**

```
当前：  输入 → 分类到 1 个意图 → 走 1 条固定链路 → 输出
缺失：  输入 → 识别为复合请求 → 生成子任务 → 依赖分析 → 调度 → 合并 → 输出
```

| 任务分解的要素 | 当前是否有 |
| --- | --- |
| ① 复合请求识别 | ❌ |
| ② 子任务生成（plan） | ❌ |
| ③ 依赖分析 | ❌ |
| ④ 调度（串行 / 并行） | ❌（全串行） |
| ⑤ 结果合并 | ❌ |
| ⑥ 部分失败的恢复 | ◐ 仅有整链降级 |

**所以：目前这个项目可以讲意图识别，但讲不了任务分解。** 需要补。

## 8. 分解的判据：按**决策点**拆，不按数据流拆

这是先要确立的标准，否则会拆错。

**错误做法**（按数据流拆）：

```
取档案 → 取记忆 → 拼 prompt → 调模型 → 后处理
         ↑ 这些是步骤，不是任务。拆开只会增加编排开销与状态膨胀
```

**正确做法**（按决策点拆）：

> 一个节点值得独立，当且仅当它**产生了影响后续路径的决策**，
> 或者**有独立的失败模式需要单独降级**。

用这个标准检验当前节点：

| 节点 | 是决策点吗 | 独立失败模式 | 值得独立 |
| --- | --- | --- | --- |
| `understand_input` | ✅ 路由决策 | ✅ | ✅ |
| `behavior_interpreter` | ✅ 概率计算 + 分档 | ✅ | ✅ |
| `response_guard` | ✅ **放行/重写/降级** | ✅ | ✅ |
| `memory_writer` | ✅ 写入/待确认/拒绝 | ✅ | ✅ |
| `memory_retriever` | ◐ 仅取数 | ✅ 空结果需处理 | ✅（弱） |
| `tts_output` | ❌ 纯转换 | ✅ 失败可静默 | ◐ |

**反例说明**：如果把「检索 + 生成」合成一个节点，
就无法回答「是检索错了还是生成错了」，也无法单独评测。

**面试表述**：

> 「我拆节点的标准不是按数据流，是按**决策点**。
> 一个节点值得独立，是因为它产生了影响后续路径的决策，或者有需要单独降级的失败模式。
> 反过来，我刻意没有把『取档案』和『取记忆』拆开——它们是数据获取，不是决策，
> 拆开只会增加编排开销和状态膨胀。」

## 9. 补什么：规划层（Plan–Execute）

要真正体现任务分解，需要一个规划层：

```
                        ┌──────────────────┐
   复合请求 ──────────►│ understand_input │  意图 = COMPOUND
                        │  + 子意图列表     │
                        └────────┬─────────┘
                                 ▼
                        ┌──────────────────┐
                        │  planner         │  ① 生成子任务
                        │                  │  ② 依赖分析
                        │                  │  ③ 拓扑排序
                        └────────┬─────────┘
                                 ▼
                  ┌──────────────┼──────────────┐
                  ▼              ▼              ▼
            ┌──────────┐  ┌──────────┐  ┌──────────┐
            │  T1      │  │  T2      │  │  T3      │  可并行
            │record    │  │interpret │  │aggregate │
            └────┬─────┘  └────┬─────┘  └────┬─────┘
                 └─────────────┼─────────────┘
                               ▼
                      ┌──────────────────┐
                      │  result_merger   │  ④ 合并 / 冲突检测
                      └────────┬─────────┘
                               ▼
                      (后续 guard → tts → writer)
```

### 9.1 依赖分析的本质

**不是看数据流，而是看：一个子任务的输出是否改变另一个子任务的输入分布。**

这个说法很关键，因为它能捕捉**非平凡依赖**。举例：

```
用户：「团团最近总在门口叫，帮我记一下。它是不是想出去？顺便看看这个月是不是比上个月叫得多」

T1: 记录事件（"最近总在门口叫"）
T2: 解释行为（scene = 门口）
T3: 聚合统计（本月 vs 上月 叫声次数）

朴素依赖分析：T1、T2、T3 数据流上互不依赖 → 全部并行
        ↑ 漏掉了真实依赖！
```

**真实依赖**：`T3` 的统计结果改变 `T2` 的先验——

如果「本月叫声显著多于上月」，那么 `T2` 中 `door_attention` 的**场景先验应该上调**
（高频重复的叫声更可能是持续性诉求，而非偶发）。

所以依赖是 `T3 → T2`（**先验注入**，不是数据传递）。

**这是任务分解里最容易被忽略、也最能体现水平的地方**：
依赖不只来自「谁的数据喂给谁」，还来自「谁的结果改变谁的先验」。

**面试表述**：

> 「我做依赖分析时不只看数据流，还看**一个子任务的输出是否改变另一个子任务的输入分布**。
> 比如『这个月比上个月叫得多吗』的聚合结果，会改变『它想出去吗』的先验——
> 高频重复的叫声更可能是持续性诉求。
> 所以这两个子任务看着独立，实际有先验依赖，不能完全并行。」

### 9.2 粒度控制

| 拆太粗 | 拆太细 |
| --- | --- |
| 无法定位错误 | 编排开销、状态膨胀 |
| 无法独立降级 | 每步引入 LLM 不确定性 |
| 无法单独评测 | 延迟累加 |

**粒度原则**：停在**决策点**，不要停在中转步骤。

### 9.3 防止过度分解（快慢路径）

简单请求不该走规划层——否则成本与延迟都白涨：

```
understand_input
  ├─ 单意图 & 高置信度 ──► 快路径（直接走固定链路）      ~1s
  └─ 复合意图 / 低置信度 ──► 慢路径（planner → 并行执行） ~4s
```

**需要一个「是否需要分解」的判别器**，并且它本身要可评测（过度分解率）。

### 9.4 部分失败的恢复

任务分解后，失败处理变复杂：

| 情形 | 处理 |
| --- | --- |
| 子任务 `T2` 失败，`T1/T3` 成功 | **部分成功**：返回已完成部分 + 明确说明哪部分失败 |
| 依赖链上的前置任务失败 | 跳过其后继，标记 `skipped` |
| 全部失败 | 整链降级（现有机制） |

**原则不变**：正确性相关降级可见，体验相关降级静默。

## 10. 任务分解的评测

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| **分解准确率** | 复合请求是否被正确拆成子任务集合 | ↑ |
| **依赖正确率** | 发现的依赖与人工标注比对（含先验依赖） | ↑ |
| **过度分解率** | 简单请求被错误地走了 planner | ↓ |
| **计划执行成功率** | 计划中有多少子任务成功完成 | ↑ |
| **部分成功可用率** | 部分失败时，返回结果对用户是否仍有用 | ↑ |

**「依赖正确率」要把先验依赖纳入标注**，否则测不出 §9.1 的能力。

## 11. 两个能力的交界

**它们不是独立的——复合意图识别就是任务分解的入口。**

```
意图识别：判断「这是不是一个复合请求」
    ↓ （如果是）
任务分解：拆成子任务、定依赖、调度、合并
```

所以补规划层会**同时**提升两个能力：

| 补的东西 | 提升意图识别 | 提升任务分解 |
| --- | --- | --- |
| 复合意图检测（多标签） | ✅ L3 | ✅ 入口 |
| 规划层 planner | — | ✅ |
| 依赖分析（含先验依赖） | — | ✅ |
| 并行调度 + reducer | — | ✅ |
| 结果合并与冲突检测 | — | ✅ |
| 快慢路径分流 | ✅（低置信度更倾向慢路径） | ✅（防过度分解） |

| 「任务怎么拆的？」 | 按**决策点**拆，不按数据流。举「没有拆开取档案和取记忆」的反例 |
| 「拆多细合适？」 | 停在决策点；拆太细会增加编排开销和 LLM 不确定性 |
| 「复合请求怎么办？」 | planner 生成子任务 → 依赖分析 → 并行调度 → 合并 |
| 「依赖怎么判断？」 | 不只看数据流，还看**一个子任务的输出是否改变另一个子任务的输入分布**（先验依赖） |
| 「并行能省多少？」 | 需要实测：串行 vs 并行的 p95 延迟 |
| 「会不会过度分解？」 | 快慢路径分流，过度分解率作为评测项 |
| 「子任务失败怎么办？」 | 部分成功可用：返回已完成部分 + 明确说明哪部分失败 |
