# 04 · 记忆系统设计

> 这是本项目最容易被追问的模块。面试官通常会问：
> 「你说你用了 RAG——那**什么该记、什么不该记**？**记错了怎么办**？**前后矛盾怎么办**？」

## 1. 三层架构：关键是**访问模式不同**

| 层 | 内容 | 存储 | 访问模式 | 生命周期 |
|---|---|---|---|---|
| **Profile** 身份层 | 名字、品种、外貌、`must_keep_features`、角色设定 | 关系库（强结构） | **主键直读，不做向量检索** | 长期，低频变更 |
| **Episode** 事件层 | 「昨天它害怕吸尘器」「最近晚上总在门口叫」 | 关系库 + 向量索引 | **混合检索** | 长期，可被取代/遗忘 |
| **Session** 会话层 | 当前对话、最近情绪、当前场景、最近一次解释结果 | Redis / 进程内 | 直读，不检索 | 会话结束即失效 |

### 为什么 Profile 层**不能**走向量检索

这是最容易犯的错误。如果把稳定身份事实塞进向量库：

```
用户问："团团是什么颜色的？"
→ 向量检索 top-3 命中：
   ① 橘白短毛（3 个月前，已过期）
   ② 白色短毛（上次 VLM 抽错，置信度 0.4）
   ③ 橘白，胸口有白毛（当前，正确）
→ 模型看到三条冲突的"事实"，开始和稀泥
```

**身份事实的正确访问方式是主键直读。** 它只有一份、有版本、有明确当前值。
把它扔进相似度检索，等于主动引入不确定性。

> 一句话原则：**能精确定位的数据，不要用相似度去找。**

同理，`Session` 层也不该走向量检索——它就是当前上下文，直读即可。

## 2. 生命周期

```
对话轮次
  │
  ├─► Session 层：立即写入（当前场景、情绪、最近解释）
  │
  └─► 会话结束
        │
        └─► 数据飞轮：候选抽取 → 判定 → 去重 → 冲突 → 路由 → 写入 Episode
                                                        │
                                    高价值且稳定的信息 ──► 提升进 Profile
```

**Session → Episode → Profile 的单向晋升**：

- 短期状态**不会**自动进长期库（"我现在在开会" 是一次性的）
- 长期事件**不会**自动进身份层（"害怕吸尘器" 是一次事件，不是身份）
- 只有**重复出现**的模式才晋升为身份层属性

晋升条件（任一）：

- 同一模式 `support_count ≥ 3` 且时间跨度 ≥ 14 天
- 用户显式陈述（"团团就是很黏人"）
- 用户对系统推断的显式确认

## 3. 写入：数据飞轮的决策管线

```
                    ┌─────────────────────┐
   一轮对话结束 ────►│ 1. 候选抽取          │  LLM + 结构化输出
                    └──────────┬──────────┘
                               ▼
                    ┌─────────────────────┐
                    │ 2. 价值判定          │  值得长期记吗？
                    └──────────┬──────────┘
                          ┌────┴────┐
                     不值得│         │值得
                          ▼         ▼
                       (丢弃)  ┌─────────────────────┐
                               │ 3. 去重              │
                               └──────────┬──────────┘
                                    ┌─────┴─────┐
                                 重复│           │新
                                    ▼           │
                          ┌──────────────┐      │
                          │ 强化 support  │      │
                          │ +1，更新时间  │      │
                          └──────────────┘      │
                                                ▼
                                     ┌─────────────────────┐
                                     │ 4. 冲突检测          │
                                     └──────────┬──────────┘
                                          ┌─────┴─────┐
                                       冲突│           │无冲突
                                          ▼           │
                                   ┌────────────┐     │
                                   │ 取代链处理  │     │
                                   └─────┬──────┘     │
                                         └─────┬──────┘
                                               ▼
                                    ┌─────────────────────┐
                                    │ 5. 置信度路由        │
                                    └──────────┬──────────┘
                              ┌────────────────┼────────────────┐
                              ▼                ▼                ▼
                        ┌──────────┐   ┌──────────────┐  ┌──────────┐
                        │ 直接写入  │   │ 待用户确认    │  │ 拒绝写入  │
                        │ ACTIVE   │   │ PENDING      │  │ REJECTED │
                        └──────────┘   └──────────────┘  └──────────┘
```

### 3.1 价值判定：什么值得记

| 记 | 不记 | 理由 |
|---|---|---|
| 与宠物**持久属性**相关（喜好 / 习惯 / 禁忌 / 性格） | 一次性闲聊 | 属性会被反复检索 |
| **重复出现**的模式（"最近晚上总是..."） | 已在 Profile 层的稳定事实 | 重复记录无增益，只增噪声 |
| 有**时间锚点**的事件（"昨天..."） | 时效极短的临时状态 | 后者应进 Session 层 |
| 用户**显式要求**记住的 | **系统自身的输出** | 见 §3.5，这是硬红线 |
| 可用于**未来解释**的（触发条件 → 行为） | 无法验证的推断 | 会污染检索 |

> **判据一句话**：这条信息**未来会不会被再次用到**？
> 不会 → 不记。记忆的价值在于被检索，不在于被存储。

### 3.2 去重：**强化**，不是重复插入

同一信息被说三次，应该产生 **1 条记忆 + `support_count = 3`**，而不是 3 条记忆。

```python
# 语义去重，而非字符串去重
if max_similarity_to_existing >= DEDUP_TAU:      # 默认 0.92
    existing.support_count += 1
    existing.last_seen_at = now
    existing.confidence = boost(existing.confidence, existing.support_count)
    return MemoryWriteDecision(action="reinforce", ...)
```

**为什么强化比插入更有价值**：

1. 检索重排序可以把 `support_count` 当特征——反复出现的模式更可信
2. `support_count ≥ 3` 是 Session/Episode 晋升到 Profile 的触发条件
3. 避免同一事实在 top-K 里重复占位（否则 5 条召回可能全是同一件事）

字符串去重不够用：「它怕吸尘器」和「一开吸尘器它就跑」语义等价但字面不同。

### 3.3 冲突消解：时序 + 取代链

用户先说「喜欢逗猫棒」，后说「最近不喜欢逗猫棒」。**这不是错误，是演变。**

#### 冲突的判定条件（三个都要满足）

```
① 同一主体：pet_id + event_type + subject 相同
② 极性相反：polarity_positive vs polarity_negative
③ 时间范围重叠：valid_from/valid_to 有交集
```

**第 ③ 条最关键。** 这两句不冲突：

| 陈述 | 时间范围 | 判定 |
|---|---|---|
| 「它上个月喜欢逗猫棒」 | [上月1日, 上月30日] | 不重叠 |
| 「它这周不喜欢逗猫棒」 | [本周1日, 本周7日] | → **不冲突，是演变** |

而这两句冲突：

| 陈述 | 时间范围 | 判定 |
|---|---|---|
| 「它喜欢逗猫棒」 | [-, -]（无边界 = 现在有效） | 重叠 |
| 「它最近不喜欢逗猫棒」 | [近 7 天, 现在] | → **冲突** |

#### 消解：保留取代链，不删除历史

```
M1: 喜欢逗猫棒
    valid_from: 2026-01-15   valid_to: 2026-09-05
    status: SUPERSEDED       superseded_by: M2

M2: 最近不喜欢逗猫棒
    valid_from: 2026-09-05   valid_to: null
    status: ACTIVE           supersedes: [M1]
```

**为什么要保留链而不是覆盖**：

1. 用户问「它以前喜欢什么」→ 需要 M1
2. 审计「为什么系统认为它不喜欢逗猫棒了」→ 需要链
3. 可能是用户记错了 → 保留可回滚

#### 消解的优先级规则

| 情形 | 处理 |
|---|---|
| 新信息来自更可信来源（用户纠正 > 用户陈述 > 系统推断） | 新记忆 ACTIVE，旧的 SUPERSEDED |
| 新信息来自**更低**可信度来源 | **不覆盖**，新记忆进 PENDING_CONFIRMATION |
| 时间范围重叠但方向是"变化" | 正常演变，建取代链 |
| 时间范围不重叠 | **不是冲突**，两条并存 |

> 面试要点：冲突消解**不能只靠 LLM 判断**。
> LLM 负责抽取出 `subject` / `polarity` / `time_range` 这三个结构化字段，
> **判定逻辑由代码执行**。否则同一对矛盾，模型两次调用可能给出不同结论。

### 3.4 置信度路由

| 来源 | 初始置信度 | 路由 |
|---|---|---|
| 用户显式纠正系统 | 0.95 | ACTIVE + 触发冲突消解 |
| 用户显式陈述 | 0.90 | ACTIVE |
| 用户对解释结果的确认 | 0.90 | ACTIVE（同时作为声学样本标签） |
| **ASR 转写后抽取** | 0.90 × 0.85 | ACTIVE，但**时间/数字字段需确认** |
| 系统推断 | ≤ 0.60 | **PENDING_CONFIRMATION** |

**ASR 降权的原因**：语音识别错误会被当作事实存下来，且事后无法察觉。
「团团每天**三点**叫我」被转成「**三点**」还是「**三點**」无所谓，
但转成「**三只**」就产生了错误事实。因此对**时间、数量**类字段降权并要求确认。

### 3.5 防自我强化（记忆投毒防护）

**这是本模块最重要的安全设计。**

失败模式：

```
第 1 轮：用户说"它一直盯着门叫"
        → 模型推测"可能是想让你开门"
        → ❌ 若把这条推测存为事实

第 2 轮：用户又问类似问题
        → 检索到"它想让你开门"（此时已被当成事实）
        → 模型更确信："它确实是想要你开门"
        → ❌ 存下更高置信度的版本

第 N 轮：幻觉被反复强化，成为"系统已知事实"
```

**根因**：模型输出不能作为下一轮的输入事实。这是**自监督闭环的退化**。

#### 防护规则（结构性，不靠 prompt）

| # | 规则 |
|---|---|
| R1 | `source = SYSTEM_INFERENCE` 的记忆**永远不得**以 `ACTIVE` 状态写入 |
| R2 | 只允许写入 `PENDING_CONFIRMATION`，且不参与默认检索 |
| R3 | 用户确认后转为 `ACTIVE`，同时 `source` 改写为 `USER_CONFIRMATION` |
| R4 | 未被确认的 `PENDING` 记忆超过 N 天 → 自动 `REJECTED` |
| R5 | 检索时**默认排除** `PENDING_CONFIRMATION` 与 `SUPERSEDED` |
| R6 | 由系统推断派生的记忆，其 `confidence` 不得作为后续推断的先验 |

R6 是防间接强化：即使 R1–R5 拦住了直接写入，
推测也可能通过「提高其他记忆的置信度」间接污染。

**可测性**：评测集中有一条断言——**数据库中 `source = system_inference AND status = ACTIVE` 的记录数必须恒为 0**。
这条断言可以直接作为 CI 检查项。

## 4. 检索：混合检索 + 重排序 + 多样性

### 4.1 为什么必须混合

| 方式 | 擅长 | 短板 |
|---|---|---|
| 向量检索 | 语义相似（"害怕吸尘器" ↔ "听到吸尘器就跑"） | 无法处理精确的时间/类型/状态约束 |
| 关系检索 | 结构化过滤（时间窗口、类型、状态） | 无法处理语义 |

只用向量 → 「最近三天」的约束会失效，召回半年前的记忆。
只用关系 → 语义变体召回不到。

### 4.2 检索管线

```
查询
 │
 ├─ ① 结构化预过滤（硬约束，不可省略）
 │     pet_id = ?               ← 多宠物隔离，必须
 │     status = ACTIVE          ← 排除 PENDING / SUPERSEDED
 │     event_type ∈ 路由推断的类型
 │     valid_to IS NULL OR valid_to >= 查询时间下界
 │
 ├─ ② 向量召回 top-K（K = 20）
 │
 ├─ ③ 重排序（见下）
 │
 ├─ ④ 多样性裁剪（MMR）
 │
 └─ ⑤ Top-N（N = 5）注入上下文
```

### 4.3 重排序公式

```
score = w₁ · semantic_similarity
      + w₂ · recency_decay(observed_at, halflife(event_type))
      + w₃ · min(1, log(1 + support_count) / log(1 + 5))
      + w₄ · source_trust
      + w₅ · type_match(intent)
```

**关键：`halflife` 依赖 `event_type`**

| event_type | halflife | 理由 |
|---|---|---|
| `PREFERENCE` | ∞（不衰减） | 半年前喜欢的玩具，今天依然成立 |
| `ROUTINE` | ∞ | 习惯是长期属性 |
| `BEHAVIOR` | 30 天 | 「昨天害怕吸尘器」两周后参考价值下降 |
| `CONTEXT` | 7 天 | 「今天加班」很快过时 |
| `HEALTH` | 按 `HealthDataPolicy` | 健康信号有独立保留期 |

用统一衰减率是常见错误：它会让系统忘记宠物"一直喜欢"的东西，
却记住"上周三发生的琐事"。

### 4.4 多样性（MMR）

避免 5 条召回全是同一件事的变体：

```
MMR = argmax [ λ · score(dᵢ) − (1−λ) · max_{dⱼ∈已选} sim(dᵢ, dⱼ) ]
```

如果强化机制（§3.2）工作正常，同一事实只会有 1 条，
但不同事件仍可能高度相似（"害怕吸尘器" / "害怕吹风机" / "害怕理发器"）。

## 5. 上下文注入契约

**不要**把检索结果平铺成一段自由文本塞进 prompt。

```jsonc
{
  "pet": { "name": "团团", "identity": "橘白短毛、圆脸、胸口白毛、左耳缺口" },
  "known_facts": [
    { "content": "害怕吸尘器", "source": "user_observation",
      "confidence": 0.9, "support_count": 3, "observed_at": "2026-08-20" },
    { "content": "喜欢逗猫棒", "source": "user_observation",
      "confidence": 0.9, "support_count": 1, "observed_at": "2026-07-02" }
  ],
  "unconfirmed": [],          // PENDING 记忆单独标注，模型不得当作事实
  "retrieval_note": "以上为检索到的记录。未在其中的信息即为没有记录，不要推测。"
}
```

三个要点：

1. **必须区分「已确认」与「待确认」**——模型不能把系统猜测当事实用
2. **必须携带 `source` 与 `confidence`**——否则 `response_guard` 无法判定断言是否有据
3. **必须显式说明「检索不到就是没有」**——否则模型会用常识补全（幻觉的主要来源）

## 6. 遗忘

**遗忘 ≠ 删除。** 分三种语义：

| 机制 | 语义 | 实现 |
|---|---|---|
| **检索排除** | 数据还在，但默认不返回 | `status = SUPERSEDED` 或衰减后 score 低于阈值 |
| **降权** | 返回但排序靠后 | `recency_decay` |
| **硬删除** | 数据消失 | 用户主动删除 / 账号注销 / 保留期到期 |

**只有用户主动要求或法定保留期到期才硬删除。** 其余都是检索层的事。

这样「你记得它去年…」这类问题仍然可答，而默认对话不会被陈年琐事干扰。

## 7. 多租户隔离

**任何存储操作必须携带 `user_id` + `pet_id`，向量检索必须按 `pet_id` 过滤。**

不隔离的后果是灾难性的且用户可见：

```
用户有两只猫：团团（黏人）和阿橘（警惕）
用户问："团团最近怎么样？"
→ 未过滤的向量检索命中"阿橘最近很警惕"
→ 模型回答："团团最近比较警惕……"
→ 用户立即发现系统错了，且从此不再信任记忆功能
```

**实现层强制**，不靠调用方自觉：

```python
class MemoryStore:
    def search(self, *, user_id: str, pet_id: str, query: str, ...):
        # pet_id 为必填关键字参数，无默认值
        # 所有查询构造器统一注入 pet_id 过滤条件
        ...
```

隔离性是**评测项**：两条宠物记忆的交叉污染率必须为 0。

## 8. 存储选型

| 数据 | 选型 | 理由 |
|---|---|---|
| Profile | 关系库（PostgreSQL / MySQL） | 强结构、需事务、主键直读 |
| Episode（结构化部分） | 关系库 | 时间范围、状态、取代链查询 |
| Episode（向量） | pgvector（首选）或 Milvus | 与关系库同源可用 JOIN 做预过滤；已有 Milvus 经验可复用 |
| Session | Redis | 天然 TTL |

**pgvector 优先于 Milvus 的理由**：本场景需要「先结构化过滤、再向量检索」，
在同一个库里 JOIN 最直接。Milvus 适合大规模独立向量检索，
但在这里会引入跨库一致性问题（向量删了、关系记录没删）。

> 如果面试时被问「为什么不用 Milvus」，这就是答案：
> 不是能力问题，是**一致性成本**问题。

## 9. 评测

| # | 测试 | 方法 | 指标 | 通过标准 |
|---|---|---|---|---|
| E1 | 记忆准确率 | 问「团团怕什么」 | 有据陈述率 / **无据陈述率** | 无据陈述率 = 0 |
| E2 | 幻觉 | 问档案中不存在的信息 | 误答率 | 应回答「没有记录」，误答率 = 0 |
| E3 | 冲突更新 | 先「喜欢逗猫棒」→ 后「不喜欢」 | 返回新值 + 保留旧链 | 两者都要满足 |
| E4 | 非冲突识别 | 先「上个月喜欢」→ 后「这周不喜欢」 | 不误判为冲突 | 两条并存 |
| E5 | 去重强化 | 同一信息说 3 次 | 记忆条数 / support_count | 1 条 / 3 |
| E6 | 租户隔离 | 两猫有相似记忆 | 交叉污染率 | 0 |
| E7 | 遗忘 | 30 天前的一次性事件 | 默认检索是否排除 | 排除，但可显式查询到 |
| E8 | **投毒防护** | 多轮诱导模型猜测 | `system_inference AND ACTIVE` 条数 | **恒为 0** |
| E9 | ASR 污染 | 含数字的语音输入 | 错误事实写入率 | 时间/数字字段需确认 |
| E10 | Profile 不漂移 | 反复询问身份 | 身份字段是否被事件污染 | 不漂移 |

**E8 是核心安全断言**，建议直接在数据库上加检查约束或 CI 断言。

## 10. 面试问答速查

| 追问 | 回答要点 |
|---|---|
| 「你用了 RAG 吗？」 | 「用了，但只用在事件层。身份层是主键直读——**能精确定位的数据不该用相似度去找**。」 |
| 「什么该记什么不该记？」 | 「判据是**未来会不会被再次检索**。属性、重复模式、有时间锚点的事件该记；闲聊和临时状态不记。」 |
| 「记重复了怎么办？」 | 「不是去重插入，是**强化**：`support_count += 1`。这同时是晋升到身份层的触发条件。」 |
| 「前后矛盾怎么办？」 | 「冲突判定要三个条件同时满足：同主体、极性相反、**时间范围重叠**。缺第三条就误判演变。消解用**取代链**而非覆盖，历史保留。」 |
| 「会不会自我强化？」 | 「这是我最担心的点。**模型输出永远不能作为下一轮的事实输入**：系统推断只能进 PENDING，用户确认才转 ACTIVE。评测里有一条硬断言——`system_inference AND ACTIVE` 恒为 0。」 |
| 「遗忘怎么做？」 | 「遗忘不等于删除。默认检索排除是主要机制，硬删除只由用户主动或保留期到期触发。」 |
| 「多只猫会串味吗？」 | 「`pet_id` 是存储层的必填参数，不靠调用方自觉。隔离率是评测项，要求 0 污染。」 |
| 「为什么不用 Milvus？」 | 「不是能力问题，是一致性成本。我需要『先过滤再检索』，同库 JOIN 最直接。」 |
